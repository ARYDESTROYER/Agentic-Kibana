    Agentic SOC 0.1¶

    Agentic SOC 0.1 is the first standardized application and documentation release line. Human-facing documentation uses 0.1; the current source version is Semantic Version 0.1.12. It carries the accepted application scope through 0.1.11 and corrects the post-verification fixture-cleanup defect that stopped the immutable 0.1.11 signed-release job before publishing a GitHub Release.

    Builds on Testing are integration and acceptance builds. Version 0.1.12 is a supported Stable patch only when the accepted tree is on main, the resulting commit has passed the release gate, and that exact commit is tagged v0.1.12 with verifiable signed release artifacts and public image digests. If that evidence is incomplete, use a previously verified Stable release. The immutable v0.1.4 tag records a failed publication that produced documentation but no application artifacts. The immutable v0.1.5 workflow built and signed candidate image digests but stopped before the canonical plan, bundle, GitHub Release, and Stable tags. Neither is an update or bootstrap source. The immutable v0.1.6 artifact set published and signed successfully, but canonical macOS Bash 3.2 bootstrap acceptance failed before supervisor installation. It is superseded and is not an update or bootstrap source. The immutable v0.1.7 artifact set also published, signed, and pulled anonymously, but its updater process could not create the control socket under the shipped capability boundary. It remains an immutable publication record and is superseded by 0.1.8; do not use it as an installation or update source. The immutable v0.1.8 publication corrected that socket boundary but canonical bootstrap then failed when cosign 3 tried to initialize its default TUF cache beneath the read-only root filesystem. It too is superseded and is not an installation or update source. The immutable v0.1.9 workflow corrected that trust-root path, passed exact-tag CI, built and signed all three public image digests, passed anonymous registry checks, and generated and host-verified its signed plan. Its constrained updater could not traverse the runner-owned /verification bind source, so the workflow published no GitHub Release, plan assets, Stable convenience tags, or Stable Help Center. It is immutable partial evidence, not an installation or update source. The immutable v0.1.10 tag passed protected source and exact-tag CI, but its signed-release job timed out while the architecture-neutral Web Console builder ran under target emulation. It published no complete three-image set, canonical signed plan, GitHub Release, Stable tags, or Stable Help Center. It is immutable partial evidence, not an installation or update source. The immutable v0.1.11 workflow then built, signed, anonymously proved, and verified all three images and the canonical plan on the host and inside the constrained updater. Its post-verification cleanup trap could not unlink the read-only fixture files while their runner-owned parent directory remained mode 0555. It published no attestations, GitHub Release, canonical plan assets, Stable tags, or Stable Help Center. It too is immutable partial evidence, not an installation or update source. Branch state alone never establishes the installed release identity.

    The repository uses Testing for integration and default main for accepted source. Patch 0.1.12 rebuilds the public and installed 0.1 guide without changing the documentation selector line; already-built artifacts keep their immutable bundled Help Center. Versions 0.1.2 and 0.1.3 remain unpublished historical Testing records. Versions 0.1.4 and 0.1.5 remain immutable failed-publication records, not installable Stable releases or artifact sources. Version 0.1.6 remains an immutable signed publication record, but not a supported bootstrap source. Version 0.1.7 remains an immutable signed publication record whose canonical updater bootstrap is blocked by its control-socket startup defect. Version 0.1.8 remains an immutable signed publication record whose canonical updater bootstrap is blocked by its read-only Sigstore trust-root defect. Version 0.1.9 remains an immutable failed-publication record whose canonical Release and signed-plan asset pair were never published. Version 0.1.10 remains an immutable failed-publication record whose release job timed out before the complete signed artifact set or canonical Release existed. Version 0.1.11 remains an immutable failed-publication record whose cleanup failure occurred after successful constrained plan verification but before canonical Release publication.

    What 0.1 provides¶

    • Vendor-neutral pull and push ingestion normalized to OCSF.
    • Elasticsearch, OpenSearch, and Wazuh pull connectors plus a broad receiver catalog.
    • Durable cursors, deterministic correlation/risk scoring, and source-scoped case identity.
    • Tiered model investigation through one cost-ledger gateway.
    • Deterministic close/escalate policy that the model, a playbook, or notification cannot override.
    • A Security Command Center with selected-window lifecycle KPIs, active risk, open/resolved composition, latest-case hover details, noise reduction, response timing, and deeper analytics. It defaults to visibility-aware five-second LIVE refresh and can expand Noise Reduction without exposing raw alert IDs.
    • Cases, traces, rationale, collaboration, feedback, campaigns, baselines, tuning, rules, and custom dashboards. Case Manager provides a persisted, accessible resizable split-pane active/all queue, a six-tab canonical detail workspace, redacted alert → cluster → case explanation, and permission-gated bulk operations. The Cases table remains available during migration and hands exact record links into Case Manager.
    • A personal Workspace Chat with newest-first searchable saved conversations, desktop history rail/narrow History Sheet, per-thread browser drafts, strict source selection, effective source/model provenance, bounded retention, and one docked composer. Case Manager Chat uses the same read-only engine while remaining case-scoped and outside personal Workspace history.
    • A standardized command-center Console grammar with a minimal identity-first sign-in, searchable flat Settings frame, persisted System/Light/Dark appearance, route-aware loading feedback, a bottom Documentation destination, and the targeted Entity investigation workflow. The sign-in surface keeps optional demo/SSO paths practical, removes marketing and synthetic audit copy, and honors narrow/reduced-motion states. Documentation opens the version-matched Help Center bundled with the app; GitHub is a secondary source/edit destination. The redundant Automated Scans screen remains deep-link compatible but is removed from primary navigation.
    • A browse/open/create/edit Playbooks manager for operator-authored Markdown; bundled procedures remain protected and every mutation is permission-gated, atomically reloaded, and audited.
    • A dedicated Intelligence → Runbooks workspace for protected bundled and durable operator-authored investigation guidance. Authorized operators can create, edit, delete, and reindex compact trusted references through optimistic revisions. New revisions enforce a 1,800-character, fixed-section plain-text body, a 1,200-character aggregate retrieval-metadata budget, and actionable Problem / Why / Fix validation; retrieval status and partial failures remain explicit, and deterministic case policy is unchanged.
    • PostgreSQL/pgvector, Elasticsearch, or SQLite application-state backends.
    • Local authentication, sessions, RBAC/custom roles, TOTP MFA, and OIDC SSO.
    • Provider-aware notifications, knowledge retrieval, enrichment, and spend controls.
    • Compatible official OpenAI alert/case calls prefer live Flex with truthful standard fallback by default; the independent asynchronous Batch queue remains opt-in.
    • An isolated five-source Demo Mode (Splunk, QRadar, Wazuh, syslog, and Microsoft Entra ID / Active Directory) and a bounded, audited, secret-free portable application-state export for authorized administrators.
    • A standalone React web console and version-matched Help Center served from the same application origin, with a complementary versioned public Stable site.

    Safe defaults and explicit choices¶

    The balanced autopilot profile performs broad deterministic ingest/routing and enables a $10/day blocking LLM budget backstop. A blocked provider call routes work to human review rather than silently discarding it. NEEDS_HUMAN never auto-closes, and true-positive auto-close remains an explicit opt-in.

    Authentication is off in the base configuration for isolated evaluation compatibility. Operators must enable authentication, replace demonstration credentials, configure HTTPS/secure cookies, and apply least privilege before shared use.

    Recommended deployment¶

    Use the standalone Compose stack with PostgreSQL/pgvector for application state and Redis for caching. Connect source systems through scoped connector credentials. Existing Elasticsearch environments may instead hold Agentic SOC state in dedicated indices, using separate management and read-only log credentials.

    Record the exact tag, image digests, commit SHA, build date, state backend, and /api/health/build-info response. A branch name alone is not a release identity. The Console badge shows v0.1.12 · Testing|Stable and exposes both Console and backend stamps; any identity mismatch is visibly downgraded to Testing.

    Important limitations¶

    Version 0.1 does not claim:

    • high availability or horizontally coordinated workers;
    • a complete database migration/rollback framework;
    • an integrated durable secret manager;
    • durable pre-ack receipt semantics for every push transport;
    • multi-tenant row-level isolation by default;
    • production certification for every source/vendor combination;
    • that Agentic SOC ledger estimates equal provider invoices;
    • autonomous write-side response actions.

    Use synthetic or non-sensitive data until the selected deployment, source protocol, model provider, backup, and failure behavior have been validated. Read the full Known limitations.

    Upgrade and support boundary¶

    Back up the state store and deployment secrets before changing versions. Because 0.1 lacks a complete schema-migration framework, do not assume that starting an older image is a safe rollback; restore the matching pre-upgrade state when compatibility is not explicitly documented.

    Start with Deployment, Security hardening, and Documentation versions. Read the detailed 0.1.12 Stable patch record before promoting or upgrading. The 0.1.11 failed-publication record, 0.1.10 failed-publication record, 0.1.9 failed-publication record, 0.1.8 bootstrap-blocked publication record, 0.1.7 bootstrap-blocked publication record, 0.1.6 superseded publication record, 0.1.5 failed-publication record and 0.1.4 failed-publication record are immutable but non-installable; the 0.1.3 record and 0.1.2 record remain historical unpublished Testing snapshots.

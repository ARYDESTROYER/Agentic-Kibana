    Agentic SOC 0.1.12¶

    Agentic SOC 0.1.12 is the governed constrained-verifier cleanup correction after the immutable, non-installable v0.1.11 publication attempt. Version 0.1.11 passed protected Testing, promoted-main, and exact-tag CI. Its signed-release workflow built and pushed all three dual-platform images, signed and verified every immutable digest, proved anonymous registry access and exact OCI labels, generated and signed the canonical release plan, and verified that plan both on the host and inside the production-constrained updater.

    The substantive verifier completed successfully. The workflow failed immediately afterward when its cleanup trap tried to unlink mode-0444 verification files from their runner-owned parent directory, which still had mode 0555:

    Verified OK
rm: cannot remove '.../upgrade-plan.sigstore.json': Permission denied
rm: cannot remove '.../upgrade-plan.json': Permission denied

    The failure occurred before attestations, GitHub Release publication, canonical plan asset publication, Stable convenience tags, or Stable Help Center publication. No application update began. Version 0.1.12 preserves v0.1.11 as immutable evidence and corrects only the post-verification cleanup boundary.

    This patch changes no application behavior, application-state schema, updater protocol, signed-plan schema, keyless publisher identity, process UID/GID, capability set, trust predicate, or frozen base Compose file. It remains in documentation line 0.1.

    A candidate is not an installable Stable release

    A branch head, checkout, version string, candidate image, generated plan, or signature alone cannot authorize an update. Version 0.1.12 becomes installable only after the annotated tag v0.1.12 resolves to the accepted main commit, every fail-closed tag and release gate passes, the public GitHub Release exposes exactly the canonical plan and bundle, all three pinned digests are anonymously readable and signature-verified, and canonical bootstrap/update acceptance succeeds. Until then, keep the existing supported deployment unchanged.

    The immutable v0.1.11 tag never received a public GitHub Release or canonical asset pair. Never move, reuse, repair, install, or bootstrap from it.

    What changed after 0.1.11¶

    The release-only constrained-verifier fixture keeps its least-privilege state for the entire container verification:

    • upgrade-plan.json and upgrade-plan.sigstore.json remain mode 0444;
    • their runner-owned verification directory remains mode 0555;
    • the real updater still runs with the shipping read-only root filesystem, cap_drop: ALL, no-new-privileges, and the production UID/GID; and
    • cosign still reads its trust state from the existing writable updater-state volume.

    Only after the constrained updater exits does workflow cleanup:

    1. preserve the verifier step's original exit status and disable recursive EXIT handling;
    2. request removal of the exact verifier container, then query Docker for that exact anchored name;
    3. fail closed and retain the mode-0555 fixture if Docker is unavailable or the verifier container still exists;
    4. remove the verifier's transient volumes only after container absence is proven;
    5. guard that the temporary verification directory still exists, restore that runner-owned directory to its original private mode 0700, and remove it; and
    6. return the original verifier failure, or promote a cleanup failure when the verifier itself succeeded.

    This is post-verification runner hygiene, not a verifier permission workaround. It does not make the plan writable during verification, recursively relax permissions, change ownership, override the updater entrypoint, or expand container privilege.

    Carried application scope¶

    This patch carries the complete accepted 0.1 application scope described by the 0.1 release line, including:

    • vendor-neutral OCSF ingest, deterministic correlation/risk/decision boundaries, and one cost-ledgered LLM gateway;
    • the Security Command Center, canonical split-pane Case Manager, durable Workspace Chat, collaboration, and version-matched installed Help Center;
    • governed runbook/playbook, memory, tuning, rules, approval, enrichment, and export workflows; and
    • signed supervised updates for the supported canonical PostgreSQL Compose profile.

    The model, memory, runbook, and playbook layers remain advisory. Deterministic code continues to own the final close/escalate route.

    Immutable release artifacts¶

    The canonical repository is ARYDESTROYER/Agentic-Kibana. After successful publication, the workflow exposes these convenience tags:

    ghcr.io/arydestroyer/agentic-kibana/backend:v0.1.12
ghcr.io/arydestroyer/agentic-kibana/webui:v0.1.12
ghcr.io/arydestroyer/agentic-kibana/updater:v0.1.12

    Convenience tags are not update authority. The signed plan contains only immutable digest references:

    ghcr.io/arydestroyer/agentic-kibana/backend@sha256:<digest>
ghcr.io/arydestroyer/agentic-kibana/webui@sha256:<digest>
ghcr.io/arydestroyer/agentic-kibana/updater@sha256:<digest>

    The public GitHub Release must contain exactly these two canonical assets:

    upgrade-plan.json
upgrade-plan.sigstore.json

    Their canonical URLs are:

    https://github.com/ARYDESTROYER/Agentic-Kibana/releases/download/v0.1.12/upgrade-plan.json
https://github.com/ARYDESTROYER/Agentic-Kibana/releases/download/v0.1.12/upgrade-plan.sigstore.json

    The expected keyless Sigstore certificate identity and OIDC issuer are:

    https://github.com/ARYDESTROYER/Agentic-Kibana/.github/workflows/release.yml@refs/tags/v0.1.12
https://token.actions.githubusercontent.com

    The workflow identity signs each image digest and the canonical release plan. The updater verifies the certificate identity, issuer, repository, annotated tag, dereferenced tag commit, release version, compatibility envelope, and every exact component digest.

    Compatibility and migration¶

    The supervised path supports only the canonical single-replica standalone Compose deployment with PostgreSQL-owned state, canonical project/service/container/network names, the canonical PostgreSQL volume, durable secrets, TLSOC_AUTH_ENABLED=true, and updater protocol 1.

    The frozen deploy/docker-compose.agnostic.yml SHA-256 remains:

    e3f7ecbb0f749cc9d88f4392c58c9a63ddbd064e80ecde9f21fe9de199086fd4

    Release-specific version and digest pins exist only in the signed generated override. A base-file change requires a new protocol and manual bootstrap; it cannot be hidden in a patch plan.

    SQLite, Elasticsearch-owned state, external PostgreSQL, Kubernetes, the legacy ELK merge, horizontal replicas, modified Compose topology, missing durable secrets, or unsupported migrations remain Manual upgrade required. PostgreSQL and Redis infrastructure remain operator-managed.

    There is no application-state schema migration in 0.1.12. A verified PostgreSQL dump is mandatory before switching. Automatic rollback restores prior application image pins; database restore remains an explicit break-glass operation because an automatic restore could discard valid writes.

    Operator bootstrap runbook¶

    Use this procedure only after the exact 0.1.12 signed release and canonical runtime acceptance are green. For a canonical deployment still running the supported pre-supervisor Stable baseline, use a clean checkout of the exact annotated tag as the one-time host-authorized transport:

    git fetch --tags origin
git switch --detach v0.1.12
test "$(git cat-file -t v0.1.12)" = tag
test "$(git rev-parse 'v0.1.12^{commit}')" = "$(git rev-parse HEAD)"
test -z "$(git status --porcelain --untracked-files=all)"
test "$(sha256sum deploy/docker-compose.agnostic.yml | awk '{print $1}')" = \
  "$(tr -d '[:space:]' < deploy/update-base-v1.sha256)"

# .env must contain durable TLSOC_PG_PASSWORD, TLSOC_AUTH_ENABLED=true,
# TLSOC_AUTH_JWT_SECRET with at least 32 characters, and:
# AGENTIC_SOC_UPDATE_REPOSITORY=ARYDESTROYER/Agentic-Kibana
./scripts/bootstrap-updater.sh

    Bootstrap verifies the exact public Release before installing or reconciling the private supervisor and applying its strictly newer plan. Active, unreadable, malformed, or otherwise unsafe supervisor state fails closed. After a successful transition, use ./scripts/agentic-soc-compose.sh for every manual lifecycle operation so the active digest override and lifecycle lock remain in effect.

    A deployment already running 0.1.12 cannot bootstrap from the same-version plan. The actionable Console update path becomes useful when a later compatible Stable release exists; it does not invent an update newer than the installed release. Testing/source-built 0.1.3 and immutable 0.1.4 through 0.1.11 failed or bootstrap-blocked records cannot be relabelled Stable and must be reconciled against their actual installed state.

    Independent artifact verification¶

    Verify that the remote exposes both the annotated tag object and its dereferenced commit:

    git ls-remote --tags https://github.com/ARYDESTROYER/Agentic-Kibana.git \
  refs/tags/v0.1.12 'refs/tags/v0.1.12^{}'

    The command must return two different 40-character IDs: the tag object and the accepted main commit.

    Verify the canonical plan with a reviewed cosign installation:

    tag=v0.1.12
repo=ARYDESTROYER/Agentic-Kibana
identity="https://github.com/${repo}/.github/workflows/release.yml@refs/tags/${tag}"
base="https://github.com/${repo}/releases/download/${tag}"

curl --fail --location --output upgrade-plan.json "${base}/upgrade-plan.json"
curl --fail --location --output upgrade-plan.sigstore.json \
  "${base}/upgrade-plan.sigstore.json"

cosign verify-blob \
  --bundle upgrade-plan.sigstore.json \
  --certificate-identity "${identity}" \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com \
  upgrade-plan.json

    Verify every immutable image signature and anonymous registry read with a fresh Docker configuration so cached credentials cannot satisfy the public-access test:

    anonymous_docker_config="$(mktemp -d)"
for component in backend webui updater; do
  image="$(jq -er --arg component "${component}" \
    '.components[$component].image' upgrade-plan.json)"
  cosign verify \
    --certificate-identity "${identity}" \
    --certificate-oidc-issuer https://token.actions.githubusercontent.com \
    "${image}"
  DOCKER_CONFIG="${anonymous_docker_config}" docker buildx imagetools inspect \
    "${image}" >/dev/null
done

    The workflow also performs credential-free HTTP verification of every exact index, child manifest, and config. All three GHCR packages must be Public; image push alone does not change package visibility.

    Release acceptance¶

    Publication requires the fail-closed CI passed aggregate on the frozen 0.1.12 candidate on Testing, the resulting accepted main commit, and the immutable annotated tag v0.1.12. The tag workflow then requires:

    1. annotated tag and dereferenced commit equal the accepted main SHA;
    2. all three dual-platform images build with exact Stable labels and signatures;
    3. every image digest is anonymously readable and content-verified;
    4. the plan passes schema, compatibility, digest, and Sigstore checks;
    5. the real updater verifies the plan inside the production-constrained runtime;
    6. post-verification cleanup proves the verifier bind is gone, restores only the runner-owned fixture directory, preserves the original result, and completes without weakening the verification-time permissions;
    7. attestations complete;
    8. the private draft contains exactly the canonical notes, plan, and bundle;
    9. downloaded assets byte-match and signature-verify before one atomic public transition; and
    10. Stable convenience tags are created only after Release publication.

    Canonical PostgreSQL Compose acceptance must then bootstrap from the supported baseline, retain the verified backup and durable receipt, switch to the exact plan digests, and pass the post-update Console browser matrix. Never move, reuse, repair, or republish a tag. Any later defect receives a newer SemVer.

    Exact Stable build identity¶

    Resolve every Stable stamp from the exact annotated tag on the accepted main commit. Never substitute a branch head, local clock, or unknown value:

    git switch main
git pull --ff-only origin main
git fetch --tags origin

release_version="$(tr -d '[:space:]' < VERSION)"
test "${release_version}" = "0.1.12"
release_sha="$(git rev-parse "v${release_version}^{commit}")"
test "${release_sha}" = "$(git rev-parse HEAD)"
release_date="$(git show -s --format=%cI "${release_sha}")"

export TLSOC_VERSION="${release_version}"
export TLSOC_RELEASE_CHANNEL=stable
export TLSOC_BUILD_SHA="${release_sha}"
export TLSOC_BUILD_DATE="${release_date}"

    Backend, Console, updater, /release.json, OCI labels, signed plan, annotated tag v0.1.12, and GitHub Release must resolve to one version and commit. Any mismatch fails safe to Testing and cannot authorize installation.

    Immutable annotated-tag checklist¶

    Create the tag only after the clean candidate passes on Testing, promotion passes on the resulting main commit, and the final tree is frozen:

    test "$(tr -d '[:space:]' < VERSION)" = "0.1.12"
test -z "$(git status --porcelain)"
git tag -a v0.1.12 \
  -m "Agentic SOC 0.1.12" \
  -m "Constrained-verifier cleanup correction. Detailed notes: docs/releases/0.1.12.md; CHANGELOG.md."
test "$(git cat-file -t v0.1.12)" = tag
test "$(git rev-parse 'v0.1.12^{commit}')" = "$(git rev-parse HEAD)"
git show --no-patch --show-signature v0.1.12
git push origin v0.1.12

    Do not create the tag before every candidate/main gate passes, and never force, delete, move, recreate, or reassign it after push. See Release channels and versioning for the canonical promotion sequence.

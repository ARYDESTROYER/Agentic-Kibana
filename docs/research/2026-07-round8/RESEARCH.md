## Root cause of the Cases-table "row peeks above header" sticky-header glitch (Round-8 ask #2)

**Findings:**
- `--header-h` IS correctly defined: webui/src/styles/theme.css:146 `--header-h: 56px;` inside the global `:root {}` block (theme.css:16), with a comment confirming it MUST match the AppShell top bar. It is NOT the bug — every consumer (PageHeader.tsx:127, ControlBar.tsx:63, FilterBar.tsx:46, DataTable→table.tsx:57) reads the same correctly-defined 56px value that matches AppShell.tsx:531 `h-14` (56px) GlassSurface top bar.
- ROOT CAUSE: a double, unintentionally-nested overflow ancestor defeats `position: sticky` before it ever reaches the window. `Cases.tsx:1318-1343` renders `<DataTable sticky rowAccent density='compact'>`. `DataTable.tsx:378-387` wraps everything in its own OUTER `<div className='overflow-hidden rounded-lg border ... shadow-elev1'>` (for rounded-corner clipping) and then calls `<Table aria-label={ariaLabel}>` — WITHOUT the `unwrapped` prop. `webui/src/ui/table.tsx:30-38` shows `Table`'s default (non-`unwrapped`) behavior: it wraps `<table>` in its OWN INNER `<div className='relative w-full overflow-auto'>`. So the sticky `<thead>` (`TableHeader sticky` at ui/table.tsx:46-64, applying `sticky top-[var(--header-h)] z-10 bg-surface ...` at line 57) has TWO ancestors between it and the window that both set `overflow` to something other than `visible`.
- Per the CSS Overflow/Position spec (and universally-documented browser behavior — this is THE most common 'position:sticky not working' cause), `position: sticky` computes its containing block against the NEAREST ancestor that is a scroll container (any `overflow` != `visible`, regardless of whether that ancestor's content actually overflows it) — it does NOT bubble further up to the window if that nearest ancestor never independently scrolls. Here the nearest such ancestor is `ui/table.tsx:36`'s inner `overflow-auto` div. That div has no fixed/max height — its box is always exactly as tall as its content (the whole `<table>`), so `scrollHeight === clientHeight` always and it NEVER develops its own internal scroll offset. Because sticky positioning is evaluated purely against THAT container's own (permanently-zero) scroll offset, the thead's 'stuck' state never engages relative to the real page scroll — it behaves like an ordinary in-flow block and scrolls away with the rest of the table content instead of parking at 56px under the app bar.
- This exactly explains the reported symptom: the true sticky element the user still sees pinned is the AppShell top bar (`AppShell.tsx:531`, genuinely `sticky top-0 z-30`, unobstructed — no overflow ancestor breaks it because `<main id=socMain>` at AppShell.tsx:669 and its child div have no `overflow` set). Cases.tsx's `PageHeader` (line 1041) is NOT itself `sticky` (no `sticky` prop passed), so nothing else pins between the app bar and the table. Once the column-header row (which never actually became sticky) scrolls up and off along with the rest of the table's top content, the first DATA ROW ends up sitting flush against the still-pinned 56px app-bar boundary with no header row above it — i.e. a row visibly occupies exactly the band where the column header was expected to remain, reading as 'a data row peeks above the column header' / 'sticky header not covering'. The header's `z-10` (table.tsx:57) is irrelevant to this — z-index only controls paint order for genuinely overlapping elements, and a non-positioned (non-stuck) header simply isn't there anymore to overlap; this is a POSITION defect, not a stacking (z-index) defect.
- Confirmed via `containerClassName`/`unwrapped` grep (webui/ toolwide): `DataTable.tsx` is the ONLY caller of `<Table>` and never passes `unwrapped` — so this same latent defect exists in the primitive for ANY future `<DataTable sticky>` use, not just Cases.tsx. `Cases.tsx` is currently the ONLY page passing `sticky` to `DataTable` (grep across `soc/pages/*` confirms no other page uses it yet), so the bug is currently only visible there.
- SECONDARY contributing bug (the 'orange left-accent bar odd' + general row unevenness): the `status` column cell (Cases.tsx:847-861) renders `<div className='flex flex-col items-start gap-1'><StatusBadge/><AutoClosedBadge/></div>`. `AutoClosedBadge` (webui/src/soc/components/badges.tsx:670-689) self-hides (`return null`, line 677) unless `isAutoClosedByAI(status, decisionBy)` is true (badges.tsx:636-645, i.e. terminal status + `decision_by === 'agent'`). So MOST rows render a single-line cell (compact `py-2`, table.tsx:140), but any auto-closed row stacks TWO badges vertically, growing that row taller than its siblings. Since `<table>` rows size to their tallest cell, this makes row heights inconsistent across the page. `DataTable.tsx:494-514`'s `rowAccent` inset box-shadow (`boxShadow: inset 3px 0 0 0 ${accentColor}`) is drawn per-row at whatever height that row happens to be, so the left accent bars visibly vary in length row-to-row — this is what reads as 'the orange left-accent bar odd', and it independently makes the compact table look uneven/glitchy even apart from the sticky defect.
**Recommendations:**
- Primary fix (restore real stickiness): in `webui/src/soc/components/DataTable.tsx:387`, stop letting `<Table>` add its own hidden inner scroll wrapper — call `<Table aria-label={ariaLabel} unwrapped>` — and move the (still-needed, for wide tables) horizontal scroll capability onto the DataTable's OWN outer wrapper by changing `DataTable.tsx:383` from `overflow-hidden rounded-lg ...` to an explicit-axis `overflow-x-auto overflow-y-visible rounded-lg ...` (do NOT use the `overflow-auto`/`overflow-hidden` shorthand, which sets both axes and is exactly what breaks sticky here). This leaves the vertical scroll chain unobstructed all the way to the window, so `TableHeader`'s `sticky top-[var(--header-h)] z-10` (ui/table.tsx:57) can finally engage against real page scroll and park under the 56px app bar as designed.
- Preserve the rounded-corner look without `overflow:hidden` clipping: since the outer wrapper no longer hides y-overflow, either add `rounded-t-lg` directly to the sticky `<thead>` classes (ui/table.tsx:57) so its own opaque `bg-surface` corner is rounded to match the card, or keep a small `overflow-hidden` layer ONLY around the (non-scrolling) card chrome that sits outside the scrollable region — do not let it re-wrap the sticky thead.
- Quick, lower-risk interim fix if the above is deferred: drop the `sticky` prop from the `<DataTable>` call in `Cases.tsx:1328` (revert to the pre-Round-7 non-sticky header) until the DataTable/Table primitive fix above lands — a plain non-sticky header is preferable to the current broken-sticky artifact, and since Cases.tsx is the only current consumer of `sticky`, this fully un-breaks the visible page with a one-line change.
- Fix the row-height inconsistency (the 'odd' accent bar) independently of the sticky fix: give the status cell's wrapper a fixed min-height that already accounts for the two-badge case (e.g. reserve `min-h-[2.25rem]` / equivalent on the `flex-col` div at `Cases.tsx:852`) so every row is the same height in compact density whether or not `AutoClosedBadge` renders, keeping `rowAccent`'s inset box-shadow (DataTable.tsx:510-514) visually uniform down the column.
- After the fix, spot check: (1) scroll the Cases page and confirm the column-header row now visibly parks at 56px below the app bar and rows scroll underneath it opaquely (bg-surface, ui/table.tsx:57) with no row visible above/through it; (2) confirm horizontal scroll still works for the full column set on a narrow viewport now that the inner `overflow-auto` div is gone and the outer div carries `overflow-x-auto`; (3) confirm auto-closed vs normal rows are visually the same height.

## RiskGauge/ActiveRiskIndex glitch at size 78 (Round-8 ask #1) — root cause + sizing fix

**Findings:**
- Mounted size is actually 64, not 78: webui/src/soc/pages/Overview.tsx:836 calls `<ActiveRiskIndex score={activeRisk.score} count={activeRisk.count} size={64} />` inside the PageHeader `hero` variant's `actions` slot (a `flex shrink-0 flex-wrap items-center gap-2` row meant for single-row control chips, PageHeader.tsx:188). ActiveRiskIndex.tsx:70 defaults `size = 78` only when no `size` prop is passed, so the on-screen instance is even smaller than the 78 in the ask.
- Both reported symptoms are real and have distinct root causes in RiskGauge.tsx. (A) 'stray diagonal notch line': the notch `<line>` (RiskGauge.tsx:161-173, geometry built at :113-129) is drawn RADIALLY (from `r - stroke/2` to `r + stroke/2` at angle theta), so its length always equals `stroke`, and `stroke = Math.max(8, Math.round(size*0.07))` (line 82) FLOORS at a fixed 8px for any size <= ~114. That means the tick's absolute length (8px) does NOT shrink as the gauge shrinks, so at size 64/78 it becomes a disproportionately large diagonal slash relative to the whole arc (8px on a 64-78px-diameter gauge vs. 8px on the 160px size the component was designed/tested at, e.g. RiskGauge.round7.test.tsx uses size=160 throughout, and ActiveRiskIndex.test.tsx's own notch-geometry test explicitly uses size={120}, not the production default). It is also positioned at a FIXED value (74, `CRITICAL_NOTCH = SCORE_BANDS.critical[0]`, ActiveRiskIndex.tsx:39) regardless of the actual score, so when the case load is low (e.g. score '8'), the notch sits far out on the muted/unfilled track, visually disconnected from the filled arc and the value text below it — reading as an unrelated stray mark rather than a meaningful threshold tick.
- (B) 'cramped 8/100': RiskGauge.tsx:135-136 computes `valueFont = Math.min(size*0.22, cy*0.5)` and `suffixFont = Math.max(9, valueFont*0.42)`. The 9px floor on suffixFont dominates the intended 0.42 ratio for ANY size below ~97px (solve `size*0.22*0.42 >= 9` → size >= ~97.4). At size 64 (suffixFont=9 vs. intended ~5.9) and size 78 (suffixFont=9 vs. intended ~7.2), the '/100' suffix is relatively oversized next to the shrunken score digit, producing the cramped look — independent of the notch bug.
- Structural aggravator: ActiveRiskIndex renders 3 stacked rows (caption+HelpTip, gauge, band-label text) — a vertical stack that does not belong inside a single-row header `actions` slot alongside other controls; this is what the user/MEMORY.md ask #1 already flags ('Round 7 moved it into header actions, size 64 — revert to a distinct card top-right').
- The notch tick does NOT spatially overlap the value-overlay text (the overlay is bottom-anchored within height `cy` at RiskGauge.tsx:178-179; at value=74 the notch sits in the upper-right, y-range well above the overlay) — so this is not a text/line collision bug, it is a disproportionate/disconnected-decoration bug plus a font-floor bug, compounding inside too little header real estate.
- A clean render exists elsewhere in the codebase as a reference: CaseTriageHeader.tsx:242 uses `<RiskGauge score={score} size={108} />` with NO notch, and the dashboard risk widget (soc/dashboard/widgets/risk.tsx:33) uses the RiskGaugeProps default size=160, also with no notch — both read clean.
- At size >= ~98px the suffix-font floor clamp stops binding (ratio math holds on its own), and at size > ~114px `stroke` itself escapes its own 8px floor and starts scaling with size again — so sizes in the 120-140px range the ask names are exactly where the component's own math (not just the notch) stops degrading.
**Recommendations:**
- Drop `notch={CRITICAL_NOTCH}` from the ActiveRiskIndex call at ActiveRiskIndex.tsx:88 (stop passing `notch` at all). The critical-band threshold (74) is already spelled out in text via `ACTIVE_RISK_HELP_TEXT` ('Critical ≥744' ladder, confirmed present in riskCopy.ts and asserted in ActiveRiskIndex.test.tsx:86), so no information is lost — only the RiskGauge component's `notch` prop/geometry (RiskGauge.tsx:20-29, 110-129, 161-173) stays as an opt-in feature other larger call sites (CaseTriageHeader, dashboard widgets) can use later at sizes where it renders cleanly; do not delete the prop, just stop feeding it from this compact instrument.
- Pull ActiveRiskIndex out of PageHeader's `actions` slot (Overview.tsx:832-839) entirely and give it its own dedicated Card, top-right of the page (per MEMORY.md ask #1), using the existing `Card`/`CardContent` primitives (webui/src/ui/card.tsx) the same way KpiTile-style tiles are composed elsewhere — a 3-row stack (caption+HelpTip / gauge / band label) needs its own box, not a single-row header actions strip.
- Size it 120-140px, not 64/78. At >=~98px the suffix-font floor (RiskGauge.tsx:136) stops clamping the `/100` ratio, and above ~114px the stroke/notch-radial-span floor (line 82) stops being a fixed absolute pixel value — both make the instrument's own math behave as designed rather than hitting its degenerate small-size floors. 120 matches the size ActiveRiskIndex.test.tsx's own notch-geometry test already uses (line 32) and 108-160 matches every other existing clean call site (CaseTriageHeader=108, dashboard widget=default 160).
- Keep the rest of RiskGauge.tsx (arc/value-overlay layout, `TEXT_CLASS`/`BAND_LABEL`, animateValue) unchanged — it is not broken at reasonable sizes; only the notch usage + the mount size need to change for this specific instrument.
- If a future call site wants the notch AND a compact footprint, consider either flooring `stroke`/notch-length proportional to `size` (e.g. remove or lower the `Math.max(8, ...)` floor below ~size 100) or gating the notch to only render when the gauge is large enough (`notch` prop ignored below some minimum size) — but for this ask, dropping the notch + growing the card is the direct fix and matches what the user already asked for.

## Reinvestigate 400 \"No events remain … aged out\" — root cause + exact stored-Case fields to reconstruct a minimal offline Cluster

**Findings:**
- ROOT CAUSE CHAIN: POST /cases/{id}/reinvestigate (backend/app/api/routes.py:3445-3497) calls `_cluster_for_case(state, case)` (routes.py:3909-3953). That helper ONLY ever tries to rebuild the Cluster by RE-HITTING the log surface: (1) an exact `ids_query(case.member_event_ids, ...)` re-fetch via `state.es.search_logs`, and if that yields 0 hits, (2) `_entity_events_widening()` (routes.py:3851-3870) which re-queries the entity field over `prefs.investigate_lookback` widened up `_WIDEN_LADDER = ("now-7d","now-30d","now-365d")` (routes.py:3815). If BOTH return zero hits (ILM/retention already purged the docs), `_cluster_for_case` returns `None` and the route raises the 400 'No events remain … aged out' (routes.py:3420-3428 / 3468-3476 / 3528-3536, and the identical helper is also used by /investigate and /run-playbook). There is NO code path today that reconstructs a Cluster purely from the stored Case — the whole function is log-surface-dependent.
- Cluster model required fields (backend/app/models.py:248-293) and constructor (`cluster_from_events`→`_build_cluster`, backend/app/engine/correlation.py:177-227): signature, entity(Entity{type,value}), group_by(EntityType), rule_values(list[str]), member_event_ids(list[str]), member_events(list[RawEvent] — the ONLY field carrying real per-event content: id/source dict/timestamp_millis/ip/user/host/rule/severity/index_role/source_id/feed_id), first_seen_millis/last_seen_millis(int epoch ms, from members_sorted[0]/[-1].timestamp_millis), count(len(members)), risk_score/risk_breakdown, trigger_reason(TriggerReason|None), source_id/source_name, is_alert, auto_investigate_eligible, feed_ids, source_ids.
- Case model (backend/app/models.py:1104-1226) stores enough AGGREGATE data to rebuild every Cluster field EXCEPT member_events' real content: cluster_signature→Cluster.signature; entity→Cluster.entity (and .type is exactly Cluster.group_by, confirmed identical in _build_cluster); rule_ids (union-merged in pipeline._merge_rules, backend/app/agents/pipeline.py:631-638)→Cluster.rule_values; member_event_ids→Cluster.member_event_ids (ids only, re-fetch already proven to fail); trigger_reason (TriggerReason: rule_value, mode, n, window_seconds, group_by, observed_count, window_start, window_end, entity string, rule_values, severity_min/max, sentence, models.py:226-245) — .observed_count (NOT .n, which is just the rule's configured threshold, not the true count) → Cluster.count, and .window_start/.window_end (the exact matched-window epoch-ms bounds set in correlation.py:257-271 from _WindowDetail, correlation.py:142-165) → Cluster.first_seen_millis/last_seen_millis; source_id/source_name→Cluster.source_id/source_name; risk_score/risk_breakdown exist but DON'T need to be carried over — engine/risk.py compute_risk() (called unconditionally at pipeline.py:314-316 on every investigate_cluster run) recomputes risk_breakdown purely from cluster.count, cluster.window_seconds (derived from first_seen/last_seen), cluster.rule_values, cluster.entity.value and reputation — it NEVER reads cluster.member_events (engine/risk.py:53-95), so whatever is pre-seeded there is immediately overwritten and is irrelevant to reconstruction fidelity.
- Case has NO field for cluster.member_events' actual raw content: no stored per-event `source` dict, ip/user/host/rule/severity per event, or first_seen_millis/last_seen_millis outside of TriggerReason. `case.evidence` (list[EvidenceItem]{summary,event_ids,query}, models.py:352-355) is the ONLY surviving human-readable trace of what the original member events looked like, but it is TEXT SUMMARIES written by a prior LLM run, not structured RawEvents, and it gets fully REPLACED (not merged) by `evidence=verdict.evidence` on every re-investigation (pipeline.py:600) — so today, if you rebuild a Cluster with `member_events=[]`, the OLD evidence is discarded before the new (evidence-blind) investigation even starts.
- Because cluster.member_events would be [] in an offline reconstruction, 3 real prompt-building/scoring consumers silently degrade: (1) agents/prompts.py render_cluster() line 166 (`for ev in cluster.member_events[:max_events]`) — used by BOTH Router (agents/router.py:49, via cluster.primary_rule() at line 48) and the Investigator — renders an EMPTY '## Sample events (raw log data — UNTRUSTED)' section, i.e. the LLM sees zero evidence to reason over; (2) Cluster.primary_rule() (models.py:295-308) falls back from trigger_reason.rule_value (which is nulled out by _cluster_for_case._finalize for cases that already have a trigger_reason, routes.py:3923-3930, specifically so the pipeline's `_trigger()` helper at pipeline.py:615-618 preserves the ORIGINAL case.trigger_reason instead of a synthetic 'manual' one) to counting cluster.member_events (empty) to finally rule_values[0] (alphabetically first, not necessarily the true dominant rule) — a minor, pre-existing-style degradation, not a new regression; (3) agents/common.py rag_query() lines 76-84 (`_distinct(ev.host ...)/_distinct(ev.user ...)/_first_message(...)`) just yields a shorter/less-specific RAG retrieval query when member_events is empty — degrades gracefully, no crash. Two OTHER member_events consumers — cost_gate.passes_suppression (engine/cost_gate.py:19-34) and engine/ingest.py's candidate-registration path (handle_clusters) — are NOT on the reinvestigate call path at all (reinvestigate calls pipeline.investigate_cluster() directly, bypassing engine/ingest.py entirely), so they are irrelevant to this fix.
- Pre-existing adjacent risk (not caused by this bug, but touches the same helper): `_entity_field()` (routes.py:3818-3823) only maps EntityType.IP/USER/HOST; if a case's entity.type is RULE/FILE_HASH/DOMAIN, today's log-re-query fallback path in _cluster_for_case would KeyError before ever reaching the 400 — worth a defensive fix alongside, though it's out of scope for the offline-reconstruction fix itself since the new offline path wouldn't call _entity_field at all.
**Recommendations:**
- Add a new offline fallback INSIDE `_cluster_for_case` (backend/app/api/routes.py, after the existing id-requery and entity-widening both fail to find events, i.e. right before the current `return None` at routes.py:3950) that builds a Cluster purely from `case` fields — never touching ES — so `reinvestigate`/`investigate`/`run-playbook` (all three callers, routes.py:3419/3467/3527) stop 400ing whenever ANY aggregate data survives on the case: `Cluster(signature=case.cluster_signature, entity=case.entity, group_by=case.entity.type, rule_values=list(case.rule_ids) or (case.trigger_reason.rule_values if case.trigger_reason else []), member_event_ids=list(case.member_event_ids), member_events=[], first_seen_millis=case.trigger_reason.window_start if case.trigger_reason else _millis_from_iso(case.created_at), last_seen_millis=case.trigger_reason.window_end if case.trigger_reason else _millis_from_iso(case.updated_at), count=(case.trigger_reason.observed_count if case.trigger_reason and case.trigger_reason.observed_count else max(len(case.member_event_ids), 1)), source_id=case.source_id, source_name=case.source_name, source_ids=([case.source_id] if case.source_id else []), trigger_reason=None)` — leave trigger_reason=None exactly like the existing widened-fallback path does (routes.py:3929), so `pipeline._trigger()` (pipeline.py:615-618) preserves the ORIGINAL case.trigger_reason unchanged rather than fabricating a new one; only synthesize `_manual_trigger_reason` when `case.trigger_reason` is already None (mirrors the existing `has_trigger` branch, routes.py:3921-3930).
- Only take this offline path when `case.member_event_ids` or `case.trigger_reason` (i.e. some aggregate signal) actually exists; if a case has NEITHER (e.g. a corrupt/ancient record), keep returning None → the existing 400, but reword the detail to distinguish 'no stored evidence to reconstruct from' vs the current generic message, since with this fix the 400 should become rare (only genuinely empty legacy cases hit it).
- Feed `case.evidence` (the prior investigation's EvidenceItem summaries) into the prompt as a REPLACEMENT for the now-empty '## Sample events' section, since member_events=[] otherwise means the LLM re-investigates with literally zero evidence. Cleanest approach: extend `render_cluster()` (agents/prompts.py:112-115) with an optional `prior_evidence: list[EvidenceItem] | None` param; when `cluster.member_events` is empty AND prior_evidence is given, render a distinct '## Prior evidence (from the stored case — the original raw events aged out of the retained log window)' block, one bullet per EvidenceItem.summary — still passed through `fence()` (consistent with #9: these summaries were authored by a prior LLM run FROM untrusted log data, so treat them as data, not instruction, exactly like the enrichment leaf-fencing pattern already used at prompts.py:155-159). - Do NOT try to fabricate fake per-event RawEvent stand-ins to slot into `cluster.member_events` — it would corrupt `agents/common.py rag_query()`'s host/user distinctness signals and `Cluster.primary_rule()`'s counting fallback with synthetic, non-representative data; leaving `member_events=[]` and instead injecting `case.evidence` as a clearly-labeled DISTINCT block (as above) is more honest and auditable.

## Bonus #5b — identifying LLM-key-blocked cases and a safe one-click/auto reinvestigate mechanism

**Findings:**
- LLM/provider secrets are stored on the runtime `Secrets` object (backend/app/config.py:48-136) and are ALL optional (`anthropic_api_key`/`openai_api_key` etc, lines 79-80). The ONLY writer of global LLM keys at runtime is `POST /api/setup/secrets` (backend/app/api/routes.py:220-227, `SecretsUpdate` model at 166-175) which calls `AppState.apply_secrets()` (backend/app/state.py:1522-1552). `apply_secrets` sets the attrs then unconditionally calls `self.gateway.reset_providers()` (state.py:1537; gateway.py:361-364), which just does `self._providers = {}` — so the VERY NEXT gateway call after a key save re-resolves credentials fresh; there is no stale-failure cache to invalidate. Webui callers: `webui/src/soc/pages/Settings.tsx:280` (`saveSecrets`) and `webui/src/soc/pages/Wizard.tsx`.
- Missing-key detection happens in `LLMGateway._provider_kwargs` (backend/app/llm/gateway.py:116-166), a pre-flight check BEFORE any network call: for `anthropic` it raises `GatewayError("Anthropic API key not configured")` at line 126 if `self._secrets.anthropic_api_key` is falsy; for `openai`/`openai_compatible` it raises `GatewayError("OpenAI API key not configured")` at line 132 if no key AND no base_url. Azure/Bedrock/Vertex do NOT pre-flight-check (empty creds pass through and fail later with a generic HTTP/auth ProviderError, differently worded) — so a clean, string-matchable 'key not configured' signal only exists for the two primary providers today.
- The GatewayError from a missing key is caught INSIDE the investigator's ReAct loop (backend/app/agents/investigator.py:207-214) and turned via `return` (bypassing the outer `except Exception`) into `_fail_to_human(f"investigator model error: {exc}", cluster, prefs)` (investigator.py:327-333): `VerdictResult(verdict=Verdict.NEEDS_HUMAN, confidence=0.0, recommended_action=truncate(reason, 400), reproduce_query=...)`. The Router (agents/router.py:62-64) and Formatter (agents/formatter.py:57-59) both swallow GatewayError into a degraded-but-not-fatal path (UNCERTAIN bucket / preserve draft verdict), so only the Investigator's own call actually fails the case — and it ALWAYS produces a normal VerdictResult, never the pipeline's outer crash path.
- This VerdictResult flows through `Pipeline._assemble_case` (backend/app/agents/pipeline.py:583-612) into `Case.recommended_action` (line 602) and `Case.summary = truncate(verdict.recommended_action, 300)` (line 605); `Case.error` stays None (that field is only set by the pipeline's OUTER exception handler at pipeline.py:473-484 / `_fail_to_human_case` at 641-676, which the investigator's internal catch never reaches). `CaseManager(prefs).apply(case)` then runs the untouched `decide()` (engine/case_manager.py:59-119): verdict=NEEDS_HUMAN/confidence=0 always falls to the generic 'No confident close decision; routing to human (fail-safe)' branch, giving `case.status = CaseStatus.NEEDS_HUMAN`, `decision_by = DecisionBy.SYSTEM` (constants.py:212/229/279-282). These deterministic fields are IDENTICAL for a key-missing case and any other NEEDS_HUMAN case (budget block, timeout cap, model overload, malformed JSON) — the ONLY distinguishing, machine-checkable signal is the free-text `case.recommended_action` (or `case.summary`) containing the literal substring 'API key not configured'. A budget-blocked case says 'budget ceiling exceeded: ...' (engine/budget.py + gateway.py:304) and a timeout-capped case says 'Investigation exceeded the Ns time cap...' (pipeline.py:416-423) — both distinguishable from key-missing by the same substring test.
- No existing query capability filters cases by `recommended_action` text in either backend: `CaseStore.list()` (backend/app/stores/cases.py:66-93, SQL twin at backend/app/stores/sql/repositories.py:103) only supports `status`/`source_surface`/`entity_value` term filters. A 'key-blocked' detector must fetch a bounded page (`state.cases.list(status=CaseStatus.NEEDS_HUMAN.value, limit=<bounded>)`) and do the substring match in Python, mirroring how other aggregate features (engine/shift_report.py, engine/metrics.py) do bounded-fetch-then-python-filter rather than adding new query surface.
- Reinvestigation already exists and is #3-safe/reusable as-is: `POST /api/cases/{case_id}/reinvestigate` (backend/app/api/routes.py:3445-3497) reconstructs the cluster via `_cluster_for_case` (routes.py:3909-3953, prefers exact `member_event_ids` re-query, falls back to a windowed entity re-query) then calls `state.pipeline.investigate_cluster(cluster, case.source_surface, prefs_eff, force=True)` — the SAME shared pipeline, so `decide()` is untouched and original provenance is preserved. It returns a clean 400 (NEUTRAL) when no events remain (partial-failure-tolerant per case). Note: unlike `/run-playbook` (which has `_=Depends(require_permission("playbooks", "run"))` at routes.py:3513), neither `/investigate` nor `/reinvestigate` currently carries an explicit `require_permission` gate even though `reinvestigate` IS a distinct grant in the RBAC catalog (backend/app/rbac/policy.py:52 and 134) — a pre-existing gap worth closing on any new endpoint built on this.
- The codebase's existing precedent for exactly this feature shape (offer, don't silently auto-run something cost-bearing) is `AutomationNudge` (webui/src/soc/pages/AutomationNudge.tsx + webui/src/soc/pages/automation.ts): an RBAC-gated, self-hiding Alert banner with a single 'Turn on ...' button doing a best-effort GET-then-PUT that never throws, plus 'Review'/'Dismiss'. Bulk multi-case ops have a bounded, partial-failure-tolerant precedent in `POST /api/cases/bulk` (routes.py:3135-3187): caps at 500 ids, one action per id via the same single-case function, RBAC-checked once up front, per-id `{id, ok, error?}` results — but it only supports lifecycle `CaseAction`s (routes.py:2851-2867 `_ACTION_STATUS`), not reinvestigate, so a bulk-reinvestigate endpoint is new. `Preferences.caps.max_concurrent` (config.py:535, default 3) is the existing bounded fan-out concurrency knob (used by engine/poller_manager.py:343) a bulk reinvestigate should reuse.
**Recommendations:**
- Define a precise, cheap predicate rather than a fuzzy heuristic: `is_key_blocked(case) -> bool` := `case.verdict == Verdict.NEEDS_HUMAN and case.error is None and any(s in (case.recommended_action or '') for s in ('Anthropic API key not configured', 'OpenAI API key not configured'))`. Keep the two exact gateway.py:126/132 strings as the match set (avoid a loose 'API key' substring — it could misfire on a future differently-worded provider message); add a new provider's exact string to the set only when it gets a pre-flight check like Anthropic/OpenAI's.
- Add a small bounded, read-only endpoint, e.g. `GET /api/cases/key-blocked?limit=200` (gate: `require_permission('cases', 'reinvestigate')`, the grant that already exists in the RBAC catalog but is unused today), implemented as `cases, _ = await state.cases.list(status=CaseStatus.NEEDS_HUMAN.value, limit=<bounded>)` then the Python-side `is_key_blocked` filter — mirroring the bounded-fetch-then-filter pattern used elsewhere — returning `{count, ids}` (ids capped e.g. at 500) so the webui can decide whether to show a nudge without leaking case content there.
- Add `POST /api/cases/reinvestigate-key-blocked` (or a generic `POST /api/cases/bulk-reinvestigate {ids: [...]}` taking explicit ids the frontend already fetched from the endpoint above — prefer explicit ids: strictly safer, matches the `/cases/bulk` idiom of caller-supplied, RBAC-checked, capped ids rather than a server-side 'reinvestigate everything matching X'). Gate with `require_permission('cases', 'reinvestigate')`. Guard at the top: if `state.secrets.configured_status()` shows both anthropic/openai still false, return 400 immediately rather than re-running N cases into the same failure. Bound concurrency with a semaphore sized from `prefs.caps.max_concurrent` (reuse, don't reinvent) and cap total ids per call (e.g. 100 — smaller than the 500 used by `/cases/bulk` since every one of these is a REAL, billable LLM call). For each id: audit BEFORE the run (mirroring the single-case reinvestigate's audit-before-run at routes.py:3482-3491, actor e.g. `'reinvestigate_key_blocked'`), then call the exact same `_cluster_for_case` + `investigate_cluster(..., force=True)` sequence, returning `{results: [{id, ok, error?}]}` per the `/cases/bulk` shape so one bad/aged-out case never breaks the batch.
- Do NOT make this fully automatic-and-silent by default; ship it as a ONE-CLICK OFFER first (satisfies '#5b bonus' literally and matches this codebase's cost-conscious UX convention). Concretely: after `saveSecrets()` succeeds in webui/src/soc/pages/Settings.tsx (and the Wizard's equivalent secrets step), call the new `GET /api/cases/key-blocked` and, if `count > 0`, surface an Alert banner (same visual/interaction pattern as `AutomationNudge.tsx`: RBAC-gated, self-hiding, a primary 'Reinvestigate N blocked case(s)' button + 'Dismiss', no persistence needed since it only shows right after a key save) that calls the new bulk endpoint and reports success/failure via toast, reusing the existing toast/errMsg helpers already in Settings.tsx.
- If a TRUE fire-and-forget auto-mode is still wanted on top of the one-click offer, add it as an explicit, additive, DEFAULT-OFF preference (consistent with every other automation toggle in this codebase, e.g. Round-4/5/6 features): `Preferences.auto_reinvestigate_on_key_restore: bool = False`. Wire it inside `AppState.apply_secrets()` (state.py:1522) right after `self.gateway.reset_providers()`: only when this pref is true AND the update flipped a previously-falsy `anthropic_api_key`/`openai_api_key` to truthy, fire an `asyncio.create_task(...)` (matching the existing notification-dispatch fire-and-forget pattern at routes.py:3117-3121) running the SAME bounded, semaphore-limited reinvestigate loop over a fetched key-blocked page. Keep it capped and audited identically to the one-click path so the only difference is who clicks the trigger.
- While building the new endpoint, also add the missing `require_permission('cases', 'reinvestigate')` (or 'investigate') gate to the pre-existing `POST /api/cases/{case_id}/investigate` and `POST /api/cases/{case_id}/reinvestigate` routes (routes.py:3404-3497) — they currently have no explicit RBAC dependency despite `reinvestigate` being a defined grant in rbac/policy.py:52/134. Land this as a separate, clearly-labeled fix so it isn't conflated with the new bulk endpoint's own gate.

## SOC-UX research: attack-path / node-graph visual language (IBM QRadar + modern peers) applied to a left-to-right, thinning-strand "Noise Reduction" alerts-to-cases pipeline for our agentic SOC console (React/Tailwind/SVG)

**Findings:**
- IBM QRadar's own docs (qsip/7.5, qsip/7.4, SS42VS_7.4 'Visualize attack paths of an offense in QRadar Risk Manager') are PROCEDURAL, not a style guide - they describe Risk Manager's attack-path view as a physical-network TOPOLOGY graph built from firewall/router/switch/IPS configs, filterable by protocol/port/vulnerability, correlating asset vulnerabilities + traffic to trace 'the path the offense took through your network' between source, destination, and associated devices. Several QRadar doc pages returned HTTP 403 on direct fetch and gave no pixel-level detail even via a proxy re-fetch (just 'click Offenses -> View Attack Path'). IBM publishes no public node-shape/color/line-weight legend, so the specific visual language has to be triangulated from QRadar's better-documented modern peers.
- Microsoft Defender / Security Exposure Management publishes the most complete, current, citable 'attack-path visual language' spec (learn.microsoft.com/defender-xdr/understand-graph-icons, updated 2025-09): circular node icons keyed by entity category (compute/network/data/identity/keys/IoT/API/etc.); directional edge arrows carrying relationship-verb icons (routes-traffic-to, can-authenticate-as, has-permission-to, moves-data-to, exposed-to-internet...); a gold crown + gold HALO ring around 'critical asset' nodes; a red bug badge for a detected vulnerability; a blue '+' affordance for progressive on-demand graph expansion (the graph is never rendered in full at once); grouped nodes collapse into one numeric-badge node. A separate dashboard surfaces 'top choke points / top entry points / top targets' and a 'blast-radius' sub-view showing cascading downstream nodes from a compromised choke point.
- XM Cyber's attack graph literalizes 'reserve color for what matters': the bulk of exposures render as small NEUTRAL GRAY squares (each square = 10 exposures, most are dead-ends), and only the junction nodes where multiple paths converge on a critical asset ('choke points') are colored yellow/red. Fixing a handful of red choke points collapses ~99% of remaining paths (Cyentia Institute's analysis cites a 99.6% remediation-scope reduction from fixing ~2% of exposures). This 'mostly gray, color only at the pinch point' convention is directly portable to Tailwind (muted/border-border by default, high/critical token only at the decisive node).
- Elastic Security's 'visual event analyzer' (process tree) and CrowdStrike Falcon Threat Graph / Predictive Path Analysis both reuse the same node-link idiom: cube/circle nodes = one entity/process each, edges = parent-child or traversal relationships, click-to-expand children (never auto-expand the whole tree), and a graph+table dual view (graph for quick scan, table for exact detail) - the same progressive-disclosure pattern as Defender's blue-plus.
- The closest real-world precedent for our exact ask - 'multiple lines entering from the left, thinning as phases pass' - is Microsoft's own published description of its internal detection funnel (microsoft.com/insidetrack, 'How Microsoft narrows the threat funnel on over 600 billion monthly security events'): a literal set of four consecutively smaller concentric funnel rings with real counts at each stage - 600 billion monthly raw events -> ~10,000 alerts (ML/threat-intel/behavioral filtering) -> ~3,500 cases (correlation/automation) -> ~500 items needing human remediation. This funnel-of-rings is effectively a coarse Sankey and is the best-documented industry analog to our own Noise Reduction value story.
- Sankey-diagram best practice (Splunk Dashboard Studio docs, Astrato 'Sankey Use Cases', detect.fyi 'Boost your Security Monitoring reports with Sankey Diagrams'): nodes are ordered strictly left-to-right; the data contract is minimal (source, target, value); LINK WIDTH (not color) should carry the volume signal; node coloring is either 'categorical' (one hue per source-node lineage, so a strand keeps its identity moving rightward) or 'dynamic' (driven by a secondary field, e.g. severity) - the latter is exactly what our 5 severity bands need. Sankeys degrade below ~8-10 nodes (a stacked bar says the same thing faster) and above ~30-40 nodes (unreadable) - our 5-band x 6-stage funnel sits safely inside that legible range.
- Nir Smilga's 'Funnel Chart - Suggested Alternatives' (Medium) argues classic wedge/diagonal funnels are HARD to compare because brains struggle judging diagonal-area sizes, and recommends bars anchored to a shared baseline (aligned-left or centered) instead - which is exactly what our existing NoiseFunnel component already does (centered, non-diagonal bars). This validates keeping the current bar funnel as the compact/legible default and treating any 'thinning strands' visual as an ADDITIVE overlay, not a replacement.
- Technical/build finding: `d3-sankey`'s horizontal link curve (also exposed by recharts' bundled `Sankey` component, and taught identically by react-graph-gallery and d3-graph-gallery) is a symmetric cubic Bezier between two fixed-height endpoints using the horizontal midpoint as the control x: `M x0,y0 C xMid,y0 xMid,y1 x1,y1` where `xMid=(x0+x1)/2`. That is precisely the 'smooth tapering strand' geometry needed and it is cheap to hand-roll as a raw SVG `<path>` with no library.

However recharts' Sankey renders nodes as fixed rectangles and needs custom `link`/`node` render props to inject our `token()` HSL-var fills; our existing hand-rolled pattern (webui/src/soc/components/NoiseFunnel.tsx's `FunnelBar`: raw `<svg>`/`<rect>`, `preserveAspectRatio="none"`, `aria-hidden`, all meaning carried in adjacent text) already satisfies the design-gate's 'no raw hex' rule and the #9 untrusted-data contract more cleanly than recharts' opinionated Sankey would.

## Sankey/alluvial 'thinning pipeline' visualization for the Noise-Reduction flow, plus supporting SOC dashboard / cases-queue / case-detail / chat UX research (Round-8, ask #8 + general context)

**Findings:**
- Sankey vs. funnel vs. alluvial vs. parallel-sets are distinct tools: a plain funnel/bar chart shows magnitude at each stage but not which inputs produced which outputs; a Sankey shows both volume AND provenance of flow, and — unlike a funnel — natively supports a stage SPLITTING into multiple outputs (source: datavizcatalogue.com). Parallel-sets force every node column to sum to a constant 100% (uniform length); alluvial diagrams allow variable node length and 'wavy/overlapping' paths. Our stage counts genuinely shrink (not a part-of-whole redistribution) and our final stage genuinely branches into 4 MECE outcomes (auto_cleared/escalated/needs_human/true_positive) — that branching is the concrete reason a Sankey communicates something a stacked bar-funnel (our current NoiseFunnel.tsx) cannot: it shows the SPLIT, not just four separate totals.
- The core Sankey/alluvial rule for honest 'gets fewer and fewer' encoding is a single invariant: link/ribbon width must be strictly proportional to the quantity it carries, computed from a brush PERPENDICULAR to the flow direction so width stays constant along a ribbon's length even when it changes vertical position between stages (source: ggsankeyfier docs via pepijn-devries.github.io). Never let a curved bezier link appear to visually widen or narrow due to slope alone — only true value should change width. Best practice caps a funnel/Sankey at ~4-6 stages for legibility (source: growth-onomics.com, tomtunguz.com) — our pipeline (ingested→clustered→cases→4 outcomes) is right at that ceiling and should not grow further without collapsing something.
- D3's canonical horizontal-Sankey link path is a simple, well-documented cubic Bezier: 'M x0,y0 C xm,y0 xm,y1 x1,y1' where x0/y0 = [source.x1, linkY0], x1/y1 = [target.x0, linkY1], and xm = the horizontal midpoint (x0+x1)/2 (this is exactly what d3.sankeyLinkHorizontal() generates internally, confirmed via github.com/d3/d3-sankey and observablehq.com/@d3/sankey). Node rects are simple x0,y0,x1-x0,y1-y0 rectangles whose height (for a vertical-node horizontal-flow layout) is proportional to value. This is ~10 lines of hand-rollable path math — no need to pull in the d3-sankey package to get the same visual.
- IMPORTANT for this codebase specifically: recharts (already a runtime dependency, v2.15.4, confirmed present in webui/node_modules and imported elsewhere in soc/components/charts.tsx) ships a NATIVE <Sankey> chart component (recharts/types/chart/Sankey.d.ts) taking data:{nodes,links}, nodeWidth, nodePadding, linkCurvature, and fully custom node/link render props (function or element) for per-node/per-link theming. This means a themed Sankey is achievable with ZERO new npm dependencies either way (hand-rolled SVG, or recharts' built-in component) — directly satisfying this project's standing 'ZERO new deps' rule that has held every round.
- Accessibility consensus for flow/Sankey charts (Smashing Magazine 2024, W3C WCAG G111, Telerik/amCharts a11y docs, MDN ARIA): (1) never encode meaning by color alone — pair every colored strand with a directly-adjacent text label, not just a legend (WCAG 1.4.1/G111); (2) wrap the diagram in a container with role="img"/aria-label (or better, keep decorative SVG aria-hidden and let real text/DOM elements carry the meaning — the same 'text carries meaning, SVG is decorative' pattern this codebase ALREADY uses in NoiseFunnel.tsx's FunnelBar); (3) provide an equivalent data-table/text summary as the authoritative accessible version rather than trying to make dozens of individual bezier paths independently screen-reader-navigable; (4) all interactions available to mouse must have a keyboard-focusable equivalent, but that equivalent should live at the node/stage level (not per-ribbon-segment) to avoid a wall of redundant stops; (5) don't rely on hover-only tooltips for the only textual explanation of a flow.
- SOC-specific precedent: Elastic's own agentic-SOC triage pipeline (elastic.co/security-labs, 2025-2026) describes almost the exact same shape of reduction cascade we have — raw alerts → deterministic ES|QL triage closes obvious FPs at zero cost → a cheap LLM triage agent closes more → survivors become a shared 'case' workspace investigated by specialist agents → a Final-Review synthesis with a structured Verdict/Assessment/Confidence header. They explicitly recommend a funnel/flow visualization of exactly this cascade (raw → closed-by-cheap-tier → closed-by-triage-agent → opened-as-case → analyst action) plus surfacing per-stage cost, which validates that our NoiseReduction contract shape (stages + by_severity + MECE outcomes) is the right generalization of this idea.
- General SOC-dashboard UX consensus for 2025-2026 (aufaitux.com, activu.com, networkershome.com, strangebee.com): apply the 'three-foot vs ten-foot' rule — an analyst's console needs granular drill-down detail, a wall/overview needs bold at-a-glance status; alert triage UIs should use 'reason-code surfacing' (show the matched fields/trigger reason/confidence in the SAME view as the alert, not behind a click) plus progressive disclosure (decision-critical context first, raw/deep detail one interaction away); centralized case management with visible disposition reasoning improves team-lead auditability of analyst decisions — this maps directly onto our existing CaseDetail 'Why' tab (WhyPanel.tsx) and DecisionCard.tsx, which already follow this pattern and should be the template for any redesign, not replaced by it.
- Collaborative/chat UX precedent (product-alpaca Medium article, agentic-design.ai chat-interface-patterns): embedded chat should blend conversational text with structured UI (buttons/cards), support threading for multi-topic case discussions, and act as a first-class collaborative surface (not a bolted-on widget) — consistent with this repo's existing CaseChatPanel.tsx + CollaborationPanel.tsx separation (chat vs. structured collab/tasks), which is already the recommended pattern; the main risk called out across sources is fragmenting attention across tabs/windows rather than keeping investigation and discussion in one shared pane.

Only ADD (optional, additive) a per-outcome by_severity breakdown on the 4 outcome stages server-side if you want severity coloring to survive all the way to the final branch; otherwise switch the color axis at the last hop from severity → verdict/status token (auto_cleared→success/low token, escalated→warning/high, needs_human→info, true_positive→critical, reusing the existing verdict semantic axis in webui/src/soc/components/palette.ts) — this is a defensible, even desirable, design choice: severity describes the input, verdict describes the output.

## Round-8 SOC-UX research: Security Command Center / Cases queue / case-detail tabs / embedded chat+collaboration best practice, plus concrete zero-dependency inline-SVG Sankey/flow-ribbon math for a "Noise Reduction" alerts→cases visualization

**Findings:**
- Alert volume is the dominant SOC pain point right now: Microsoft/Omdia's State of the SOC 2026 reports ~2,992 alerts/day per org, 46% false positives, 63% go unaddressed, per-analyst load peaks ~174 alerts/day with only ~22% needing genuine investigation, and 76% of orgs cite alert fatigue as a top concern (cited via Vectra, Torq, CyberDefenders roundups). This validates giving a 'signal vs noise' visualization real prominence rather than a small side widget.
- Agentic triage workflows (enrich→correlate→assess→escalate-or-suppress) are reported to cut noise ~60% and shrink mean-time-to-triage from hours to minutes/seconds (CompuQuip, Corelight, Exaforce). The stage ordering our backend already emits — ingested→clustered→cases→{auto_cleared,escalated,needs_human,true_positive} in `engine/metrics.py`'s noise-reduction contract, consumed by `webui/src/soc/components/NoiseFunnel.tsx`'s `deriveFunnel()` — matches this industry-validated shape, so a ribbon upgrade should reuse it verbatim rather than inventing new stages.
- Microsoft Sentinel's incident-detail page (the most mature 'case detail with tabs' reference) converges on ~5 tabs: Overview (triage/timeline/entities preview), Entities, Activity Log (automations + analyst comments), Logs (ad-hoc query inline), Similar Incidents (algorithmic similarity ranking). Our `CaseDetail.tsx` already has 5 tabs (overview/investigation/threat/collab/chat) — same tab count and same 'never leave the page to query or comment' philosophy. The one Sentinel pattern we lack as a first-class surface is 'Similar/Related Incidents' — we have the underlying data (Round-4 campaign correlation, Round-3 threat_context related-cases) but it isn't a dedicated tab.
- Google SecOps (Chronicle) SOAR case management is built around grouping related alerts into ONE case by shared entity (IP/host/user/domain) plus a case queue that supports sort/filter/assign/collaborate — the same shared-entity clustering model our `engine/correlation.py`/`engine/campaigns.py` already implement.
- Explainable-AI-for-SOC research (arXiv 2601.22653, 'Human-Centered Explainability in AI-Enhanced UI Security Interfaces') and Microsoft's own Security Copilot / Defender Phishing Triage Agent docs converge on: the goal is 'appropriate trust,' not maximized trust — the UI should surface counter-evidence, model blind spots, and confidence caveats, and gently invite skepticism/hesitation rather than only projecting confidence, to guard against automation bias. Defender's triage agent renders its decision path as an explicit graphical decision tree alongside a plain-text rationale.
- Case queue / detail SaaS UX patterns (SaaSUI, Outsystems case-management pattern write-ups) name this exact shape 'Details View + Inbox View' or 'Split Pane' (master list + focused detail), with tabs for progressive disclosure of dense sections — validates the Cases-list + CaseDetail-tabs architecture already in `webui/src/soc/pages/Cases.tsx` / `CaseDetail.tsx`.
- For flow-ribbon/Sankey geometry: d3-shape's `linkHorizontal()` (the primitive underlying d3-sankey's default link path, confirmed by reading the actual d3-shape/d3-sankey source) draws each link as a single cubic Bézier: `M x0,y0 C xm,y0 xm,y1 x1,y1` where `xm = (x0+x1)/2` (the horizontal midpoint) — this 'symmetric S-curve, control points at the midpoint, each retaining its own anchor's y' is THE standard sankey/flow curve shape and the exact math needed to hand-roll it without d3.
- A closed, variable-width ribbon (not just a thick stroked line) is built by applying that same bumpX cubic twice — once along the top edge (source-top → target-top) and once along the bottom edge in reverse (target-bottom → source-bottom) — and stitching them with two vertical/near-vertical edges at the source and target columns; this is the standard technique behind no-d3 Sankey/alluvial implementations referenced in Observable notebooks (Ian Johnson 'Weird Sankey Links', Fil 'Sankey link paths #91') and matches how RAWGraphs/amCharts render alluvial ribbons.
- CSS transforms (`scaleX`) on SVG geometry elements are supported in all evergreen browsers; combined with `transform-box: fill-box` + `transform-origin: 0% 50%`, a path scales from its own left edge (its bounding-box min-x) outward — this gives a literal left-to-right 'flow draw-in' with zero coordinate-space math and zero new dependencies, and composes with a plain CSS `@keyframes` + per-element `animationDelay` stagger, which is exactly the pattern this codebase already uses for `Stagger.tsx`/`rise-in` (defined in `webui/tailwind.config.js`) and is automatically neutralized by the existing global `prefers-reduced-motion: reduce` reset in `webui/src/styles/theme.css`.
**Recommendations:**
- SVG RIBBON PATH FORMULA (the core ask) — for a ribbon flowing from a source column at x0 (band spanning y sy0..sy1) to a target column at x1 (band spanning ty0..ty1), use two mirrored cubic Béziers sharing one midpoint control-x, closed into a fillable shape:
```ts
function ribbonPath(x0: number, sy0: number, sy1: number, x1: number, ty0: number, ty1: number, curvature = 0.5): string {
  const xm = x0 + (x1 - x0) * curvature; // 0.5 = symmetric S-curve (d3-sankey's default 'bumpX' shape)
  return `M${x0},${sy0} C${xm},${sy0} ${xm},${ty0} ${x1},${ty0} L${x1},${ty1} C${xm},${ty1} ${xm},${sy1} ${x0},${sy1} Z`;
}
```
This is literally d3-shape's `bumpX` curve (`M x0,y0 C xm,y0 xm,y1 x1,y1`, xm=(x0+x1)/2 — verified from the actual d3-shape source) applied once to the top pair of points and once (reversed) to the bottom pair, closed with two straight verticals — the standard way every no-d3 Sankey/alluvial renderer builds a variable-width ribbon. Because sy0/sy1 and ty0/ty1 are independent, the band tapers correctly when a stage's volume shrinks (the literal 'noise reduction' visual). Export this as a pure, unit-testable function (mirrors the existing `deriveFunnel()` export-for-tests convention in `webui/src/soc/components/NoiseFunnel.tsx`).
- COLUMN / BAND STACKING (proportional widths) — pick ONE global scale `k` across the whole diagram (not renormalized per column) so band height literally shrinks stage-to-stage, which IS the funnel story:
```ts
const k = plotHeight / topTotal; // topTotal = row[0].total (the 'ingested' stage)
function stackBands(values: number[], gap = 3) {
  let y = 0;
  return values.map(v => {
    const h = v > 0 ? Math.max(1, v * k) : 0; // 1px min sliver keeps a nonzero band visible/clickable
    const band = { y0: y, y1: y + h };
    y += h + gap;
    return band;
  });
}
// then center the stack in the column: yOffset = (plotHeight - finalY) / 2, add to every band.y0/y1
```
Feed it `SEV_ORDER`-ordered `by_severity` values already present on each `FunnelRow` in `NoiseFunnel.tsx` — zero new backend/data work, this is a pure rendering upgrade of data you already compute in `deriveFunnel()`.
- COLOR AXIS SWITCH mid-diagram — for the ingested→clustered→cases columns, color each ribbon strand by SEVERITY (`SEVERITY_COLOR` in `webui/src/soc/components/palette.ts`: critical/high/medium/low/info), matching the existing `FunnelBar` segments. For the cases→{auto_cleared,escalated,needs_human,true_positive} fan-out, switch the ribbon's color to VERDICT (`VERDICT_COLOR` in the same file: true_positive→critical, escalated→high, needs_human→warning, auto_cleared/false_positive→info) since verdict, not original severity, is what's semantically meaningful post-triage. Both maps already exist — this is a zero-new-token, reuse-only recommendation, and keeps the design-gate's 'no raw hex' rule intact.
- GRADIENT STRANDS — give every ribbon its own `<linearGradient gradientUnits="userSpaceOnUse" x1={x0} x2={x1}>` (NOT the default objectBoundingBox, which would misalign against the curve's actual bounding box) with two `<stop>`s using `token(name, alpha)` from `palette.ts`, e.g. `token('critical', 0.85)` fading to `token('critical', 0.35)` for a ribbon that's mostly being dropped, or staying near-full-opacity into `token('high', 0.85)` for one that survives to 'escalated'. Encoding survival-vs-drop as BOTH hue (severity→verdict token) AND opacity reinforces the noise-reduction narrative and gives a second (non-color) cue, which helps toward the codebase's existing WCAG 1.4.1 non-color-redundancy rule (pair with the existing `SEMANTIC_ICON` glyph in a small legend beside the diagram, not on the ribbons themselves).
- STAGGERED DRAW-IN — recommended zero-new-dependency technique: give each `<path>` `style={{ transformBox: 'fill-box', transformOrigin: '0% 50%', animation: 'ribbon-grow 600ms cubic-bezier(0.16,1,0.3,1) both', animationDelay: `${i * 70}ms` }}` and add ONE keyframe alongside the existing ones in `webui/tailwind.config.js` (next to `'rise-in'`):
```js
'ribbon-grow': { from: { opacity: '0', transform: 'scaleX(0.04)' }, to: { opacity: '1', transform: 'scaleX(1)' } }
```
`transform-box: fill-box` + `transform-origin: 0% 50%` pins the scale origin to the path's own left edge (its bbox min-x, i.e. the source column) so it visibly grows rightward toward the target column — no per-ribbon coordinate math needed for the animation itself. This mirrors the exact idiom `Stagger.tsx` already uses (per-item `animationDelay` + a named `animate-*` keyframe) and is automatically neutralized by the existing global `prefers-reduced-motion: reduce` block in `webui/src/styles/theme.css` (animation-duration collapses to ~0), so no extra reduced-motion branch is needed. If a more literal 'ink flowing along the curve' look is wanted later, a `<clipPath clipPathUnits="userSpaceOnUse">` containing a `<rect>` animated via `scaleX` (same transform-box trick) gives a masked reveal instead of a squash — more code, marginal visual gain, treat as a stretch goal only.
- AVOID DISTORTING THE CURVES ON RESIZE — the existing `FunnelBar` in `NoiseFunnel.tsx` uses `preserveAspectRatio="none"` on a 1000×24 viewBox, which is safe for flat rects but will visibly warp bezier curvature if reused for ribbons. For the ribbon variant, pick a fixed design-time viewBox (e.g. `0 0 640 220`) and render with `width="100%" height="auto"` and the DEFAULT `preserveAspectRatio` (`xMidYMid meet` — uniform scale), so curvature never distorts. Keep all analyst-facing text as HTML overlaid outside the `<svg>` (the existing pattern: `FunnelBar` is `aria-hidden` and decorative, with the real label/count/percent as sibling HTML) so text doesn't get stretched by the SVG's own scaling.
- SHIP IT AS A NEW VARIANT, NOT A REWRITE — add a `variant="ribbon"` (wide, full-bleed) rendering path to `NoiseFunnel.tsx` (or a sibling `NoiseRibbon.tsx` that imports and reuses the already-exported `deriveFunnel()`/`FunnelRow`), used on `Overview.tsx` (the Security Command Center home) where there's more horizontal real estate via `PageContainer`'s wide variant, while keeping the current compact stacked-bar `NoiseFunnel` for tighter contexts (sidebars, smaller cards). This is additive, changes no API contract, and needs no backend change since `GET /api/metrics/noise-reduction` already supplies everything the ribbon needs.
- COMMAND CENTER LAYOUT — given Omdia 2026's 46%-false-positive / 174-alerts-per-analyst-per-day reality, keep the single 'noise reduced by X%' headline number (already in `NoiseFunnel`'s `Header`) as the FIRST thing above the fold on Overview, and consider a role-scoped default: a 'manager rollup' custom dashboard preset (already supported via Round-5/6's per-role default `Dashboards.tsx` layouts) that leads with the ribbon + MTTA/MTTR/dwell posture tiles, versus an 'analyst working queue' preset that leads with the Cases table and skips the ribbon — role-based dashboarding (CISO-level risk vs analyst-level detail) is a named best practice across every SOC-dashboard write-up surveyed.
- CASE-DETAIL TABS — `CaseDetail.tsx`'s existing 5 tabs (overview/investigation/threat/collab/chat) already match Sentinel's ~5-tab convergence; the one gap versus Sentinel's 'Similar Incidents' tab is that our campaign/related-case data (Round-4 `engine/campaigns.py`, Round-3 `engine/threat_context.py` related_cases) is currently surfaced as chips, not a dedicated ranked tab. If case volume grows, promote it to a first-class 'Related' tab (sortable by shared-entity overlap) rather than adding a 6th top-level tab for something else — keep tab count at 5.
- EXPLAINABILITY / TRUST — the 'appropriate trust, not maximized trust' principle (arXiv 2601.22653; Microsoft Defender Phishing Triage Agent's decision-tree + plain-text rationale) argues for extending the existing case 'Why' tab / `GET /api/cases/{id}/rationale` payload with an explicit counter-evidence or 'what would change this verdict' field alongside the reasoning excerpt, and for surfacing a collapsible 'show reasoning' affordance INLINE in the embedded chat (reusing the existing `TraceTimeline` component) rather than only in the separate Why tab — this reduces automation bias by making the agent's uncertainty visible at the point of decision, not just on a secondary page.

## Round-8 SOC-UX research: SOC Command Center dashboard, Cases queue, case-detail tabs, embedded chat/collaboration, and Noise Reduction flow — best-practice synthesis with file-specific recommendations for the TLSOC webui (webui/src/soc/*)

**Findings:**
- SOC dashboard consensus (aufaitux, activu, ArmorPoint, abnormal.ai): 'show the right thing first, everything else one click away' — prioritize by weighted risk score, cap ~7-8 concrete KPIs per view, role-based density (analyst=granular, manager=operational, exec=trend), dark-mode-first for 24/7 SOC eye strain. Our Overview.tsx KPI strip (~5 tiles) plus severity drill-through is already within this range.
- Alert-fatigue research (D3 Security, RedLegg, Graylog) is unanimous that the trusted fix is enrichment + an honest, evidenced reduction — never silent suppression. D3 frames the math gap as ~100k alerts/day vs 5-10 analysts (~320 alerts/analyst/shift) and frames AI value as 'confirmed verdict + evidence.' Our NoiseFunnel.tsx's MECE stage design (ingested→clustered→cases→{auto_cleared, escalated, needs_human, true_positive}) already matches this 'evidenced funnel' pattern closely.
- Nielsen Norman Group's 10 AI-chatbot guidelines (nngroup.com/articles/ai-chatbots-design-guidelines): one consolidated chat entry point everywhere; state capabilities plainly; keep suggested-question chips clickable THROUGHOUT the conversation, not just the first turn; prefer progressive disclosure over dumping detail inline; AVOID AUTOSCROLLING that fights where the analyst is reading; support content export/preservation; allow window resize; show visual content alongside text.
- NN/G's Explainable-AI article and thefrontkit's production-chat-UI piece agree: citations must be visible and prominent, styled distinctly from body text, never buried only inside a collapsed 'how did we get this' disclosure — they should sit as their own labeled block.
- The 'production vs. demo' gap (thefrontkit, Vercel AI Elements taxonomy) names the pieces that separate a professional chat surface from a prototype: buffered/non-thrashing streaming render, a prominent Stop control (not hidden in a menu), Regenerate, tiered feedback (thumbs → category → free text), context-window transparency ('using the last N messages'), and enterprise accessibility (aria-live=polite with aria-atomic=false, debounced announcements during streaming, Escape/Arrow key nav, focus returns to composer after a response).
- Vercel's AI Elements / shadcn AI component taxonomy (elements.ai-sdk.dev) is becoming the industry-standard vocabulary for chat sub-components: Conversation, Message, Reasoning/Chain-of-Thought, Sources/Inline-Citation, Suggestion, Shimmer, Tool, Task, Queue, Confirmation, Model Selector. Our existing ChatPanel.tsx already half-implements this set (Provenance ≈ Reasoning+Tool+Knowledge combined; starters ≈ Suggestion; TypingIndicator ≈ a generic, non-informative Shimmer) — the gaps are a distinct always-visible Sources block and a real Shimmer status line.
- The well-documented ChatGPT/Claude scroll pattern (multiple engineering write-ups, an open GitHub issue on this exact complaint in anthropics/claude-code #35261) is: pin the user's new message near the top of the viewport and let the answer grow below it via bottom padding computed ONCE at send time and held static during streaming; distinguish user-initiated wheel scroll from programmatic scroll; show a floating 'scroll to latest' control when the user has scrolled away from the bottom. Blindly forcing scrollTo(bottom) on every update (our current ChatPanel.tsx behavior) is the exact anti-pattern flagged as jarring/'chasing' the reader.
- Empty-state research (Mobbin, Eleken, multiple 2026 chat-UI guides) converges on 3-5 specific, realistic starter prompts (never a generic 'Ask anything'), shown only before the first message. ChatPanel.tsx's EmptyState + starterIcon heuristic already matches this closely and needs no structural change.
- Tabs research (Setproduct, Eleken): 2-6 peer tabs per row, ≤2 nesting levels, tertiary content belongs in a sidebar/accordion rather than a new tab layer, actions inside one tab must never leak into another. CaseDetail.tsx's 5 tabs (Overview/Investigation/Threat/Collab/Chat) sit at the healthy end of that range — a 6th top-level tab should be avoided in favor of folding new content into an existing tab.
- Sidebar research (UX Planet, Mobbin): 240-300px expanded / 48-64px collapsed with hover tooltips on collapsed icons, and users scan the left 80% of the time — worth a quick width audit against NavSidebar.tsx (not independently re-verified in this pass).
- Typography/spacing consensus for 'tidy vs busy' professional chat UI: 14-16px body text, 1.4-1.6 line-height, restrained palette, role differentiated by alignment/label (not color alone), avatars used sparingly, secondary actions revealed on hover/focus rather than always visible. The project's custom Tailwind type scale (fontSize.base = 14/20 for primary UI, fontSize.md = 15/22 explicitly labeled 'comfortable reading panels' and used for chat bubble text) and the ChatPanel .socMsgActions hover-reveal pattern already match this — validated as correct, no change needed.
**Recommendations:**
- ChatPanel.tsx scroll behavior (highest priority, cheap fix): replace the unconditional `el.scrollTo({top: el.scrollHeight...})` effect (fires on every `transcript`/`loading` change) with a 'stick-to-bottom' guard — before appending a new turn, check whether the user was already within ~80-120px of the bottom of the transcript lane; only auto-scroll if so. When they were scrolled up reading history, leave the scroll position alone and show a small floating 'New reply ↓' button pinned to the bottom-right of the scroll lane that jumps down on click. This directly fixes NNG guideline #7 ('avoid autoscrolling') and the widely-reported 'scroll chases the user' complaint.
- Split the Provenance accordion's `citations` block out of the collapsed 'How the agent got this' disclosure into its own small always-visible 'Sources' strip (numbered chips, e.g. '[1] source-label') rendered directly under the answer, before the collapsed Reasoning/Tools/Knowledge accordion. Keep Reasoning/Tools/Knowledge collapsed as-is — that part is already correct progressive disclosure. This matches NN/G's explicit 'don't bury citations, make them visible and prominent' guidance and mirrors the industry-standard Sources/Inline-Citation split in Vercel's AI Elements taxonomy.
- Upgrade `TypingIndicator` in ChatPanel.tsx from 3 generic pulsing dots to a short shimmer-text status line reflecting the actual pipeline phase when cheaply knowable (e.g. 'Querying logs…', 'Checking knowledge base…', 'Composing answer…'), rather than one static string — even a coarse 2-3 phase signal is enough. This answers the 'silence reads as broken' / 'show the work' finding without requiring true token-level LLM streaming, so it stays compatible with CLAUDE.md non-negotiable #7 (aggregate-then-summarize, never raw logs to a model) and doesn't require wiring the existing realtime.py EventBus into chat.
- Add a visible Stop/Cancel control next to Send while `loading` is true (currently the composer is only disabled with no way to abort an in-flight `api.chat` call). Wire an AbortController into the fetch so a stuck or slow answer can be cancelled — thefrontkit and general production-chat-UI guidance both call out a prominent stop control (not hidden in a menu) as an enterprise-blocking gap when absent.
- Add 2-3 short, contextual follow-up suggestion chips under `MessageActions` after an assistant answer (e.g. 'Show related cases', 'Explain the verdict', 'Escalate this'), not only in the empty state. NNG guideline #4 explicitly calls for clickable suggested questions throughout the conversation, and this reuses the existing starter-chip visual language (`Button variant="outline" size="sm"`) already built for the empty state.
- Hold CaseDetail.tsx at 5 top-level tabs; if a new surface (e.g. a dedicated Timeline) is requested, fold it into an existing tab (Overview or Investigation) via progressive disclosure/accordion rather than adding a 6th top-level TabsTrigger, per the 2-6-peer-tabs / ≤2-nesting-levels tabs research.
- NoiseFunnel.tsx: consider adding one HelpTip/footnote anchor comparing the funnel's `cases.total` against a rough 'alerts an unaided analyst could triage in a shift' baseline (the ~320/analyst/shift figure SOC research repeatedly cites) so the headline reduction % has a concrete human-workload anchor, not just an abstract percentage. Purely presentational/optional — no data-model change required since the funnel already carries the raw counts.
- Cases.tsx queue: current severity-first sort/filter (via `severityBand`/`risk_score` fallback) already matches 'weighted risk analysis ranks the queue' best practice — no change needed there. Consider surfacing a one-line workload/SLA chip in the queue header (e.g. 'X open · Y aging past SLA') since `engine/shift_report.py` / `engine/metrics.py` already compute this aggregate data server-side; this would just be a new small chip consuming an existing endpoint, not a new backend surface.
- No typography/spacing change is needed in ChatPanel — the custom Tailwind scale (`base` 14/20 default UI, `md` 15/22 'comfortable reading panels' used for bubble text) and the hover-revealed `.socMsgActions` pattern already land exactly on the 14-16px / generous-line-height / declutter-until-needed consensus from chat-UI research; treat this as validated, not a to-do.
- If/when token-level streaming is added to chat (via the existing realtime.py SSE EventBus or otherwise), plan the accessibility contract now: `aria-live="polite"` with `aria-atomic="false"` on the transcript region (already set on the scroll container), and debounce screen-reader announcements to every ~1-2s rather than per-token, per thefrontkit's enterprise-accessibility guidance — this is cheap to bake into the design up front and expensive to retrofit.

## SOC case-collaboration UI research (Round-8): discussion thread + task checklist + activity feed + ownership layout for a calm, scannable "war-room" case-detail page

**Findings:**
- Industry case tools converge on our 3-part shape but split the seams differently. Microsoft Sentinel's incident page keeps 'Tasks' as its own panel but MERGES comments and system actions into one 'Activity log' (a single rich-text comment box sits at the bottom of that same panel, not a separate tab) -- https://learn.microsoft.com/en-us/azure/sentinel/incident-navigate-triage , https://learn.microsoft.com/en-us/azure/sentinel/audit-track-tasks. TheHive keeps Details/Tasks/Observables as tabs plus one persistent live-stream aside visible from every tab -- https://strangebee.com/thehive-case-management-platform/ , https://docs.strangebee.com/thehive/overview/.
- The wider industry (GitHub Issues timeline, Salesforce Activity Timeline, Dynamics 365 Timeline) has moved from 'separate comments tab' toward ONE reverse-chronological stream mixing comments + lifecycle events, with type filters layered on for scanning, because two divergent surfaces for 'what happened' and 'what did we say about it' forces the reader to reconcile two timelines by hand -- https://github.com/features/issues , https://www.getweflow.com/blog/salesforce-activity-timeline , https://crmmatthew.wordpress.com/2017/06/27/activity-timelines-in-dynamics-365/. Our own CaseThread already partially does this ('persisted in-case AI chat turns surface in the SAME thread') but task/assignment/status changes still only land in the separate CaseActivityFeed, never the thread -- an inconsistent application of the same idea.
- Codebase-specific gap #1 (chat duplication): webui/src/soc/pages/casedetail/CaseChatPanel.tsx's ChatTab keeps its own component-local `useState` transcript (never reads/writes CaseThread), while the sibling Collaboration tab's CaseThread separately renders AI turns as first-class thread messages. An analyst can hold two divergent 'AI conversations about this case' (the Chat tab transcript vs the Discussion thread) with no visual link between them -- directly against the general 'consolidate everything into one interface, zero tab-switching' incident-response philosophy incident.io describes as their calm-interface principle: https://incident.io/blog/implementation-guide-slack-native-incident-management-platform-2026
- Codebase-specific gap #2 (ownership isn't pinned): webui/src/soc/pages/casedetail/CollaborationPanel.tsx's aside (`grid lg:grid-cols-[1fr_20rem]`) stacks Ownership + Tasks + Activity in a plain (non-sticky) column inside a SINGLE shared scroll container (`min-h-0 flex-1 overflow-y-auto` wraps the whole Tabs body in CaseDetail.tsx). A long Discussion thread scrolls the Ownership/assignee picker out of view along with it. Competing products keep this exact metadata rail pinned while only the narrative column scrolls -- Linear: 'the sidebar stays fixed... your brain maintains spatial context because the frame never breaks' (https://www.925studios.co/blog/linear-design-breakdown-saas-ui-2026); GitHub's issue sidebar is the same fixed-metadata pattern (https://github.blog/changelog/2026-04-09-release-info-in-issue-sidebar-and-project-defaults/).
- Codebase-specific gap #3 (assignee has no at-a-glance surface): grep confirms CaseTriageHeader.tsx and OverviewPanel.tsx never render `assignee` -- the only place to see or change who owns a case is 4 tabs deep inside Collaboration's narrow aside (assignee IS visible/filterable in the Cases queue list, so it's not fully hidden, just missing from the detail header). SOC dashboard research is explicit that role/ownership clarity belongs at a glance, not behind navigation: 'reducing the number of dashboards or windows analysts must switch between... reduces alert fatigue' -- https://www.activu.com/security-operations-center-dashboard-best-practices-a-checklist-for-critical-situational-awareness/ , https://uxreactor.com/5-user-experience-design-must-haves-for-cybersecurity-products/
- Activity-feed scannability research (GetStream's activity-feed design guide) gives concrete, checkable rules our CaseActivityFeed.tsx mostly follows already (relative timestamps via humanizeAge, one icon+tone per kind, plain-text summaries) but violates one: it does NOT aggregate repeated same-actor/same-kind events ('72 people congratulated Josh' vs 72 separate rows) -- a burst of task-status edits or reactions in a short window will currently render as N separate timeline rows. https://getstream.io/blog/activity-feed-design/ : 'Feeds should be simple. Always look to remove redundancies... Combine similar activities to reduce clutter.'
- Real-time/SSE update ergonomics: our `onLiveActivity`/`onLiveThread` callbacks (useEventStream) just trigger a raw refetch-and-replace; Smashing Magazine's 2025 real-time-dashboard research recommends short (200-400ms) fade/slide transitions on newly arrived items plus 'snapshot/pause' affordances so live updates don't yank the reader's scroll position or attention mid-read, and to prefer a subtle 'new activity' affordance over silent content replacement -- https://www.smashingmagazine.com/2025/09/ux-strategies-real-time-dashboards/
- General SOC-dashboard cognitive-load research (applies to Security Command Center + Noise Reduction, which the task also named): reduce widget/tile count, cluster related signal, prioritize by risk/confidence, and keep list->detail->timeline navigation consistent across modules so analysts don't relearn layout per screen -- https://www.aufaitux.com/blog/cybersecurity-dashboard-ui-ux-design/ , https://medium.com/design-bootcamp/alert-fatigue-and-dashboard-overload-why-cybersecurity-needs-better-ux-1f3bd32ad81c , https://dl.acm.org/doi/10.1145/3723158 (ACM survey on SOC alert fatigue). Our Overview.tsx already follows the 'flat KPI grid + zoned sections' shape these sources recommend, so no structural change is needed there -- it's a good baseline to preserve, not a gap.
- 'War-room / evidence-board' as a literal design reference (corkboard, red string, pins) is a movie/detective trope aimed at consumer templates (Creately, Canva, Pinterest boards), not a real security-product pattern -- none of the actual SOC/case tools researched (Sentinel, TheHive, GitHub, Linear) use that skeuomorphism. The useful reading of 'war-room tidy' for a real console is Linear's principle instead: a muted, low-saturation base palette with color reserved ONLY for state/priority/severity, everything aligned to a strict spacing grid, and clearly bounded zones -- which is also exactly the direction our own Round-5/6 semantic-token system (severity/status/verdict axes, WCAG-AA both themes) already took. https://www.925studios.co/blog/linear-design-breakdown-saas-ui-2026
**Recommendations:**
- Pin the Ownership/Tasks rail: in webui/src/soc/pages/casedetail/CollaborationPanel.tsx, change the `<aside className="space-y-6">` to `<aside className="space-y-6 lg:sticky lg:top-4 lg:self-start lg:max-h-[calc(100vh-8rem)] lg:overflow-y-auto">` so the assignee picker and task checklist stay visible while a long Discussion thread scrolls beneath them -- matches Linear's 'sidebar stays fixed' and GitHub's issue-sidebar pattern. Widen the fixed column from `20rem` to something like `minmax(0,1fr)_22rem` so the assignee Select and task titles don't truncate.
- Surface the assignee (and an open-task count) at the top of the case, not 4 tabs deep: add a small 'Assigned to <name>' + '<n>/<m> tasks' chip to CaseTriageHeader.tsx (or as a compact strip above the Tabs in CaseDetail.tsx), reusing the existing assigneeSelectValue/AssigneePicker logic so it's still one source of truth -- do NOT duplicate the edit control, just the at-a-glance read plus a click-through to the Collaboration tab.
- Fold task/assignment/escalation events INTO the Discussion thread as compact system-authored messages (reusing the existing `author_type: 'system'` styling CaseThread already renders), the same way AI chat turns already surface there, and keep CaseActivityFeed as the terse audit-grade record. This turns Discussion into the single readable narrative ('what happened + what did we say about it') while Activity stays the compliance-grade trail -- mirrors Sentinel's merged Activity-log-with-comments and the GitHub/Salesforce/Dynamics unified-timeline convergence. Concretely: when postTaskStatus/assign succeed, also append a lightweight system CaseMessage client-side (or have the backend do it) instead of only writing to the activity store.
- Resolve the Chat-tab vs Discussion-tab duplication: either (a) remove CaseChatPanel's private transcript state entirely and have its composer post into the SAME CaseThread (so 'Chat' becomes just a focused compose-only view onto the one thread, consistent with CLAUDE.md's non-negotiable #5 'ONE chat engine, two entry points'), or (b) if the ephemeral scratch-chat is intentionally kept separate for quick Q&A, relabel the tab 'Ask AI' and visually route any answer the analyst wants kept into the thread via a one-click 'Post to case' button on each assistant reply, so there is never an orphaned second conversation about the same case.
- Aggregate bursty activity in CaseActivityFeed.tsx: before rendering, collapse consecutive items with the same `actor` + `kind` within a short window (e.g. 2 minutes) into one row ('Alice updated 3 tasks -- 2m ago', expandable on click) instead of one row per event -- directly implements GetStream's 'combine similar activities to reduce clutter' rule and keeps the feed scannable as a case's audit trail grows.
- Animate live-arriving items instead of a hard refetch-replace: when `onLiveThread`/`onLiveActivity` fire, fade/slide-in only the new rows (reuse the existing `animate-fade-in` utility already used for tab transitions) over ~250ms, and if the reader has scrolled away from the top, show a small non-intrusive 'N new' pill/button to jump up rather than silently reflowing content under their cursor -- per Smashing Magazine's real-time-dashboard guidance on avoiding jarring live updates.
- Add an open-tasks safety check to the existing close-with-disposition dialog (Round-4's unified close flow): if `tasks` has any non-done items, show a small inline warning ('3 open tasks -- close anyway?') in the dialog. This is purely a client-side UX nudge reading the same task list the Collaboration tab already fetches -- it must NOT gate or alter `decide()` (#3), only inform the human before they confirm.
- Resist literal 'evidence board' skeuomorphism (corkboard/pins/red string) -- it doesn't appear in any real competitor tool researched and would clash with the existing muted, WCAG-AA severity/status/verdict token system. Treat 'war-room tidy' instead as: one narrative focal column (Discussion), a pinned metadata rail (Ownership+Tasks), and a quiet audit spine (Activity) -- three clearly bounded, low-saturation zones with color reserved for state, which is the direction already established and should just be extended (via the sticky-rail and merged-events changes above), not re-skinned.
- Leave Overview.tsx's KPI-strip + zoned-grid structure and the existing empty-state handling (CaseThread/CaseTasks/CaseActivityFeed all already have friendly EmptyState copy) alone -- both already match the SOC-dashboard cognitive-load literature (flat KPI grid, list->detail->timeline consistency, no blank-feed anti-pattern) and are worth protecting from regression in this pass rather than rewriting.

## Modern dashboard/console page-header pattern — plain big title (no card/hero wash) + inline controls + one distinct "instrument" card to the right — researched for the TLSOC webui's Security Command Center / Cases / CaseDetail headers

**Findings:**
- Industry has converged on REMOVING card/hero chrome from page headers. Stripe's dashboard team redesigned from a card-based dashboard to a 'no-card' one: heavy shadows and rounded card edges were identified as the actual problem (consumed space, blocked side-by-side layout, buried important info); the replacement is 'clean, bold section titles' sitting flat on the page background, with typography/spacing/color — not a card wash — doing the hierarchy work.
- Vercel's Geist design system states its whole dashboard aesthetic is 'pure blacks and pure whites, with no accent colors or decoration — just typography, spacing, and the occasional gradient.' Its type scale literally names a token for this exact use case: `text-heading-32` ('Subtle') is documented as the recommended size for 'dashboard headings' — distinct from `text-heading-48/72` which are reserved for marketing heroes. That is materially bigger than a typical UI section heading.
- Linear's redesign write-up describes deliberately 'limiting how much chrome was used' and simplifying headers to cut visual noise. Its type system uses Inter Display specifically for headings (plain Inter elsewhere) at weights in a low 400–510 band (never bold), tight negative letter-spacing (roughly -0.011 to -0.022em), and hairline 0.5px borders / 6–12px radii — a 'precision-machined,' restrained look rather than heavy card framing.
- Every mainstream design-system page-header spec (Atlassian, GitHub Primer, Carbon, USWDS, SAP Fiori) converges on the SAME anatomy: title (+ optional breadcrumb above it) on the left, actions/controls right-aligned on the same row, no second control band, and the header sits on the plain page background — a card/border is optional chrome applied only when there's a reason (e.g., a nav bar underneath needs a separator), never a default 'wash'.
- SAP Fiori's Object Page header pattern is the closest documented precedent for 'plain title + one distinct instrument to the right': the title/breadcrumb block is a plain, unadorned band, while a separate 'key facts / KPI' area on the right IS deliberately given its own distinct facet/tile treatment (border, background, distinct number typography) — i.e., the contrast between plain-title and distinct-instrument is the actual design mechanism used to draw the eye to the one number that matters.
- Numeral micro-typography for any prominent instrument/KPI number: use `font-variant-numeric: tabular-nums` (Tailwind `tabular-nums`) so digits occupy equal width and don't jitter or misalign on live updates — near-universal best practice for dashboards, timers, and any auto-refreshing metric.
- In THIS codebase, `webui/src/soc/components/PageHeader.tsx`'s `variant='hero'` currently wraps the ENTIRE header band in `rounded-lg border border-border bg-card` plus a decorative `bg-hero-glow` wash, and the title itself is only `text-xl` (20px) even in the hero variant — smaller than the `text-heading-32`/`text-2xl`-`text-3xl` (24–30px) that the research above recommends for a primary dashboard title, and the card/wash is applied to the whole band rather than reserved for a single instrument.
- `webui/src/soc/pages/Overview.tsx` already puts a single 'ONE risk instrument' — `ActiveRiskIndex` (a `RiskGauge`, default size 78px) — into the hero header's `actions` slot next to the `TimeRangePicker`, but today it renders bare (no card/border of its own) inside the already-carded hero band, which is the inverse of the Fiori pattern (there the title is plain and the KPI/instrument is what gets the distinct card).
- `webui/src/soc/components/KpiTile.tsx` already demonstrates the exact 'distinct instrument card' proportions this research recommends elsewhere in the app: `rounded-lg border border-border bg-card p-4`, with its number at `text-3xl font-semibold tracking-tight tabular-nums` — i.e., the desired treatment already exists as a pattern in the design system, just not yet applied to the header's risk instrument.
**Recommendations:**
- Add (or repurpose) a PageHeader treatment that renders NO wrapper chrome at all on the header band itself: drop `rounded-lg border border-border bg-card` and the `bg-hero-glow` decorative wash from the title/controls row — let it sit flush on the page background like the existing `dense` variant's row structure, just bigger. Concretely: change the hero title class from `text-xl` to `text-2xl sm:text-3xl font-semibold tracking-tight` (24–30px, matching Vercel Geist's named 'dashboard heading' token and Linear's restrained-weight philosophy) and keep `text-muted-foreground` description small underneath, unchanged.
- Move the card/border treatment OFF the header band and ONTO the single instrument that deserves emphasis: wrap `ActiveRiskIndex` (in `Overview.tsx`'s header `actions` slot) in a small `rounded-lg border border-border bg-card` (or the existing `Card`/`CardContent` primitives) with `p-3`/`p-4` padding and a subtle `shadow-sm`, so it visually reads as ONE deliberate instrument set apart from the now-plain title — this is literally the Fiori Object-Page-header mechanism (plain title left, one distinct KPI facet right) and mirrors the card treatment your own `KpiTile.tsx` already uses elsewhere, so no new visual language is introduced.
- Keep the existing anatomy (breadcrumb/eyebrow above the title, controls/actions right-aligned on the same row, tabs on the bottom edge, no second control band) — this already matches Atlassian/Primer/Carbon/USWDS/Fiori convention; the fix needed is title scale + removing the card wash from the row, not restructuring the layout.
- Preserve `tabular-nums` on every number in the new instrument card (already used in `RiskGauge.tsx` and `KpiTile.tsx` — confirm `ActiveRiskIndex`'s gauge value keeps it once boxed in a card) so the number doesn't jitter on auto-refresh.
- Use restraint on weight: prefer `font-semibold` (600) over `font-bold` (700) for the plain big title, matching Linear's low-400s-to-510 weight band and Stripe/Vercel's typography-led (not boldness-led) hierarchy — bold reads as 'shouting,' semibold + size reads as authoritative.
- Apply the same plain-title-plus-boxed-instrument pattern consistently to Cases-queue and CaseDetail headers wherever a single high-value number/gauge (e.g., case risk score) currently sits inside a hero card — for visual consistency across the console, not just Overview.
- Do not increase overall header BAND height to achieve the bigger-title look — industry examples (Carbon's 48px UI shell header, GitHub Primer's compact title bars) keep the row compact (~52–68px, matching this codebase's current dense/hero rhythm); get 'authoritative' from type size/weight and the removed card noise, not from a taller header.
- Since the codebase's non-negotiable #9 requires all header text to stay plain text (never markup) — this recommendation only changes Tailwind classes/wrapper divs in `PageHeader.tsx` and `Overview.tsx`, not the plain-text rendering discipline already in place; no security-relevant change is implied.

## SOC-console UX research: what makes a data-dense triage UI (Security Command Center dashboard, Cases queue, case-detail tabs, embedded chat/collaboration, Noise-Reduction alerts-to-cases flow) FEEL clean/overhauled rather than cluttered — with a checklist mapped onto the current webui codebase (which already has a mature Round 5-7 token system in webui/src/styles/theme.css and webui/src/soc/components/palette.ts).

**Findings:**
- Whitespace is a functional element, not empty space: research converges on roughly 30-40% whitespace for data-dense screens, with well-placed whitespace measurably improving comprehension (one estimate: ~20%); executive/overview screens can afford MORE whitespace than operational tables (UXPin, 'Dashboard Design Principles').
- Visual hierarchy is created with only three levers — size, weight, color — applied as an 'inverted pyramid': the single most important number/insight at the top (largest/boldest), supporting trends in the middle, raw detail at the bottom or behind a click (UXPin; Refactoring UI).
- Refactoring UI's core discipline for looking 'designed' without formal training: design in grayscale first and add color last, so hierarchy comes from spacing/contrast/type before color is used as a crutch; use a constrained spacing scale (4/8/16/24/32/48/64px) and a modular type scale; when unsure, add MORE whitespace than feels natural, then remove until 'just enough.'
- Linear's public redesign write-up is the clearest real-world precedent for 'dense but calm': not every element carries equal visual weight — central task content stays in focus while orientation/nav chrome recedes; most text/icons sit at 40-60% opacity ('muted' tier) and ONLY status/priority/interactive elements get full-saturation color. Borders were deliberately softened because they had 'quietly proliferated... without clear reason'; Linear now uses a 3-tier hairline system (hairline / hairline-strong / hairline-tertiary) instead of one heavy border everywhere.
- Badge/status-color best practice: backgrounds should be a desaturated, low-opacity tint of the intent color (never full saturation) with an AA-contrast-tuned foreground text color — full-saturation red/green badges read as 'visually loud and unprofessional' on dense pages. Our own webui/src/ui/badge.tsx ALREADY implements this correctly (wash-style `border-x/20 bg-x/10 text-x-text` variants) — this is a strength to preserve, not a gap.
- Data tables: prefer horizontal-only hairline dividers over a full grid or zebra striping; correct spacing/typography separates rows better than alternating background colors; letting users choose row density (comfortable/compact) is a common, well-liked enterprise-table affordance (Pencil & Paper 'Enterprise Data Tables'; UX Movement).
- Progressive disclosure (collapsible sections, summary-first/detail-on-demand) is the standard technique for keeping a data-heavy dashboard from overwhelming users — it reduces cognitive load by revealing only what's needed, when needed, without removing power-user access to detail (IxDF; UXPin 'Progressive Disclosure').
- SOC/cybersecurity-dashboard-specific guidance converges on: a 3-tier alert structure (critical bold at top, moderate collapsible mid, informational greyed-out/low-emphasis at bottom); grouping/clustering related events into ONE higher-level alert instead of showing every raw event; and attaching one-click response actions (e.g. 'Investigate' / 'Mark false positive') directly to each alert/case row rather than requiring a drill-in (aufaitux 'Cybersecurity Dashboard UI/UX Design').
- Real production evidence that alert-clustering/noise-reduction is the highest-leverage SOC UX move: Elastic reports customers going from 1,000+ raw daily alerts to ~8 actionable 'discoveries' (attack chains) with false positives cut ~75% by correlating alerts into chains rather than listing them individually; industry baseline stats show SOCs get 10k-15k alerts/day, 60-83% are noise, and agentic triage has cut mean-time-to-triage from hours to seconds in production deployments (Elastic Security blog; Vectra/Swimlane alert-fatigue writeups).
- Microsoft Sentinel's incident page is the closest real precedent to our case-detail: it consolidates overview + timeline (all alerts/bookmarks in time order) + entities (IP/host/user/file, each opening a mini Info/Timeline/Insights side panel) + MITRE tactics into ONE investigation surface specifically to minimize tab-switching and context loss (Microsoft Learn, 'Investigate incidents in the Azure portal').
- Enterprise chat/collaboration UX pattern: keep a 'persistent context panel' visible alongside the conversation (Slack's pinned-info panel, Teams' meeting context bar, Intercom's customer-context sidebar) rather than making the case context and the chat mutually exclusive tabs — this is the standard way products avoid analysts losing case context while chatting (UXPin 'Chat UI Design'; Setproduct 'Designing AI chat interfaces').
- Codebase-specific findings from reading the current webui (not just external research): (1) webui/src/soc/pages/Overview.tsx renders 9 `<DashboardGroup>` widget bands and NONE of the 9 call sites pass `defaultOpen`, so — despite the component explicitly supporting collapse-by-default for progressive disclosure (webui/src/soc/components/DashboardGroup.tsx, `defaultOpen = true`) — every group ships fully expanded, meaning the dashboard shows all ~9 sections at once with equal visual weight. (2) webui/src/soc/components/DataTable.tsx already has a `density?: 'normal' | 'compact'` prop (cellPad px-4/py-2 vs py-3), but webui/src/soc/pages/Cases.tsx hardcodes `density="compact"` (line ~1343) with no user-facing toggle, so the density best-practice is half-built but not exposed to operators. (3) CaseDetail.tsx (webui/src/soc/pages/CaseDetail.tsx) already puts overview/investigation/threat/collab/chat behind 5 tabs (line ~1378-1400) rather than a persistent-context + activity-pane split, so switching to the Chat tab currently hides the case's severity/status/entities exactly the situation the Sentinel/Intercom pattern warns against. (4) A quick grep found ~90 files across soc/ + ui/ using off-4pt-grid Tailwind spacing utilities (gap-1.5/px-2.5/py-2.5 = 6px/10px/14px) alongside the project's own documented 4/8px density scale (`--density-unit: 0.25rem` in theme.css) — legitimate for icon-to-label micro-gaps per the 8pt-grid literature, but worth auditing where it's used as outer card/container padding instead, since mixed off-grid paddings are a common, hard-to-name reason dense UIs read as 'slightly off.'
**Recommendations:**
- Overview.tsx (Security Command Center): pass explicit `defaultOpen` on the 9 `<DashboardGroup>` calls — keep only the 2-3 highest-priority bands open by default (Noise-Reduction funnel / attention queue / severity mix) and set `defaultOpen={false}` on the rest (case-volume trend, connector health, workload, top signatures/entities). This actually realizes the progressive-disclosure the component already supports, turning '9 equally-loud sections' into a real inverted-pyramid landing view. If DashboardGroup doesn't yet persist collapse state per user, wire it through the existing per-user UserPrefsStore (stores/user_prefs.py + GET/PUT /api/prefs/user) the same way table column state is already persisted, so an analyst's chosen layout sticks.
- Cases.tsx: expose the `density` prop that DataTable.tsx already supports as a user-facing 'Comfortable / Compact' toggle (small segmented control near the existing filter bar) instead of the hardcoded `density="compact"`, and persist the choice via the existing per-user prefs table-state mechanism (GET/PUT /api/prefs/user/tables/{table_id}) — this is a documented enterprise-table best practice (Pencil & Paper) and the plumbing already exists.
- Cases.tsx row design: audit how many semantic badges render per row (severity + verdict + status + risk are common today). Where more than 2 semantic chips would appear in one row, demote the lower-priority ones to the existing `SEMANTIC_ICON` glyph-only form (palette.ts already exports `semanticIcon()`/`SEMANTIC_ICON` for exactly this) instead of a full colored Badge, so a row reads as one dominant color signal plus small monochrome glyphs rather than a 'row of confetti chips.' This follows both the SOC-dashboard guidance ('bold top-priority, greyed-out informational') and Linear's '40-60% opacity for everything but the one actionable signal' rule — and keeps using tokens you already have.
- CaseDetail.tsx: convert the current 5-tab layout (overview/investigation/threat/collab/chat) toward a two-pane pattern for at least the Chat tab — keep a slim, always-visible case-identity strip (case id, severity/status/verdict badges, top entities) pinned above or beside the chat/collab pane rather than making chat a fully separate tab that hides that context. This mirrors the Slack pinned-panel / Teams context-bar / Intercom customer-panel pattern and Microsoft Sentinel's decision to keep entities+timeline visible during investigation rather than tab-switching away from them. Minimal-diff version: add a compact sticky header (reusing the existing OverviewPanel chip row) at the top of the `TabsContent value="chat"` and `value="collab"` panels.
- Noise Reduction funnel (Overview.tsx / NoiseFunnel component): make the 'before → after' reduction the single boldest number on the page (e.g. '1,247 alerts → 6 cases' as a large stat, matching Elastic's '1,000+ → 8' messaging), sized/weighted above the surrounding KPI tiles rather than equal to them — since research and production data agree this ratio is the single most persuasive proof-of-value number a triage console can show, it should dominate the inverted-pyramid, not compete with 8-9 other tiles of equal visual weight.
- Border audit: following Linear's 'borders quietly proliferate' finding, do a pass over nested Card-in-Card / Card-in-Tab-in-Group compositions in CaseDetail.tsx and Overview.tsx and remove the inner border wherever a `bg-surface-sunken`/`bg-accent/30` tint (tokens already defined in theme.css) can separate the region instead — reserve `border-border` for the outermost card only. This is exactly the DESIGN_STANDARD 'ONE card grammar' rule already documented; the ask here is enforcement, not a new rule.
- Spacing audit (low priority, systemic polish): grep for `px-2.5`/`py-2.5`/`p-2.5` used as CONTAINER/card padding (not icon-label gaps, where 6px half-steps are legitimate per the 8pt-grid literature) across the ~90 flagged files, and normalize those specific cases to the nearest 4/8/12/16 value already in `--density-unit`'s scale. Small, but consistent spacing math is one of the most common reasons a dense screen reads as 'not quite clean' even when no single element is individually wrong.
- Cases.tsx / row actions: add the one-click 'Investigate' / 'Mark false positive' affordance directly on the case row (hover-revealed action icons) rather than requiring a full CaseDetail navigation for the common triage actions, per the aufaitux SOC-dashboard checklist ('actionable elements on each alert') — check whether this already exists as a bulk-action bar (Round-2 W7c shipped bulk actions) and, if so, surface a single-row quick-action affordance too, not just multi-select.
- Keep (do not change) what's already best-practice-aligned so effort isn't wasted re-solving solved problems: the wash-style badge tokens in ui/badge.tsx (`border-x/20 bg-x/10 text-x-text`) already match the 'desaturated tint + AA text' research finding; the 3 orthogonal severity/status/verdict axes with non-color SEMANTIC_ICON redundancy in palette.ts already satisfy WCAG 1.4.1 and the 'restraint in color' literature; the hairline `--border` at ~1.45:1 plus `--border-strong` at >=3:1 in theme.css already implements Linear's 2-tier hairline system. Round 8 effort should go to LAYOUT/DENSITY DISCIPLINE (collapse defaults, tab-vs-context-panel, per-row badge count, density toggle) rather than re-touching the color-token layer, which is already research-aligned.

## Cohesive card grammar for the TLSOC SOC console (Security Command Center dashboard, Cases queue, Case Detail tabs, embedded chat/collaboration, Noise-Reduction alerts-to-cases flow) — border vs shadow, elevation levels, header/padding rhythm, avoiding nested-card noise

**Findings:**
- Every design system researched converges on the same core rule: define ONE resting-card look (border + a faint shadow, or a light fill) and reserve a visually heavier second level ('raised'/'overlay') exclusively for things that move or float ABOVE the page — dropdowns, popovers, dialogs, drag ghosts. Atlassian's Elevation model (sunken/default/raised/overlay) is explicit: raised is 'reserved for cards that can be moved, such as Jira and Trello cards... avoid using [raised] to group content when a border or white space would suffice.' Material Design 3's elevated/filled/outlined card variants exist purely as an emphasis choice — 'each provides the same legibility and functionality... the variant depends on style alone,' never on nesting depth.
- Border-first, shadow-as-accent (not shadow-as-primary-depth-cue) is the clear 2026 direction. Dashboard-design guidance for 2026 states plainly that 'perspective and shadows distort perception; keep charts clean and flat' — the shift is toward flat/bordered surfaces with shadow reserved for genuine overlays, which lines up with Atlassian's rule and with GitHub Primer's Card (border + a light box-shadow + border-radius, normal/condensed/none padding) and Shopify Polaris (16px/space-400 default card padding, space-200/300 — tighter than the outer card gap — used INSIDE a section so related content doesn't visually detach).
- Nested cards ('cards inside cards inside cards, three levels of visual containers because the design doesn't understand hierarchy') is a widely-named anti-pattern. The fix documented across sources is never a new visual style, it's a rule: at most ONE bordered/shadowed container between the page background and leaf content. Deeper grouping inside that one card should use a heading + a hairline divider, extra whitespace, or a chrome-less ('flat'/frameless) variant of the SAME card component — never a second border+shadow pair.
- Codebase check confirms the primitive is already right, only the rule/discipline is missing: webui/src/ui/card.tsx already exposes `padding` (sm=16px/md=24px/lg=32px), `elevation` ('none'|'sm'), and `variant` ('default'|'flat'), and webui/src/styles/theme.css already defines exactly two shadow tokens — `--elev-1` (resting, Tailwind `shadow-elev1`) and `--elev-2` (raised, `shadow-elev2`). MfaSetupCard.tsx already independently invented a `frameless` boolean escape hatch ('render WITHOUT the outer Card frame... login MFA-enroll step wraps this in its own titled Card') proving the team has already hit the nested-card problem once and solved it ad hoc rather than as a system rule.
- There are already 217 raw `<Card` usages across webui/src/soc; none of the existing design-gate tests (webui/src/soc/__tests__/design-gates.test.ts — token existence, WCAG contrast, CVD safety, arbitrary-text-size ratchet) check for a Card nested inside another Card's CardContent, so any accidental double-chrome introduced since Round 5/6 would currently go undetected.
- NN/g's card-vs-list distinction is directly applicable to our three surfaces: cards win when the user is BROWSING (our Command Center KPI/chart tiles — right as-is); lists/tables win when the user is SEARCHING, sorting, or scanning under time pressure ('cards are less effective for data-heavy or highly structured information... if quick scanning is essential, lists or tables are a better fit'). This matters directly for SOC alert fatigue: the 2025 SANS survey figure that 73% of teams cite false positives as their top challenge, plus the standard SOC-dashboard 'three-foot vs ten-foot' hierarchy principle (glanceable KPI row vs. deep desktop-console detail), argue AGAINST ever 'cardifying' the Cases queue or the Noise-Reduction alert list per-row — extra card chrome per row directly adds scan-time and reinforces alert fatigue rather than reducing it.
- Elastic Security's Cases feature and Microsoft Sentinel's incident investigation panel are the two most directly comparable real SOC products. Elastic Cases uses a tab bar (Alerts / Attachments-Events / Investigation-guide) per case rather than one long scrolling page of cards. Sentinel's revamped entity side-panel shows exactly THREE fixed cards per entity (Info / Timeline / Insights) rather than an open-ended card list — both examples support a case-detail pattern of 'one card-boundary per tab, a small fixed set of named cards, never an unbounded stack.'
- For embedded chat/collaboration, the 'threaded UI' pattern (as used in Notion/Linear-style tools) is documented as the right fit for asynchronous, longer SOC-analyst conversations: anchored to ONE side of the screen (a right-hand panel/sheet), not inline mid-page, with the ability to pin key artifacts (decisions/diagrams) so they don't scroll out of view — directly analogous to how Sentinel pins an 'Insights' card and how our own DecisionCard.tsx is already documented as 'the SINGLE, most-prominent, pinned deterministic-decision card' for a case.
**Recommendations:**
- Codify (don't just use) a 2-level elevation ladder mapped onto the tokens that already exist: Level 0 'flat' = `variant="flat" elevation="none"` for anything sitting inside an already-bordered container (toolbars/filter bars, a sub-section inside a Card, tab-panel bodies) — never stack a second border here. Level 1 'resting card' (the current default: border + `shadow-elev1`) = the ONLY look for top-level content: KPI tiles, ChartCard sections, case-detail panels, table/list containers. Level 2 'raised' (`shadow-elev2`) = reserved EXCLUSIVELY for things that visually float above the page: Radix Popover/DropdownMenu/Dialog/HoverCard/Sheet content and the react-grid-layout drag-ghost in dashboard edit mode. Add a one-line comment in card.tsx codifying this so future contributors don't reach for elev2 to make a static card 'pop.'
- Add a design-gate test (extend webui/src/soc/__tests__/design-gates.test.ts, following the same grep/AST-scan pattern already used for arbitrary text sizes) that fails when a component's JSX return contains a literal `<Card` nested inside another `<Card>`'s subtree (i.e., inside its own or an ancestor's `<CardContent>`/`<CardHeader>`/`<CardFooter>`). This turns the nested-card anti-pattern from a code-review judgment call into an automated, ratcheting gate like the existing ones.
- Promote MfaSetupCard's ad hoc `frameless` boolean into the shared primitive: audit DecisionCard.tsx, BudgetCard.tsx, and any dashboard WidgetShell/CaseThread composite for the same problem (a component that sometimes needs to BE a Card and sometimes needs to sit INSIDE one), and have them accept `variant="flat"` from `ui/card.tsx` directly instead of re-inventing a local frameless flag per component. One flag, one place, reused everywhere.
- Never give a static content card `shadow-elev2` or a heavier drop-shadow to signal 'this one matters more' (e.g. DecisionCard). Use the semantic-token system that already exists in palette.ts instead: a colored left-accent stripe or a slightly heavier border-color drawn from SEVERITY_COLOR/STATUS_COLOR/VERDICT_COLOR. This is cheaper, holds up under prefers-reduced-motion/high-contrast, and matches the 2026 flat-dashboard direction of using color/typography for hierarchy rather than decorative depth.
- Lock the padding scale to a decision table instead of leaving it to author preference: `sm` (16px) for dense/nested/list-row cards and narrow dashboard-grid cells; `md` (24px, the current unset default) for ALL top-level page cards — KPI tiles, ChartCard, case-detail panels; `lg` (32px) reserved for single-focus hero/empty-state cards only. Document this table directly above the `PADDING_X` map in card.tsx so it stops being tribal knowledge.
- Keep Command Center as cards/tiles (KpiTile/ChartCard grid) — that's correct per NN/g's browsing-context guidance — but explicitly do NOT let the Cases queue or the Noise-Reduction alert list drift toward a card-per-row layout. Keep them as the existing dense DataTable/list pattern; if a 'richer' case row is requested, add it as an expandable row or a hover-card preview (CaseHoverCard already exists) rather than converting rows into cards, since per-row chrome measurably increases scan time and directly fights the alert-fatigue problem this product is designed to reduce.
- For Case Detail tabs, follow the Elastic Cases / Sentinel model: one Card-boundary per tab body maximum (a TabsContent panel does not need its own redundant bordered wrapper — the Tabs strip already provides the visual boundary), and keep DecisionCard as the ONE pinned/most-prominent card per case, with all sibling cards (Timeline, Threat-context, Enrichment) staying uniform Level-1 so DecisionCard wins visually through position/accent-color, not extra shadow weight.
- For the embedded chat/collaboration panel (CaseThread), apply the threaded-UI pattern directly: anchor it to a single right-hand rail/Sheet (not inline mid-page), give the PANEL itself exactly one Level-1 Card boundary, and render individual messages as a flat list (avatar + timestamp + text + hairline `border-t` dividers, subtle `bg-muted` tint to distinguish AI-authored per the #9 untrusted-fencing convention) rather than one bordered/shadowed Card per message bubble — a 50-message thread rendered as 50 stacked cards is the textbook nested-card-noise failure mode this research warns against.
- When a Card body needs to signal 'more content below' (long table, MITRE heatmap, chat scrollback), use the existing `scrollBody` pattern in ChartCard.tsx (internal `overflow-auto` + `min-h-0`) plus a plain top/bottom hairline border or a CSS mask-image fade — do NOT add a drop-shadow for this; per Atlassian's elevation guidance, overflow shadows are reserved for very small UI or borderless table contexts, and a border is the correct default cue everywhere else in this product.

## SOC-UX spacing/rhythm/type-scale best practice + concrete application to the TLSOC console (Security Command Center, Cases queue, case-detail tabs, embedded chat/collaboration, Noise Reduction alerts->cases flow)

**Findings:**
- Density is not the enemy — disorder is. NN/G and Smashing Magazine both frame the goal as maximizing CLARITY, not minimizing content: a dense interface that surfaces more context/controls at once is efficient for power users (analysts) as long as it has a clear grid, consistent grouping, and whitespace used as a STRUCTURAL signal (separating groups) rather than decoration. This directly supports keeping our SOC console dense (compact tables, KPI-tile dashboards) while fixing 'clutter' via consistent rhythm, not by removing data. (nngroup.com/articles/dashboards-preattentive, smashingmagazine.com/2021/11/dashboard-design-research-decluttering-data-viz)
- Preattentive-attribute guidance (NN/G): position and LENGTH (bar/line charts) are processed far faster than area (pie/donut/treemap) or color alone; color should reinforce, not carry, meaning (never color-only for severity — pair with icon/shape, which our SEMANTIC_ICON signaling already does). Eye-tracking shows an F-pattern scan (top-left first, horizontal sweep, then down the left rail) — the single highest-priority KPI/metric must sit top-left, not bottom-right. (nngroup.com/articles/dashboards-preattentive, nngroup.com/videos/chartjunk)
- Progressive disclosure (Nielsen, 1995; still the core NN/G cognitive-load reduction pattern) works by hiding EXTRANEOUS load behind a click/expansion, not by deleting information — the classic dashboard failure mode is 'everything visible at once.' Applies directly to: collapsing secondary analytics rows on Overview into an opt-in group, collapsing consecutive alerts inside a correlated case, and collapsing older activity in a case thread. (nngroup.com/videos/progressive-disclosure, nngroup.com/articles/4-principles-reduce-cognitive-load)
- 8px-grid spacing systems from Atlassian and IBM Carbon (both enterprise/analyst-tool design systems) converge on the same shape: base unit 8px, half-step 4px reserved ONLY for the smallest/densest chrome (icon gaps, chip padding), and — critically — both systems SKIP 20px and 28px once they reach section-level spacing (Carbon's scale jumps 16->24->32 and 12->16, never landing on 20 or 28; Atlassian groups 0-8px = 'compact', 12-24px = 'medium/balanced', 32-80px = 'spacious/layout-level'). This independently validates that Tailwind's own `space-5` (20px) and `space-7` (28px) are off-rhythm outliers that professional dense-UI systems deliberately omit. (atlassian.design/foundations/spacing, carbondesignsystem.com/elements/spacing/overview)
- Typographic scales for dense B2B/enterprise dashboards commonly start from a 14px (not 16px) base, and best practice is a NON-uniform, compressing-then-expanding curve (small steps near the base for table/label text, wider steps at the top for page/section titles) rather than one fixed ratio throughout — this is exactly the shape of a well-tuned analyst-console type scale. (fontfyi.com/blog/building-type-scale-design-system, designsystems.com/typography-guides, penpot.app/blog/using-design-tokens-for-a-proportional-typographic-scale)
- Table/row density has settled industry numbers: MUI Data Grid's 'compact' density uses 8px cell padding (yielding ~32-36px rows with a 13-14px line height); AG Grid's default 'standard' row is 42px; Elastic's own EUI DataGrid exposes an explicit density toggle (expanded/normal/compact) rather than one fixed height. WCAG 2.2's 24x24px minimum target size sets the floor for any interactive control inside a compact row. (mui.com/x/react-data-grid/row-height, ag-grid.com/javascript-data-grid/row-height, eui.elastic.co/docs/components/data-grid/style-and-display, material-react-table.com/docs/guides/density-toggle)
- Command-center / KPI-dashboard layout convention: a 12-column grid with 16px gutters; hero/primary KPI tiles span 4-6 columns x 2 rows, secondary metric cards 2-3 columns x 1 row, charts 4-8 columns — tile SIZE should encode data PRIORITY, not just content volume, reinforcing the F-pattern top-left rule above. (datawirefra.me/blog/dashboard-layout-patterns, orbix.studio/blogs/bento-grid-dashboard-design-aesthetics)
- Alert-fatigue / noise-reduction UX literature (Signal Detection Theory applied to triage UIs) frames every alert-handling decision as hit / miss / false-alarm / correct-rejection, and recommends: tiered VISUAL treatment by severity (size+color+placement together, never one alone), threshold controls that show the hit/false-alarm trade-off (not a bare slider), and grouping/deduplication BEFORE presentation so the analyst's attention budget is spent on true signal. (ux-bulletin.com/signal-detection-theory-in-ux, panther.com/blog/what-is-alert-fatigue)
- Real alert-correlation products (ServiceNow Event Management, New Relic, Rootly, Upstat) converge on 3 grouping strategies that map cleanly onto our existing cluster-signature engine: tag/entity-based grouping (shared IP/host/user), pattern/text-similarity grouping, and time-window deduplication — surfaced in the UI as 'N similar alerts merged into this case' with an expand affordance (progressive disclosure), not a flat always-expanded list.
- Elastic Security's alerts-to-cases workflow (the closest real analog to our Noise Reduction flow) is: multi-select alerts in a table -> bulk action 'Add to new/existing case' -> case carries severity/status/tags, with an explicit alert<->case status-sync toggle. Microsoft Sentinel's incident page uses a small, fixed tab set (Overview / Entities / Timeline) plus a right-side slide-in panel for entity drill-down so the analyst never leaves the incident context — both patterns argue for a small, fixed tab count with in-place drill-in panels rather than deep navigation. (elastic.co/guide/en/security/8.19/cases-open-manage.html, elastic.co/guide/en/security/8.19/signals-to-cases.html, learn.microsoft.com/en-us/azure/sentinel/investigate-incidents, learn.microsoft.com/en-us/azure/sentinel/entity-pages)
- Linear's collaboration/thread pattern (current best-practice bar for 'calm but functional' collaboration UX) threads comments+reactions inline, and — most relevant to our case-thread — COLLAPSES consecutive same-type activity events between comment threads so the feed doesn't become a noisy status-change log; the composer sits quietly at the bottom rather than as a heavy header. (linear.app/docs/comment-on-issues, linear.app/changelog/2025-04-03-collapsed-issue-history, linear.app/changelog/2023-02-09-threaded-comments)
- Tooling exists to enforce a spacing/type-token discipline at CI time rather than relying on review discipline alone: eslint-plugin-tailwindcss's `no-arbitrary-value` rule (and the newer token-aware `@poupe/eslint-plugin-tailwindcss` with `prefer-theme-tokens`) can fail a build on any `text-[..]`/`gap-[..]` arbitrary value or on off-scale utility classes outside an explicit allowlist. (github.com/francoismassart/eslint-plugin-tailwindcss/blob/master/docs/rules/no-arbitrary-value.md, npmjs.com/package/@poupe/eslint-plugin-tailwindcss)
- Cross-check against our own codebase: `webui/tailwind.config.js` already ships a hand-tuned, non-linear type scale (2xs 11/14, xs 12/16, sm 13/18, base 14/20, md 15/22, lg 16/24, xl 18/24, 2xl 20/26, 3xl 24/30, 4xl 30/36) and `webui/src/ui/table.tsx` already implements exactly the industry-standard density split (`density='compact'` -> `h-9`/`py-2` ~= 34-36px rows; `density='normal'` -> `h-11`/`py-3` ~= 44px rows) — both are already correctly shaped per the research above and should be preserved, not reinvented. The gap is enforcement/consistency, not the tokens themselves: `docs/research/2026-07-round8/PLAN.md` (item #4b) independently found the exact off-rhythm violations this research predicts — `gap-5`(20px) x26, `space-y-5`(20px) x5, `space-y-8`(32px) x11 used at section level across Metrics/Scans/Catalog/Account/Tuning/etc. — and had already drafted a fix (section rhythm = `space-y-6` only; card-internal = `space-y-4`; tight in-component = `space-y-1/2/3`) plus a single `Eyebrow`/overline primitive to replace 5+ divergent micro-label sizes. This is independent convergence with real design-system precedent (Carbon/Atlassian), not a coincidence, and is strong grounds to ship the R1-R5 ruleset in PLAN.md as-is.
**Recommendations:**
- Adopt (or, per the Round-8 PLAN.md #4b finding, CONFIRM and ship) a strict spacing-rhythm rule with exactly 3 legal tiers, matching Carbon/Atlassian precedent: page-section rhythm = `space-y-6` (24px) ONLY — never `space-y-5`/`space-y-7`/`space-y-8`/`gap-5` at section level; card/panel-internal stacks = `space-y-4` (16px); tight in-component clusters (icon+label, chip rows, badge groups) = `space-y-1`/`space-y-2`/`space-y-3` (4/8/12px). Reserve 32px+ (`space-y-8`, `gap-8`) exclusively for top-level PageContainer ZONE separation (e.g. between the KPI strip and the widget grid), never for ordinary content stacking — mirroring Carbon's deliberate 16->24->32 jump that skips 20/28px.
- Add a CI lint gate (extend the existing design-gate/gate-grep referenced in PLAN.md, or add `eslint-plugin-tailwindcss`'s `no-arbitrary-value` rule scoped to `gap-*`/`space-y-*`/`p-*`/`text-*`) that fails the build on `gap-5`, `space-y-5`, `space-y-7`, or any `text-[..]` arbitrary font-size outside the defined scale, so this doesn't regress the way it already has in Metrics.tsx/Scans.tsx/Catalog.tsx/Account.tsx/Tuning.tsx/etc. per PLAN.md's own audit.
- Keep the existing non-linear Tailwind `fontSize` scale (11/12/13/14/15/16/18/20/24/30px) unchanged — it already matches the 'compressed near the 14px base, widening toward headings' shape enterprise research recommends — but finish enforcing ONE micro-label ('eyebrow'/overline) recipe: a single `export const overline` in `webui/src/soc/lib/ui-recipes.ts` plus a matching `<Text variant="overline">` in `webui/src/ui/typography.tsx`, and codemod away the ~5 duplicate ad hoc sizes (`text-xs uppercase`, `text-sm uppercase`, `text-[11px]`, `text-[10px]`, `text-[0.65rem]`) currently scattered across KpiTile.tsx/DashboardGroup.tsx/NavSidebar.tsx/BaselineGauge.tsx/etc.
- Establish an explicit 2-level heading hierarchy app-wide: page `<h1>` (PageHeader) at `text-2xl`/600 weight (20-26px) must always visually outrank a card title (`text-lg`/16-18px, `CardTitle`) — currently PageHeader hardcodes `text-lg sm:text-xl`, the SAME size as a card title, per PLAN.md's audit; route it through the shared `Heading` component (`as="h1" level={2}`) so the fix lands once and every page benefits, not just Overview's one-off `.hero-display` CSS class.
- For the Cases/Logs/alert-list tables, keep `density='compact'` (`h-9`/`py-2`, ~34-36px rows) as the analyst default — it already matches MUI's 8px-compact-padding convention and sits above the WCAG 2.2 24px interactive-target floor — but expose a per-user compact/comfortable toggle (wire into the existing `UserPrefsStore` table-column-state, which already persists per-user column state) rather than hardcoding one density everywhere, matching MUI/EUI's own density-toggle pattern.
- On the Security Command Center (Overview), apply the 12-column-grid + tile-size-encodes-priority convention explicitly: the single highest-priority tile (Active Risk Index / open-critical-cases count) must sit top-left (F-pattern), sized as a hero tile (4-6 cols x 2 rows); secondary KPIs at 2-3 cols x 1 row; charts at 4-8 cols. This validates PLAN.md's own proposed fix — wrapping the lower-priority analytics rows (current Rows B/C/D, 9 widget cards) in ONE collapsed-by-default `DashboardGroup` labeled 'Deeper analytics' — as the correct progressive-disclosure move, not a compromise; ship it.
- For the Noise Reduction alerts->cases flow, replace/avoid any area-based visualization (donut/pie 'noise reduced' charts) with a LENGTH-encoded horizontal funnel (raw alerts -> deduplicated -> correlated -> cases created), consistent with NN/G's preattentive-attribute guidance and with the QRadar-style horizontal-flow redesign already scoped in PLAN.md item #8; show the live before/after signal-to-noise count as the funnel's own labels rather than a separate stat.
- Model the alert-to-case grouping UI directly on Elastic Security's cases workflow: bulk-select correlated alerts -> a single 'N similar alerts merged' expandable chip (progressive disclosure — collapsed by default, matching our correlation engine's cluster signature) rather than an always-expanded alert list; keep an explicit status-sync affordance between the case and its member alerts.
- For CaseDetail, keep the small fixed tab set (Overview / Timeline-Trace / Evidence / Collaboration / Why) and use a right-side slide-in panel for drill-down (e.g. entity/enrichment detail) rather than new routes/tabs, mirroring Microsoft Sentinel's Entities-tab-plus-side-panel pattern — this keeps investigation context intact; don't add more top-level tabs.
- In CaseThread/CaseActivityFeed, collapse consecutive same-type system events (status changes, tuning updates) between human/AI comment threads, Linear-style, instead of listing every event flatly; keep the composer visually quiet (a plain `border-t pt-4` divider, no icon/label header) so it doesn't compete with case evidence for attention — matching PLAN.md's own proposed composer simplification and directly validated by Linear's shipped pattern.
- When exposing threshold-tuning controls (the existing `threshold_tuner`/Tuning UI), frame them with Signal-Detection-Theory language and visuals rather than a bare slider: show the current hit-rate / false-alarm-rate trade-off (e.g., a small two-bar or scatter visual next to the Wilson-lower-bound FP metric already computed server-side) so operators see the consequence of tightening/loosening a rule, not just a number.

## Round-8 SOC-UX research: empty-state + loading-skeleton design for a data-sparse first-run install, applied to our Security Command Center dashboard, Cases queue, case-detail tabs, embedded chat/collaboration, and the Noise Reduction alerts-to-cases flow

**Findings:**
- Skeleton vs. spinner timing (NN/g): skip loading indicators under 1s; use skeleton screens (not spinners) for full-page/list loads of 1-10s because they give layout context and measurably improve perceived performance; switch to a determinate progress bar over 10s. Our webui/src/soc/components/PageSkeleton.tsx and webui/src/ui/skeleton.tsx already implement this correctly: a 1.8s ease-in-out shimmer sweep, a skeleton that mirrors the resting header+KPI+card chrome so layout never shifts on resolve, and a prefers-reduced-motion fallback to a static block (webui/src/styles/theme.css lines ~341-405). This is a validated strength, not a gap.
- Empty-state anatomy (Pencil & Paper, IBM Carbon, SAP Fiori, Material Design): every good empty state has 3 parts — informative copy, a visual/icon, and a CTA that answers 'what do I do now' — and copy must never imply user fault. Our EmptyState.tsx primitive (webui/src/soc/components/EmptyState.tsx) already encodes exactly this shape (icon chip + title + description + action slot, plus an error variant) and is used consistently across Overview, Cases, Campaigns, Tuning, Approvals, Inbox, and Audit.
- Zero-data vs. no-results vs. cleared-filters are three DISTINCT empty states needing different copy and CTAs — a filtered 'no results' must never be a dead end (Slack/Pencil & Paper pattern: suggest clearing filters or related content). Cases.tsx already implements this correctly: title flips between 'No cases yet' and 'No cases match your filters' with a 'Clear filters' action (webui/src/soc/pages/Cases.tsx ~lines 1345-1360) — this is the single most complete instance of the pattern in the codebase and should be the template other list pages are audited against.
- GAP (verified in code): chart empty-states are inconsistent. DonutChart, HBarChart, and TrendArea (webui/src/soc/components/charts.tsx) all render a centered visible 'No data' text label when their data array is empty (lines ~131-142, ~225-236, ~317-328), but MiniBars (line ~404-406) and Sparkline (line ~448) render a fully blank <div> with only an aria-label and zero visible pixels when empty. This breaks the core empty-state rule shared by Carbon/SAP/Material — never render literal nothing, because a sighted user cannot distinguish 'no data yet' from 'broken layout'. These two components are exactly the ones used inline next to KPI numbers on Overview.tsx, so on a fresh install the KPI strip will show numbers with invisible holes beside them instead of an intentional-looking placeholder.
- GAP (verified in code): NoiseFunnel.tsx explicitly renders `null` when there is no data and it isn't loading ('Absent data + not loading -> render nothing', line ~329-330). The Noise Reduction funnel is the single best 'value prop' visualization in the whole product (the story of alert-volume reduction), yet on a brand-new install with zero sources connected it simply doesn't exist on the page — a true blank hole in the Overview layout, which is the worst possible first impression for a demo/evaluation audience.
- GAP (verified in code): the Cases queue — explicitly called out in the task as a primary surface — is hardcoded to `density="compact"` in Cases.tsx (line ~1343) with no user-facing density toggle, while a much lower-traffic page (Knowledge.tsx, the RAG documents table) DOES have a working density toggle persisted to raw localStorage (`tlsoc.knowledge.density`, lines ~129, ~1100, ~1313-1318). DataTable.tsx itself already supports a `density: 'normal' | 'compact'` prop end-to-end, so the underlying capability exists; it's simply not exposed as a control on the highest-traffic dense table in the app, and the one place it IS exposed doesn't use the existing synced per-user preferences store.
- Enterprise dense-table research (Pencil & Paper, Denovers, Justinmind): recommended row-height presets are ~40px compact / 48px regular / 56px relaxed, with the choice persisted per user and a visible reset-to-default; row actions should be revealed on hover or collapsed into a single trailing kebab menu rather than shown inline at all times; numeric columns should right-align in a monospace/tabular-nums font so figures compare visually; default sort should be most-urgent-first for a triage queue.
- SIEM/SOC-specific noise research (SANS 2025 Detection and Response Survey via Cybrill/Vectra/Graylog writeups): 73% of security teams cite false positives as their top detection challenge; an alert only reads as 'signal' once it arrives enriched with asset criticality, owner, and related prior alerts on the same entity — context-poor alerts read as noise regardless of how they're styled. This validates investing further in the Noise Reduction funnel's per-severity breakdown and the case's enrichment/threat-context panel as the actual lever, not just visual polish.
- Microsoft Sentinel/Defender's 2025 case-management redesign converged on a single unified incident+case queue where an analyst triages an incident then 'cuts a case' and attaches evidence/queries for collaboration, with an AI-generated, transparently-scored risk ranking surfaced directly in the queue (not hidden behind a click) — directly analogous to our Cases queue + CaseDetail 'Why' rationale tab pairing.
- Accessibility for severity/status coding (WCAG 1.4.1, Carbon/Red Hat design-system guidance): color alone is never sufficient — status indicators need at least a second channel (icon or text label) and a minimum 3:1 contrast between the indicator and its background. Our badges.tsx already does this correctly via a shared SemanticGlyph icon-plus-color pairing on every severity/status/verdict/disposition/risk badge (webui/src/soc/components/badges.tsx) — validated as already meeting the bar.
- Empty-state 'starter content' pattern (Whimsical, Amplitude): rather than a blank container, populate the surface with real or seeded structure the user can explore/modify, which measurably reduces first-run anxiety versus a pure CTA-only blank state; Linear instead uses progressive disclosure (reveal power features only as they become relevant) rather than a guided tour. Our product already has the exact mechanism to do this for a SOC console (a sandboxed, $0, one-flip-reversible Demo Mode seeding a fictional org through the real pipeline, per engine/demo_generator.py / engine/demo_runtime.py) but the Overview.tsx wholly-empty state (line ~863-877) offers only a single 'Connect a source' CTA, not a 'try it with sample data' path into that existing Demo Mode.
- Chat/collaboration side-panel patterns (Claude Artifacts, Microsoft 365/Google Workspace Copilot placement, Slack's two-panel list+thread model): AI chat should sit beside the primary workflow, not replace or cover it, and an empty conversation should offer clickable starter prompts rather than a blank input. Our ChatPanel.tsx already implements exactly this: a centered empty state with clickable, immediately-submitting suggested starter prompts (webui/src/soc/components/ChatPanel.tsx, 'Suggested prompts for the empty state' at line ~114, empty-state block ~line 658-919) — validated as already matching best practice.
**Recommendations:**
- Fix charts.tsx MiniBars (line ~404-406) and Sparkline (line ~448) to match their sibling components: when the data array is empty, render the same visible 'No data' muted-foreground text used by DonutChart/HBarChart/TrendArea, or — since these are inline/small (KPI-adjacent) contexts where text may not fit — render a flat dashed baseline in `text-muted-foreground`/`bg-muted` at mid-height as a 'ghost trend' placeholder. Either way, never leave a literal empty <div>; a sighted first-run user must be able to tell 'no data yet' from 'this is broken'.
- Give NoiseFunnel.tsx a genuine empty/ghost state instead of returning null when `!data && !loading`: render the existing FunnelBar geometry with a fixed illustrative taper (e.g. flat 100/70/45/25/12% in bg-muted, no severity segmentation) captioned 'Your noise-reduction funnel will appear here once cases start flowing' plus the same 'Connect a source' CTA already used on Overview's page-level EmptyState. This turns the single best value-prop widget in the product from an invisible hole into an intentional-looking preview on a fresh install — exactly the 'show structure, not blankness' principle from the empty-state research.
- Add a secondary CTA to Overview.tsx's wholly-empty state (EmptyState at line ~863-877) and to Cases.tsx's 'No cases yet' state: alongside 'Connect a source', offer 'See it with sample data' / 'Try Demo Mode' wired to the existing `POST /api/demo/enable`. This reuses infrastructure that already exists (sandboxed, $0, one-flip-reversible per the W5 Demo Mode) to solve the classic SOC cold-start problem the same way Amplitude solves it for analytics dashboards — populate real-looking structure instead of forcing evaluators to stare at empty text before connecting a live source.
- Expose a density toggle on the Cases queue (Cases.tsx) the same way Knowledge.tsx already does, since DataTable.tsx's `density` prop is already fully wired end-to-end — this is a small, low-risk change (one control + one bit of state). While doing it, route the persisted choice through the EXISTING per-user prefs cascade (`PUT /api/prefs/user/tables/{table_id}`, stores/user_prefs.py) instead of Knowledge.tsx's raw localStorage key, so the preference syncs across devices/sessions like the rest of the per-user customization system — and backfill Knowledge.tsx's toggle onto the same store while you're there for consistency.
- Audit every other filterable/dense list surface (Campaigns.tsx, Tuning.tsx, Audit.tsx, Approvals.tsx, Inbox.tsx, Baseline.tsx, BatchJobs.tsx) against the Cases.tsx gold-standard empty-state pattern: confirm each distinguishes a true zero-data state from a filtered-to-nothing state with distinct copy and a 'clear filters' recovery action, since a quick grep shows most currently render a single generic EmptyState regardless of whether filters are active.
- When adding new dense surfaces (Dashboards.tsx custom widget grid, any future Round-8 pages), keep enforcing the existing skeleton discipline already proven on DataTable's SkeletonRow and PageSkeleton — row-shaped placeholders that match the real column layout, a shared 1.5-2s ease-in-out shimmer, and a static reduced-motion fallback — rather than a generic spinner; this is cheap to keep consistent and expensive to retrofit later, so consider adding a lint/design-gate check (mirroring the project's existing design-gate CI check) that flags any new async list/table view that renders a spinner instead of a Skeleton-family placeholder.
- For the Cases queue and any other high-density table, adopt the 40/48/56px compact/regular/relaxed row-height convention from the enterprise-table research as the concrete pixel targets if/when a broader density system is introduced, and keep numeric/count columns (Alerts, Playbooks, Risk score) right-aligned with tabular-nums — spot-check that this is already true; it appeared to be for the columns inspected.
- On CaseDetail's tabs (overview/investigation/threat/collab/chat), consider surfacing a lightweight count badge on tabs whose content can be legitimately zero on a fresh case (e.g., 'Collaboration (0)') so users don't have to click into an empty tab to discover it's empty — a small discoverability win consistent with the empty-state goal of never leaving a user guessing whether something is broken.

## SOC-console UX research: data-table design (density, sticky headers, severity accents, badge restraint, column curation) plus Command Center / Noise Reduction / case-detail chat patterns, benchmarked against our actual webui code

**Findings:**
- Sticky headers: consensus (Pencil & Paper, NN/g) is 'fixed headers should be default for any table likely to exceed one viewport.' Our webui/src/ui/table.tsx already implements the two things most implementations get wrong: an OPAQUE background (bg-surface, not translucent) so scrolled rows never bleed through, and a top offset matched exactly to the real fixed app-bar height (top-[var(--header-h)], 56px) rather than top:0 — this is precisely the failure mode CSS-Tricks/Carbon/community threads flag ('header tucks behind the app bar' / 'scrolled rows show through a semi-transparent header').
- What makes sticky headers read as 'glitchy' (CSS-Tricks, Carbon Design System GitHub issues, freeCodeCamp/dev.to writeups): (1) position:sticky on <thead> instead of <th> — cross-browser support for sticky thead is inconsistent, so implementations must sticky the <th> cells; (2) translucent/backdrop-blur-only backgrounds letting body rows bleed through while scrolling; (3) border-collapse:collapse + sticky causes borders to vanish/double — fixed via border-collapse:separate + border-spacing:0, or an inset box-shadow instead of a border; (4) missing/low z-index letting dropdowns/popovers render under the pinned header; (5) horizontal-scroll tables where the sticky header desyncs from body columns once a scrollbar appears; (6) no box-shadow depth cue (e.g. 0 2px 2px -1px rgba(0,0,0,.4)) so the header doesn't read as 'floating above' scrolled content.
- Row density: guidance (Pencil & Paper 'Enterprise Data Tables') recommends discrete tiers around Condensed 40px / Regular 48px / Relaxed 56px, exposed via an icon switcher OUTSIDE the table, persisted per-user. Zebra striping is now widely discouraged for interactive tables because it conflicts with hover/selected/disabled row states (Pencil & Paper and MindK independently make this point); the modern consensus is thin 1px horizontal hairlines + a hover highlight only — which is what our DataTable already does (no zebra striping in webui/src/ui/table.tsx / DataTable.tsx).
- Left-edge severity accents: an established, low-noise pattern for signaling per-row severity (colored ~3-4px left border on a neutral row background) is documented across status/severity design-system patterns (Carbon, PatternFly). It must never be the ONLY signal — WCAG 1.4.1 requires a non-color channel too. PatternFly explicitly separates STATUS (system/lifecycle state) from SEVERITY (how bad an issue is) as non-interchangeable axes, each requiring an icon+text+color triad, with icon shapes never reused across different color meanings.
- Badge restraint: 'if everything has a badge, none of them feel important' — badges should carry ONE content type (icon, short text, or count — not compound) and be used sparingly; overuse causes notification-fatigue-style blindness (Povio, Setproduct). Column curation guidance (NN/g's 'four major user tasks' framework: find/compare/view-one-record/act) says to design the table around what it's FOR, prioritize which columns matter on first load, and hide overlapping/secondary columns behind a discoverable, reversible 'Columns' control rather than dumping every available field.
- SOC-specific alert-triage conventions: a standard alert-queue field set is source/timestamp/entity/asset/user/severity/MITRE-tactic/environment, ranked by a composite risk score blending alert signal + asset criticality + user/entity context + threat-intel + recency; analysts are trained never to treat a vendor/source severity as final. Elastic Security Cases (the closest direct comparable) shows case severity/status/assignee/tags on the case itself, lists attached alerts oldest-to-newest in a dedicated Alerts tab, and surfaces row actions via HOVER-triggered inline actions (filter in/out, add to timeline, copy) rather than a permanently-visible actions column.
- Noise reduction / alert grouping: intelligent grouping clusters on shared root cause/entity/time-window; well-tuned pipelines report >90% dedup rates (incident.io, Datadog). Critically, backend correlation alone is not sufficient — a Feb-2026 paper (arXiv 2602.01671, 'AI-Assisted Adaptive Rendering for High-Frequency Security Telemetry in Web Interfaces') found static pagination/fixed-poll rendering fails above ~hundreds-of-thousands events/sec, causing frozen UIs and stale displays; its fix — dynamic refresh-rate throttling by volume, semantic (severity-based) render prioritization, and local ML-based aggregation of low-priority events — cut client rendering overhead 45-60% while preserving the analyst's PERCEPTION of real-time updates.
- Embedded chat/collaboration trend (2025-2026): keep case/customer CONTEXT visible in a persistent side panel alongside the conversation (Intercom-style), rather than a full-screen chat takeover; render AI outputs as distinct structured 'assistant cards' instead of more chat bubbles for anything beyond short text; prefer one-click review/confirm affordances for agentic suggestions over free-text back-and-forth.
- Command-center dashboards: organize KPIs into role-relevant groups (detection effectiveness / response performance / coverage / risk / operational efficiency); place the highest-urgency information top-left (F-pattern scan start point); every on-screen element should earn its cognitive-load budget — remove anything that doesn't support the user's current decision.

- TRIPLE-REDUNDANT case header (highest-impact finding): CaseDetail's Overview tab renders the same handful of signals three times in three different visual grammars, stacked with no breathing room between them — (1) the CaseTriageHeader 4-chip row (Risk/Severity/Impact/Priority; the Risk chip embeds a full RiskGauge), (2) a 2-column 'Verdict + Confidence' HeadlinePanel pair directly beneath it, (3) a badge strip right below THAT with VerdictBadge + ConfidenceBadge + RiskBadge + StatusBadge + DispositionBadge + an escalation Badge + AutoClosedBadge (webui/src/soc/pages/casedetail/OverviewPanel.tsx lines 487-540). Risk is shown via gauge AND badge; Verdict and Confidence are each shown in the headline panel AND again one row down as a badge. Three rows of chrome recompute the same ~5 facts before any case content appears.
- SettingsCard (webui/src/soc/components/SettingsGrid.tsx:74-104) — the section-card chrome used across ALL of Settings plus Campaigns/Baseline/Tuning/BatchJobs (12 consumer files: Settings.tsx, Campaigns.tsx, Baseline.tsx, Tuning.tsx, BatchJobs.tsx, settings/knowledge.tsx, settings/advanced-schema.tsx, settings/primitives.tsx, settings/detection.tsx, settings/case-policy.tsx, settings/advanced.tsx, settings/general.tsx) — is a hand-rolled <section> hardcoding px-5 py-4 for header/body/footer instead of using the shared <Card> primitive's sanctioned padding scale (sm=px-4 / md=px-6 / lg=px-8). The Card primitive's own docstring (webui/src/ui/card.tsx) explicitly calls px-5 'the off-grid padding the overhaul set out to kill' — yet the single most-reused section-card component in the entire Settings surface still uses it, undermining the 'ONE card grammar' claim at its widest point of leverage.
- 21 files still use the disavowed off-grid p-5/px-5 instead of Card's sm|md|lg scale: components/SettingsGrid.tsx, components/BudgetCard.tsx (a raw border+bg-card+p-5 div that bypasses <Card> entirely, 2 instances), components/PageHeader.tsx (3, incl. the 'hero' variant band), components/ChatPanel.tsx, components/DataTable.tsx, components/MfaSetupCard.tsx, components/SessionPolicyEditor.tsx, components/BrandingEditor.tsx, and pages/Metrics.tsx (11 instances — the single worst offender), plus Wizard.tsx (5), Account.tsx (4), Scans.tsx (3), Catalog.tsx (3), Security.tsx (2), Memory.tsx (2), and one-off hits in Tuning/Investigate/Chat/BatchJobs/Baseline/casedetail/DecisionCard.
- CardContent padding is inconsistent everywhere it's hand-specified: grep across pages/+components/ turns up 12x 'py-4', 3x 'pt-6', 3x 'space-y-4 p-5', 3x 'p-0', 2x 'space-y-5 p-6', 2x 'space-y-4 py-4', 1x 'p-6 sm:p-8', 1x 'p-6 sm:p-7', 1x 'p-5', 1x 'space-y-2.5 p-5', 1x 'divide-y divide-border p-5' — essentially every card on every page re-derives its own padding ad hoc rather than using the Card `padding` prop, so no two pages' cards feel like the same rhythm.
- StatCard is documented @deprecated in its own file ('absorbed into KpiTile as variant="bar"'; kept only for 'one transition wave') but is still the LIVE, actively-used component in 6 files: Metrics.tsx (16 call sites — by far the heaviest user), Models.tsx (4), BatchJobs.tsx (4), BaselineGauge.tsx (4), plus Cost.tsx (1). Metrics.tsx mixes StatCard and KpiTile in the SAME page for the same visual concept (small stat tiles), so identical-looking tiles are produced by two different code paths depending on which section of the page you're in.
- Metrics.tsx is the single densest, most visually noisy page: ~29 Card/ChartCard/KpiTile-level sections across 4 tabs (Operational/Performance/Posture/Cost), including 6+ near-identical `<h2 className="text-xs font-semibold uppercase tracking-wider text-muted-foreground">` subsection labels that were never componentized (each hand-typed inline instead of a shared SubsectionHeading), producing a page that reads as a long column of small-caps labels punctuated by cards rather than a small number of clearly demarcated zones.
- Header-size inconsistency outside the shared PageHeader: ad-hoc <h1>/<h2> sizes are scattered across pages at 6+ different scales with no evident rule — text-base (Approvals, Knowledge, Metrics section headers), text-sm (Models, Memory, Security x2, Roles, Tuning), text-lg (CaseDetail case-name, Wizard step title), text-xl (Login wordmark), text-xs uppercase (6 Metrics subsections), and the CaseTriageHeader/Metrics KPI values themselves at text-2xl font-bold — next to 195 other uses of font-semibold for comparable weight, i.e. font-bold vs font-semibold is used interchangeably for 'big numeral' emphasis (Cost.tsx:898, Metrics.tsx:466/592/644, CaseTriageHeader.tsx:137, BrandingEditor.tsx:833) with no evident rule for when a numeral gets bold vs semibold.
- Badge-density hotspots: Knowledge.tsx (22 <Badge> renders), Catalog.tsx (14, several as stacked BadgeRow groups — e.g. one signature card shows four separate capped badge-rows for rule_ids/entity_types/mitre/tags back-to-back under one 'Match criteria' label, Catalog.tsx:295-330), Standup.tsx/Cases.tsx/Approvals.tsx (10 each), Scans.tsx (9). Cases.tsx additionally spreads Status+AutoClosed, Disposition, Category, Severity, Confidence, Verdict, Risk each into its OWN table column (7 separate badge-bearing columns) — defensible as optional/hideable columns but still the densest badge surface in the app when several are on at once.
- HeroPanel.tsx is marked @deprecated ('merged into PageHeader as variant="hero"') and is now just a thin pass-through wrapper around PageHeader — not visually divergent anymore, but it's still the load-bearing hero for components/layouts.tsx's DashboardLayout archetype (consumed by pages/Dashboards.tsx), meaning there are two parallel named entry points (PageHeader variant='hero' directly, vs HeroPanel via layouts.tsx) for the identical visual result — a tidiness/indirection leftover rather than a visible bug.
- CardHeader className overrides show minor drift from the Card primitive's own default (px-6 py-4): 11 call sites use 'pb-3' as a bespoke bottom-padding tweak, 2 use the flex-row-justify-between reset pattern, and a handful of one-off combinations (gap-3/gap-1.5/gap-4) — small individually but signals CardHeader's rhythm isn't treated as a fixed contract.
**Recommendations:**
- Fix CaseDetail's Overview tab redundancy first (highest visible payoff, single file): collapse the three stacked verdict/confidence/risk representations in OverviewPanel.tsx (lines ~487-540) into one. Keep the CaseTriageHeader 4-chip row as the ONE risk/severity/impact/priority surface; fold Verdict + Confidence into it as a 5th/6th chip (or into the chip row's sub-line) and delete the separate HeadlinePanel pair; keep the badge strip only for the things NOT already in the chip row (Status, Disposition, escalation, AutoClosed) so nothing is shown twice.
- Rebuild SettingsCard (components/SettingsGrid.tsx) on top of <Card padding="md"> / <CardHeader> / <CardContent> / <CardFooter> instead of a hand-rolled <section> with hardcoded px-5 — this one fix ripples across all 12 Settings/Campaigns/Baseline/Tuning/BatchJobs consumers at once and eliminates the single biggest source of off-grid padding.
- Convert components/BudgetCard.tsx's raw 'border+bg-card+p-5' divs to <Card padding="md"> so it stops being a second parallel card implementation.
- Do a mechanical sweep of the remaining p-5/px-5 sites (Metrics.tsx x11, Wizard.tsx x5, Account.tsx x4, Scans.tsx x3, Catalog.tsx x3, PageHeader.tsx hero band x3, plus the single-instance files) to the Card sm/md/lg scale, prioritizing Metrics.tsx since it's both the worst padding offender and the most over-sectioned page.
- Migrate Metrics.tsx's remaining StatCard call sites (16 of them) to KpiTile variant="bar" directly per the Codemod note already written into StatCard.tsx's own docstring — do the same for Models.tsx, BatchJobs.tsx, BaselineGauge.tsx, Cost.tsx, then delete StatCard.tsx once zero importers remain.
- Componentize Metrics.tsx's repeated inline subsection label (`text-xs font-semibold uppercase tracking-wider text-muted-foreground`, used 6+ times) into a single SubsectionHeading/ChartCard-style primitive, and use it to actually merge/thin adjacent one-off sections (Operational tab alone has 8+ ChartCards) rather than just re-skinning the same count of sections.
- Pick ONE weight convention for big numerals (recommend font-semibold everywhere, matching the KpiTile/StatCard default and the 195:6 existing ratio) and change the 6 stray font-bold sites (Cost.tsx:898, Metrics.tsx:466/592/644, CaseTriageHeader.tsx:137, BrandingEditor.tsx:833) to match.
- For badge-dense surfaces (Knowledge.tsx, Catalog.tsx signature cards, Cases.tsx table), audit which badges are load-bearing vs decorative per view and cap simultaneous visible badge rows (e.g. Catalog's four stacked BadgeRow groups under 'Match criteria' could share one wrapped flex row with icon-differentiated groups instead of four separate label-less rows).
- Once SettingsCard is rebuilt on <Card>, delete HeroPanel.tsx's remaining live consumer path (components/layouts.tsx DashboardLayout) by pointing pages/Dashboards.tsx at <PageHeader variant="hero"> directly, then retire HeroPanel.tsx and layouts.tsx's hero re-export to remove the duplicate entry point.
- Normalize the 11 bespoke CardHeader 'pb-3' overrides to the Card's own padding='sm'|'md' prop so CardHeader stops being individually tweaked per call site.

## #1 Active Risk Index — reposition top-right + (?) tooltip + unify the two conflicting numbers


**Approach:** CANONICAL DEFINITION (the single decision this item makes). Today there are two numbers labelled "Active Risk Index": (a) Overview's `riskIndex` memo (`Overview.tsx:397-408`) = `clamp(round(avg*0.7 + criticalDensity*100*0.3))`, where `avg` is the ALL-cases/all-time `metrics.avg_risk_score` (or a windowed client fallback) and `criticalDensity` is the fraction of the windowed 200-case sample in Overview's LOCAL `bandOf` "critical" band (>=80) — an incoherent blend of an all-time mean with a windowed density; and (b) the custom-dashboard widget (`widgets/risk.tsx:17-19`) = the raw `metrics.avg_risk_score` mean over up to 2000 cases of EVERY status (open+closed+benign), which dilutes "active" pressure with terminal cases. I am collapsing both into: **Active Risk Index = the arithmetic mean of the deterministic per-case `risk_score` (0-100) over all currently-OPEN (non-terminal) cases**, where OPEN = status NOT in `TERMINAL_CASE_STATUSES` (i.e. excludes only `resolved`/`closed`; includes new/open/investigating/escalated/on_hold/needs_human/reopened). Rounded to 1 dp; 0.0 when there are no open cases. This is honest to the name ("Active"=open), reuses the existing deterministic per-case primitive (never recomputed), drops the un-disclosable critical-density blend, and is stable across the TimeRangePicker (open pressure is "now", not a created-at window) — a fact the tooltip discloses. The old `avg_risk_score` field is LEFT UNTOUCHED (Metrics.tsx:538 "Avg risk" tile still uses it honestly), so this is purely additive.

BACKEND (one function, additive). In `compute_metrics()` (`backend/app/engine/metrics.py:111-162`) compute `open_risks = [c.risk_score for c in cases if isinstance(c.risk_score,(int,float)) and (c.status.value if c.status else "") not in TERMINAL_CASE_STATUSES]` (the symbol is already imported at metrics.py:17), then `active_risk_index = round(sum(open_risks)/len(open_risks),1) if open_risks else 0.0`, and add two keys to the returned dict: `"active_risk_index": active_risk_index` and `"active_risk_case_count": len(open_risks)`. No route change — `GET /api/metrics` returns the dict verbatim. Advisory/read-time only; never read by `decide()` (#3 held — this function already has that contract). The exact-dict-free assertions in `test_existing_compute_metrics_unchanged` stay green.

FRONTEND — the hero instrument + shared copy. New component `webui/src/soc/components/ActiveRiskIndex.tsx` renders a COMPACT top-right instrument: a micro-caption "ACTIVE RISK INDEX" + a `HelpTip` (?), and beneath it a small `RiskGauge` (size 78 — reuses the existing gauge, which already draws value + band word and uses the canonical `scoreBand` 74/48/22 ladder). When `count===0` it renders a DASH placeholder ("no open cases") instead of a misleading green "0 / Low". It is wired into Overview's existing `PageHeader variant="hero"` via the currently-empty `actions` slot (PageHeader hero already right-aligns `actions` at the top of the band — that IS the header top-right; the SLA badge stays in `meta`). The old Row-A "Active Risk Index" `DashboardGroup` card (`Overview.tsx:707-738`) is REMOVED (its Open/Critical/Crit-High mini-stats already duplicate the KPI-strip tiles), so the page shows exactly one ARI; Row A's grid drops from `xl:grid-cols-3` to `xl:grid-cols-2` (open-by-severity + attention queue). Overview's `riskIndex` memo is replaced by an `activeRisk` memo that prefers `metrics.active_risk_index` (+`active_risk_case_count`), falls back to a client mean over open cases in the loaded sample, then to `avg_risk_score`, so a minimal `/api/metrics` mock still renders. The `RiskGauge` import moves out of Overview (now used inside ActiveRiskIndex); `bandOf`/`derived.critical` stay (still used by the KPI tiles + severity widget).

FRONTEND — the custom-dashboard widget. `widgets/risk.tsx` reads `data.active_risk_index ?? data.avg_risk_score` (back-compat), relabels the gauge from "mean case risk" to "open cases", surfaces the same `ACTIVE_RISK_HELP_TEXT` via `WidgetShell`'s existing `action` header slot (a `HelpTip`), and its empty message becomes "No open cases yet." Registry description (`dashboard/registry.ts:255`) updates from "The mean case risk score as a gauge." → "Average deterministic risk across currently-open cases (0-100)." Both surfaces now render the identical backend number.

COPY / DRY. The tooltip text is authored once as `ACTIVE_RISK_HELP_TEXT` and COMPOSES the existing per-factor copy so the 5-factor weights stay in one place. To avoid a third drifting copy of the weights (the `CaseTriageHeader.tsx:154` comment already warns the copies "must stay in sync"), I extract `RISK_HELP_TEXT` + `RISK_FACTOR_HELP` into a tiny side-effect-free module `webui/src/soc/components/riskCopy.ts`, add `ACTIVE_RISK_HELP_TEXT = 'Active Risk Index — the average deterministic risk score (0-100) across every currently OPEN case (it excludes resolved/closed cases and is not scoped to the selected time range). ' + RISK_HELP_TEXT` there, and re-export `RISK_HELP_TEXT`/`RISK_FACTOR_HELP` from `CaseTriageHeader.tsx` so its only external importer (`CaseTriageHeader.test.tsx`, which imports from `'../CaseTriageHeader'`) keeps working. ## #5 Animations + motion system (clearer UI, subtle, reduced-motion-safe)


**Approach:** Decision: pure CSS/Tailwind for everything that a CSS transition/keyframe can express (reveals, tab fades, hover/press affordances, gauge sweep — all auto-neutralized by the existing global `@media (prefers-reduced-motion: reduce)` block at `theme.css:374-383`), plus TWO tiny dependency-free React hooks for the things CSS cannot do: number count-up (rAF tween) and optional on-scroll reveal (IntersectionObserver). NO new npm deps — `framer-motion` was removed in Round 5 and `bundle-first-paint.test.ts` actively forbids re-adding any JS animation lib. This matches the codebase's established "pure-CSS motion + a reactive `usePrefersReducedMotion()` hook" pattern.

Foundation — wire the ALREADY-DECLARED-BUT-UNUSED motion tokens into one dial. `theme.css:147-150` defines `--motion-fast (120ms)`, `--motion-base (200ms)`, `--motion-slow (280ms)`, `--motion-ease-standard: cubic-bezier(0.2,0,0,1)`, but a grep confirms nothing references them (TESTING_BRANCH_STATE §2 "Motion tokens declared but under-used"). I add `transitionDuration.{fast,base,slow}` and `transitionTimingFunction.standard` (each = `var(--motion-*)`) plus a new `scale-in` keyframe/animation to `tailwind.config.js` `theme.extend`, giving `duration-fast/base/slow`, `ease-standard`, and `animate-scale-in` utilities. A small JS mirror `MOTION = {fast:120, base:200, slow:280, easeStandard:'cubic-bezier(0.2,0,0,1)'}` in a new `soc/motion.ts` (CSS is canonical, JS mirrors it) feeds rAF/recharts durations; I add an `easeOutCubic` fn and a `chartAnimation(reduced)` helper that returns recharts-ready `{isAnimationActive, animationDuration, animationEasing}` so the Noise-Reduction funnel (sibling item ★) and any future recharts fill animate consistently and reduced-motion-safely.

## #10 Fold feedback grading into the case-close flow

## ★a Noise-Reduction funnel — BACKEND durable raw-alert-by-severity counters + aggregation endpoint


**Approach:** Today the poll/ingest paths compute a per-cycle `stats` dict (`polled/new/clusters/investigated/candidates/attached/suppressed/ignored`) that is written to ONE free-text `AuditDoc.result_summary` and then discarded (`poller.py:289-378`, `ingest.py:196-256/438-514`); severity NEVER appears, and once N events collapse into a Cluster/Case the raw ingested volume by severity is irrecoverable. So a true "total alerts by severity → what the AI reduced it to" funnel needs a NEW durable counter store fed at ingest, stitched at read-time with the live Case store.

Split of responsibility (the honest, minimal, #3-safe design): the durable store owns ONLY the irrecoverable top-of-funnel — `ingested` (raw new events, banded) + `clustered` (clusters formed, banded) + the transient pre-triage drops `suppressed`/`ignored` (aggregate). Everything below the case boundary — `cases opened`, `auto_cleared`, `escalated`, `needs_human` by severity — is derived at READ time from the live Case store (a new pure tally alongside `quality_metrics`), because case outcomes evolve (open→investigating→closed) and read-time self-heals. `engine/case_manager.py` and `handle_clusters()` stay BYTE-IDENTICAL (I attribute bands in the poll/ingest path from the `new_events`/`clusters` lists already in scope, not inside `handle_clusters`, so its many key-access tests are untouched).

Store: `stores/funnel_counters.py::FunnelCounterStore(kv)`, the exact zero-migration KV pattern of `stores/baseline.py` (shared `self._kv` — works on ES `EsKVStore` + SQL `SqlKVStore`, no new index/table). Sharded per UTC day (`ns="funnel"`, `key="YYYY-MM-DD"`) so each write touches only today's small doc (≤24 hours × 5 bands × 2 counters ≈ a few KB) — NOT one ever-growing document — keeping the poll path fast. Value: `{"date","hours":{"HH":{"ingested":{band:n},"clusters":{band:n},"suppressed":n,"ignored":n,"cycles":n}}}`. Writes go through `base.kv_mutate` (per-key lock + `_rev` CAS) so concurrent per-source pollers can't clobber; every method is try/except fail-open (a counter glitch can never drop an event or break a poll). A one-time `_meta` doc records `first_recorded_at` (in-process flag skips the meta write after the first success → one small write per cycle in steady state).

Banding: new `engine/funnel.py` holds pure helpers — a single 5-band ladder `SEVERITY_BANDS=("critical","high","medium","low","info")` (constants) with 0-100 cut points aligned to `OCSF_SEVERITY_TO_SCORE` (constants.py:618). Scale is resolved ONCE per cycle (all events in a poll come from one source): I factor the source-lookup half of `priority.py::_scale_for_case` into a public `severity_scale_for_source(src)->str`, then `_normalise_severity(ev.severity, scale)` (existing) → `funnel_band(magnitude)`. This makes the funnel severity axis CONSISTENT with the per-case severity chip (`severity_band_from_events`). Increment points: `poller.poll_once` (band `new_events+funnel_events` → ingested; band `clusters` → clustered; `suppressed/ignored` from `cluster_stats`; one best-effort `self._funnel_sink(delta)` right before the existing audit write) and `IngestService.ingest` (band `events`; on the ignore early-return record `{ingested, ignored=len}`; else after `handle_clusters`). The sink is wired the same way as the existing `_event_funnel` hook: `Poller.__init__` gets `self._funnel_sink=None`, `PollerManager` propagates it to every child (mirroring `_event_funnel` in `_build_primary`/`_build_child_for`/`_propagate_funnel`/`rebuild` + a `set_funnel_sink()` method), and `IngestService` gets `self.record_funnel=None` set post-construction by state — default None ⇒ byte-identical when the feature isn't wired.

Endpoint: `GET /api/metrics/funnel?window_hours=24` in `routes_metrics.py` (reuses `require_permission("metrics","view")` — already granted to every role, no RBAC change; `metrics:view` confirmed in `rbac/policy.py:62`). It (1) reads durable counts for the window via `funnel_counters.read_window(window_hours)` (enumerate UTC dates in range, `get` each day-doc fail-open, sum in-window hour buckets), (2) loads cases via the existing `_load_cases` (5000-cap + `store_total`), window-filters (`_window_filter`), and tallies outcomes-by-band via the new `metrics.funnel_outcomes_by_severity(cases, prefs)`, and (3) assembles an ordered `stages[]` (each tagged `source:"counters"|"cases"`), `drops`, `reduction` pcts, and honest truncation flags. Honesty is first-class (mirrors `truncation_marker`): `counters.since`/`counters.incomplete` (window reaches before `first_recorded_at` ⇒ ingested/clustered are lower bounds ⇒ the reduction pcts return the `DASH` sentinel with a reason, never a fabricated number), plus the case-side `truncated/store_total/fetched`.

## ★b Noise-Reduction funnel — FRONTEND infographic on the Command Center


**Approach:** GOAL. Build a single, headline-grade widget that tells the value-prop story "the AI cut the alert load by N%": Stage 1 = total raw alerts by severity (durable ingest counters), Stage 2 = what correlation collapsed them into (cases, by severity), Stage 3 = the AI outcome split (auto-cleared-FP / true-positive / escalated / needs-human). It mounts as a full-width band directly under the KPI strip on Overview (the current landing page, `PAGE_TITLE` being renamed to "Security Command Center" by item #2 — I depend on that rename but do not own it). It is purely advisory (#3): it summarises `decide()` output and never feeds it; all labels are humanized enums / formatted numbers rendered as plain text (#9).

RENDERING CHOICE — hand-built DOM/CSS, NOT recharts. recharts ships `Funnel`/`FunnelChart` (bundled, zero deps) but its geometry is a single-metric tapering trapezoid stack — it cannot express per-stage severity segmentation nor a 4-way outcome split, and recharts `ResponsiveContainer` needs a sized parent that is awkward under jsdom (every existing chart sets `isAnimationActive={false}` precisely to survive tests). The codebase's own "funnel-ish" precedents — `BarList`, the Overview "Open cases by severity" `<ul>`, `MitreHeatmap` — are all pure DOM with token color classes (`bg-critical`…`bg-info`), `role="progressbar"`, and an `sr-only` `<table>` fallback. I match that language exactly: a new `NoiseFunnel` SOC component of three CENTER-ALIGNED tapering bars whose WIDTH is proportional to that stage's total relative to Stage 1 (so the taper itself shows the reduction), each bar internally a stacked flex row of severity segments (`SEV_BAR` tokens), joined by CSS `clip-path` trapezoid "funnel walls" (pure DOM, jsdom-safe, token-themed via `hsl(var(--muted))`). This gives the clean QRadar/Splunk "flow" look with no SVG-path fragility and full control of the animation and the accessible fallback. A visual-width FLOOR (`Math.max(pct, 6)`) keeps a 96%-reduction Stage 2 from collapsing to an invisible sliver while the LABEL always prints the true count/percent.

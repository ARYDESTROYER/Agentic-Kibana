# Agentic SOC 0.1.7

Agentic SOC **0.1.7** is the governed Stable bootstrap-portability correction after
the immutable `v0.1.6` publication. Version 0.1.6 produced a valid signed artifact
set, but canonical host acceptance found that its one-time supervisor bootstrap used
an empty array expansion that exits under macOS Bash 3.2 with `set -u`. Version 0.1.7
preserves those immutable records, carries the accepted application scope forward,
and repairs that host boundary without changing application state or updater
protocol 1. It remains in the **0.1** documentation line.

!!! warning "Verify the immutable release before installation"

    A source checkout, branch head, version string, candidate image, or signed image
    alone is not a Stable release. Version 0.1.7 is installable only when the
    annotated tag `v0.1.7` resolves to the accepted `main` commit, the exact-tag CI
    and release workflows succeed, the GitHub Release contains the canonical signed
    plan and bundle, and every digest in that plan is anonymously readable. If any
    evidence is absent, continue using a previously verified Stable release.

    The immutable `v0.1.6` tag, images, signatures, plan, bundle, and GitHub Release
    remain publication evidence and must never be moved or replaced. Its clean-tag
    bootstrap is not a supported canonical installation source because it exits on
    the macOS Bash 3.2 host path before starting the supervisor. Use `v0.1.7` only
    after every acceptance gate on this page succeeds.

## What changed after 0.1.6

The one-time bootstrap no longer stores an optional Compose argument in an empty
Bash array. Apple's supported host shell is Bash 3.2, where expanding that empty
array under `set -u` raises `unbound variable` before Compose can create the private
updater. The bootstrap now calls one small helper with `"$@"`: zero optional
arguments for first installation and exactly `--force-recreate` when replacing an
inspectable idle supervisor.

CI now includes a required `macos-14` lane that proves the runner uses Bash 3.2,
syntax-checks the shipping bootstrap, extracts the shipping helper itself, and
executes both argument paths against a fake Compose wrapper. The fail-closed
aggregate requires that lane, so Ubuntu Bash 5 syntax or static source checks cannot
silently substitute for the supported host runtime again.

No application-state schema migration is introduced. The corrected release repeats
the complete candidate, promotion, exact-tag, artifact, bootstrap, and browser
acceptance sequence; no 0.1.6 result substitutes for a 0.1.7 gate. The frozen base
Compose SHA remains unchanged and all component pins remain in the signed generated
override.

## Carried Stable scope

The release carries the complete accepted product scope documented in the
[0.1.6 publication record](0.1.6.md), including:

- the Security Command Center and canonical split-pane Case Manager;
- durable Workspace Chat and governed runbook/playbook catalogs;
- explainable Intelligence inputs, analyst-confirmed tuning, approvals, export,
  and the version-matched installed Help Center;
- OpenAI live Flex preference with truthful Standard fallback and one cost ledger;
- signed, supervised updates for the supported PostgreSQL Compose topology; and
- the hardened Console, accessibility, packaging, documentation, and fail-closed CI
  contracts accumulated through the 0.1 beta patches.

The model, memory, runbook, and playbook layers remain advisory. Deterministic code
continues to own the final close/escalate route.

## Compatibility and migration

The supervised path supports only the canonical, single-replica standalone Compose
deployment with PostgreSQL-owned application state, canonical service/container/
network names, the canonical PostgreSQL volume, durable secrets,
`TLSOC_AUTH_ENABLED=true`, and updater protocol 1.

The frozen `deploy/docker-compose.agnostic.yml` SHA-256 remains:

```text
e3f7ecbb0f749cc9d88f4392c58c9a63ddbd064e80ecde9f21fe9de199086fd4
```

Release-specific version and digest pins exist only in the signed generated
override. Changing that base requires a new protocol and manual bootstrap; it must
never be hidden inside a patch plan.

SQLite, Elasticsearch-owned state, external PostgreSQL, Kubernetes, the legacy ELK
merge, horizontal replicas, modified Compose topology, missing durable secrets, or
unsupported migrations remain **Manual upgrade required**. PostgreSQL and Redis
infrastructure remain operator-managed.

There is no application-state schema migration in 0.1.7. A catalog-verified
PostgreSQL dump is still mandatory before application switching. Automatic rollback
restores prior application image pins; database restore remains an explicit
break-glass operation because restoring automatically could discard valid writes.

## Bootstrap and upgrade boundary

For a canonical deployment currently running supported Stable `v0.1.1`, use a
clean checkout of the strictly newer, fully published `v0.1.7` tag as the
host-authorized bootstrap transport:

```bash
git fetch --tags origin
git switch --detach v0.1.7
test "$(git cat-file -t v0.1.7)" = tag
test "$(git rev-parse 'v0.1.7^{commit}')" = "$(git rev-parse HEAD)"
test -z "$(git status --porcelain --untracked-files=all)"

# .env must contain durable TLSOC_PG_PASSWORD, TLSOC_AUTH_ENABLED=true,
# TLSOC_AUTH_JWT_SECRET with at least 32 characters, and:
# AGENTIC_SOC_UPDATE_REPOSITORY=ARYDESTROYER/Agentic-Kibana
./scripts/bootstrap-updater.sh
```

The bootstrap verifies the exact release before installing or reconciling the
private supervisor and applying its strictly newer plan. After the successful
transition, use `./scripts/agentic-soc-compose.sh` for every manual lifecycle
operation so the active digest override and lifecycle lock remain in effect.

Source-built/Testing deployments, the non-installable 0.1.4 or 0.1.5 attempts, and
the published-but-bootstrap-blocked 0.1.6 artifact record cannot be relabelled
Stable. Reconcile them manually to the canonical signed 0.1.7 deployment. A
deployment already running 0.1.7 cannot bootstrap from the same plan;
the updater deliberately requires a strictly newer target.

Read [Upgrades and promotion](../operations/upgrades.md) and
[Known limitations](known-limitations.md) before rehearsing the transition.

## Independent artifact verification

Verify that the remote exposes both the annotated tag object and its dereferenced
commit before inspecting release assets:

```bash
git ls-remote --tags https://github.com/ARYDESTROYER/Agentic-Kibana.git \
  refs/tags/v0.1.7 'refs/tags/v0.1.7^{}'
```

The command must return two different 40-character object IDs: the annotated tag
object and the accepted `main` commit to which it dereferences.

Install a reviewed cosign version and verify the release plan:

```bash
tag=v0.1.7
repo=ARYDESTROYER/Agentic-Kibana
identity="https://github.com/${repo}/.github/workflows/release.yml@refs/tags/${tag}"
base="https://github.com/${repo}/releases/download/${tag}"

curl --fail --location --output upgrade-plan.json "${base}/upgrade-plan.json"
curl --fail --location --output upgrade-plan.sigstore.json \
  "${base}/upgrade-plan.sigstore.json"

cosign verify-blob \
  --bundle upgrade-plan.sigstore.json \
  --certificate-identity "${identity}" \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com \
  upgrade-plan.json
```

Verify all three immutable digest references with a fresh Docker configuration
so cached credentials cannot satisfy the public-access test:

```bash
anonymous_docker_config="$(mktemp -d)"
for component in backend webui updater; do
  image="$(jq -er --arg component "${component}" \
    '.components[$component].image' upgrade-plan.json)"
  cosign verify \
    --certificate-identity "${identity}" \
    --certificate-oidc-issuer https://token.actions.githubusercontent.com \
    "${image}"
  DOCKER_CONFIG="${anonymous_docker_config}" docker buildx imagetools inspect \
    "${image}" >/dev/null
done
```

The release workflow additionally performs credential-free HTTP reads of each exact
index, child manifest, and config. Repository administrators must make the three
GHCR packages **Public** if anonymous reads return 401; package visibility is a
GitHub setting and cannot be established by image push alone.

## Release acceptance

Publication requires the fail-closed `CI passed` aggregate on the frozen 0.1.7
candidate on `Testing`, the resulting content-equivalent `main` commit, and the exact
immutable `v0.1.7` tag. The release workflow then requires:

1. the annotated tag and its dereferenced commit equal the accepted `main` SHA;
2. all three dual-platform images build, carry exact Stable labels, and are signed;
3. every image digest is anonymously readable and content-verified;
4. the canonical plan passes schema, compatibility, digest, and Sigstore checks;
5. the private draft contains exactly the canonical notes, plan, and bundle; and
6. downloaded release assets byte-match before the draft becomes public.

The candidate must also pass the Console browser matrix and canonical PostgreSQL
Compose bootstrap/update rehearsal. Never move, reuse, or repair a published tag.
Any later defect receives a newer SemVer.

## Exact Stable build identity

Resolve every Stable stamp from the exact annotated tag on the accepted `main`
commit. Never substitute a branch head, local clock, or unknown value:

```bash
git switch main
git pull --ff-only origin main
git fetch --tags origin

release_version="$(tr -d '[:space:]' < VERSION)"
test "${release_version}" = "0.1.7"
release_sha="$(git rev-parse "v${release_version}^{commit}")"
test "${release_sha}" = "$(git rev-parse HEAD)"
release_date="$(git show -s --format=%cI "${release_sha}")"

export TLSOC_VERSION="${release_version}"
export TLSOC_RELEASE_CHANNEL=stable
export TLSOC_BUILD_SHA="${release_sha}"
export TLSOC_BUILD_DATE="${release_date}"
```

Backend, Console, updater, `/release.json`, OCI labels, signed plan, tag, and GitHub
Release must all resolve to the same version and commit. A mismatch fails safe to
Testing and cannot authorize installation.

## Immutable annotated-tag checklist

Create the tag only after the clean candidate passes on `Testing`, promotion passes
on the resulting `main` commit, and the final tree is frozen:

```bash
test "$(tr -d '[:space:]' < VERSION)" = "0.1.7"
test -z "$(git status --porcelain)"
git tag -a v0.1.7 \
  -m "Agentic SOC 0.1.7" \
  -m "Stable bootstrap portability correction: macOS Bash 3.2 supervisor installation, signed supervised updates, and fail-closed native-host acceptance. Detailed notes: docs/releases/0.1.7.md; CHANGELOG.md."
test "$(git cat-file -t v0.1.7)" = tag
test "$(git rev-parse 'v0.1.7^{commit}')" = "$(git rev-parse HEAD)"
git show --no-patch --show-signature v0.1.7
git push origin v0.1.7
```

Do not create the tag before all candidate/main gates pass, and never force, delete,
move, or reassign it after push. See [Release channels and
versioning](channels.md) for the canonical promotion sequence.

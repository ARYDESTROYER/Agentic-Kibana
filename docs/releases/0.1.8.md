# Agentic SOC 0.1.8

Agentic SOC **0.1.8** is the governed least-privilege portability correction after
the immutable `v0.1.7` publication. Version 0.1.7 completed exact-tag CI, public
multi-platform images, image and plan signing, the canonical plan and bundle,
GitHub Release, and versioned Help Center. Canonical PostgreSQL Compose acceptance
then reached the updater container and found that its unconditional ownership change
for the Unix control socket is denied when every Linux capability is dropped on
Docker Desktop. The 0.1.7 image had no `USER` instruction, so the process ran as
UID/GID 0:0 and attempted to change the new socket to 0:10001 without `CAP_CHOWN`.
Version 0.1.8 preserves the complete 0.1.7 artifact record and corrects that runtime
boundary without changing application state, updater protocol 1, or the frozen base
Compose file. It remains in the **0.1** documentation line.

!!! warning "Verify the immutable release before installation"

    A source checkout, branch head, version string, candidate image, or signed image
    alone is not a Stable release. Version 0.1.8 is installable only when the
    annotated tag `v0.1.8` resolves to the accepted `main` commit, exact-tag CI and
    release workflows succeed, the GitHub Release contains the canonical signed plan
    and bundle, and every digest in that plan is anonymously readable. If any
    evidence is absent, continue using a previously verified Stable release.

    The immutable `v0.1.7` tag, public images, signatures, plan, bundle, GitHub
    Release, and Help Center remain factual publication evidence and must never be
    moved or replaced. Its canonical bootstrap is unsupported because the supervisor
    cannot publish the private control socket under the dropped-capability runtime.
    Use `v0.1.8` only after every acceptance gate on this page succeeds.

## What changed after 0.1.7

The updater remains the only component with host-runtime authority, and the ordinary
backend and browser still never receive the Docker socket. The image now starts the
supervisor process with UID 0 and application group 10001 while the reference runtime
continues to drop every Linux capability. That identity creates the private control
socket with the backend-readable group directly, so startup no longer depends on an
ownership change that the runtime is intentionally forbidden to perform.

Socket publication remains fail closed. Before the HTTP service accepts requests,
the supervisor uses `lstat` to require a Unix socket with UID 0 and the configured
GID 10001, then sets the socket mode to `0660`. An unexpected object, owner, or group
stops startup rather than widening access or continuing with a control plane the
backend cannot safely reach. Running UID 0 does not weaken the
trust boundary created by withholding the Docker socket from the browser and ordinary
backend. It does not broaden the already documented trust boundary: access to the
updater and Docker socket remains root-equivalent host authority and part of the
host trusted computing base.

Shipping-image acceptance executes the real updater image with its capabilities
dropped and inspects the control socket from the backend-facing mount. This is a
runtime contract, not only a source-level unit test. The complete candidate,
promotion, exact-tag, publication, canonical bootstrap, and browser sequence must be
repeated for 0.1.8; no 0.1.7 result substitutes for a new release gate.

No application-state schema migration is introduced. The frozen base Compose SHA is
unchanged, and all application pins remain in the signed generated override.

## Compatibility and migration

The supervised path supports only the canonical, single-replica standalone Compose
deployment with PostgreSQL-owned application state, canonical service/container/
network names, the canonical PostgreSQL volume, durable secrets,
`TLSOC_AUTH_ENABLED=true`, and updater protocol 1.

The frozen `deploy/docker-compose.agnostic.yml` SHA-256 remains:

```text
e3f7ecbb0f749cc9d88f4392c58c9a63ddbd064e80ecde9f21fe9de199086fd4
```

Release-specific version and digest pins exist only in the signed generated
override. Changing that base requires a new protocol and manual bootstrap; it must
never be hidden inside a patch plan.

SQLite, Elasticsearch-owned state, external PostgreSQL, Kubernetes, the legacy ELK
merge, horizontal replicas, modified Compose topology, missing durable secrets, or
unsupported migrations remain **Manual upgrade required**. PostgreSQL and Redis
infrastructure remain operator-managed.

There is no application-state schema migration in 0.1.8. A catalog-verified
PostgreSQL dump is still mandatory before application switching. Automatic rollback
restores prior application image pins; database restore remains an explicit
break-glass operation because restoring automatically could discard valid writes.

## Bootstrap and upgrade boundary

For a canonical deployment currently running supported Stable `v0.1.1`, use a
clean checkout of the strictly newer, fully published `v0.1.8` tag as the
host-authorized bootstrap transport:

```bash
git fetch --tags origin
git switch --detach v0.1.8
test "$(git cat-file -t v0.1.8)" = tag
test "$(git rev-parse 'v0.1.8^{commit}')" = "$(git rev-parse HEAD)"
test -z "$(git status --porcelain --untracked-files=all)"

# .env must contain durable TLSOC_PG_PASSWORD, TLSOC_AUTH_ENABLED=true,
# TLSOC_AUTH_JWT_SECRET with at least 32 characters, and:
# AGENTIC_SOC_UPDATE_REPOSITORY=ARYDESTROYER/Agentic-Kibana
./scripts/bootstrap-updater.sh
```

The bootstrap verifies the exact release before installing or reconciling the
private supervisor and applying its strictly newer plan. After the successful
transition, use `./scripts/agentic-soc-compose.sh` for every manual lifecycle
operation so the active digest override and lifecycle lock remain in effect.

Source-built/Testing deployments, the non-installable 0.1.4 or 0.1.5 attempts, and
the published-but-bootstrap-blocked 0.1.6 and 0.1.7 artifact records cannot be
relabeled Stable. Reconcile them manually to the canonical signed 0.1.8 deployment.
A deployment already running 0.1.8 cannot bootstrap from the same plan; the updater
deliberately requires a strictly newer target.

Read [Upgrades and promotion](../operations/upgrades.md) and
[Known limitations](known-limitations.md) before rehearsing the transition.

## Independent artifact verification

Verify that the remote exposes both the annotated tag object and its dereferenced
commit before inspecting release assets:

```bash
git ls-remote --tags https://github.com/ARYDESTROYER/Agentic-Kibana.git \
  refs/tags/v0.1.8 'refs/tags/v0.1.8^{}'
```

The command must return two different 40-character object IDs: the annotated tag
object and the accepted `main` commit to which it dereferences.

Install a reviewed cosign version and verify the release plan:

```bash
tag=v0.1.8
repo=ARYDESTROYER/Agentic-Kibana
identity="https://github.com/${repo}/.github/workflows/release.yml@refs/tags/${tag}"
base="https://github.com/${repo}/releases/download/${tag}"

curl --fail --location --output upgrade-plan.json "${base}/upgrade-plan.json"
curl --fail --location --output upgrade-plan.sigstore.json \
  "${base}/upgrade-plan.sigstore.json"

cosign verify-blob \
  --bundle upgrade-plan.sigstore.json \
  --certificate-identity "${identity}" \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com \
  upgrade-plan.json
```

Verify all three immutable digest references with a fresh Docker configuration so
cached credentials cannot satisfy the public-access test:

```bash
anonymous_docker_config="$(mktemp -d)"
for component in backend webui updater; do
  image="$(jq -er --arg component "${component}" \
    '.components[$component].image' upgrade-plan.json)"
  cosign verify \
    --certificate-identity "${identity}" \
    --certificate-oidc-issuer https://token.actions.githubusercontent.com \
    "${image}"
  DOCKER_CONFIG="${anonymous_docker_config}" docker buildx imagetools inspect \
    "${image}" >/dev/null
done
```

The release workflow additionally performs credential-free HTTP reads of each exact
index, child manifest, and config. Repository administrators must make the three
GHCR packages **Public** if anonymous reads return 401; package visibility is a
GitHub setting and cannot be established by image push alone.

## Release acceptance

Publication requires the fail-closed `CI passed` aggregate on the frozen 0.1.8
candidate on `Testing`, the resulting content-equivalent `main` commit, and the exact
immutable `v0.1.8` tag. The release workflow then requires:

1. the annotated tag and its dereferenced commit equal the accepted `main` SHA;
2. all three dual-platform images build, carry exact Stable labels, and are signed;
3. every image digest is anonymously readable and content-verified;
4. the canonical plan passes schema, compatibility, digest, and Sigstore checks;
5. the private draft contains exactly the canonical notes, plan, and bundle; and
6. downloaded release assets byte-match before the draft becomes public.

The candidate must also pass the Console browser matrix and canonical PostgreSQL
Compose bootstrap/update rehearsal. The required
`Smoke updater control socket without Linux capabilities` gate must start the real
read-only updater image with `cap_drop: ALL` and `no-new-privileges`, prove a separate
10001:10001 client sees a UID-0/GID-10001 socket at mode `0660`, and reach protocol-1
`/v1/status`. The end-to-end rehearsal must then apply the signed plan, retain a
durable receipt and verified backup, and activate an exact coherent backend/Console
pair. Never move, reuse, or repair a published tag. Any later defect receives a
newer SemVer.

## Exact Stable build identity

Resolve every Stable stamp from the exact annotated tag on the accepted `main`
commit. Never substitute a branch head, local clock, or unknown value:

```bash
git switch main
git pull --ff-only origin main
git fetch --tags origin

release_version="$(tr -d '[:space:]' < VERSION)"
test "${release_version}" = "0.1.8"
release_sha="$(git rev-parse "v${release_version}^{commit}")"
test "${release_sha}" = "$(git rev-parse HEAD)"
release_date="$(git show -s --format=%cI "${release_sha}")"

export TLSOC_VERSION="${release_version}"
export TLSOC_RELEASE_CHANNEL=stable
export TLSOC_BUILD_SHA="${release_sha}"
export TLSOC_BUILD_DATE="${release_date}"
```

Backend, Console, updater, `/release.json`, OCI labels, signed plan, tag, and GitHub
Release must all resolve to the same version and commit. A mismatch fails safe to
Testing and cannot authorize installation.

# Agentic SOC 0.1.2

Agentic SOC **0.1.2** was a backward-compatible beta snapshot in the **0.1**
documentation line. Its source reached `main`, but no immutable `v0.1.2` tag or
GitHub Release was published. It remains here only as a historical record and does
not create a documentation selector entry.

!!! danger "Unpublished snapshot — do not deploy or tag"

    There is no official `v0.1.2` release artifact, update plan, or bootstrap target.
    Do not create that tag retroactively and do not execute any older 0.1.2 release
    commands copied from prior drafts. Version 0.1.3 was also never published; the
    next governed release target is 0.1.4. Use the
    [0.1.4 release record](0.1.4.md) and current
    [upgrade guide](../operations/upgrades.md).

## Release highlights

### Governed Intelligence and continuous improvement

- Threshold tuning observes independently analyst-confirmed outcomes and proposes
  bounded changes for human approval by default. Missing evidence remains explicit;
  suppression always requires approval, and confirmed-evidence auto-apply remains a
  separate operator opt-in that requires shadow evaluation. Rule identifiers are
  normalized before evidence, proposal, ledger, and rollback operations, so harmless
  source whitespace cannot create a second tuning history for the same rule.
- Tuning preference changes and their durable ledger records are one governed
  operation: a ledger failure restores the exact prior preference, while rollback is
  idempotent and retry-safe. Historical duplicate rows imported from an older release
  remain historical evidence; new v0.1.2 observations converge on the normalized rule.
- Approvals, scheduler health, and tuning evidence make the reason, recommended
  action, attempts, and latest success or error visible without turning a model
  suggestion into decision authority.
- Auto-tuning now uses one attention-ordered rule-review workspace instead of
  duplicating recommendations in a separate queue. Its three-state evidence strip,
  responsive rows, and focused inspector distinguish collecting, within-policy, and
  needs-attention rules without presenting model verdicts as analyst learning.
- Intelligence now exposes five direct, non-overlapping destinations—Knowledge corpus,
  Reference runbooks, Operator memory, Response playbooks, and Agent personas—without
  hiding Personas behind a second in-page tab switcher. The old `#/catalog` deep link
  remains a compatibility alias for Response playbooks.
- Runbooks and Playbooks are durable operator catalogs layered over immutable bundled
  content. Runbooks remain retrieval guidance; Playbooks remain selected procedures;
  neither can override deterministic case policy.
- The protected reference catalog adds cloud-IAM compromise and data-exfiltration
  guidance, plus exact-match cloud-identity, exfiltration, and ransomware procedures.
  Two specialist personas cover cloud identity and data protection without adding a
  second agent engine or turning keyword similarity into procedure selection.
- Case Manager records the latest investigation's actual knowledge, approved memory,
  runbook, playbook, and tuning inputs. It does not infer use from enabled settings or
  leak earlier investigation inputs into a later run.
- Telemetry-source recommendations require versioned query or tool evidence for a
  specific investigation gap. Until a connector-neutral controlled query boundary
  emits that proof, the Console reports capture unavailable; connector absence by
  itself never creates a recommendation.

### Operations, export, and release handling

- Authorized administrators can export supported application-state scopes through
  resumable, response-bounded segments rather than treating 5,000 records as a
  lifetime ceiling. Cursors stay actor, scope, and snapshot bound; secrets and raw
  source telemetry remain excluded.
- The source-discovery and coherent-pair activation work established prerequisites
  for supervised updates, but 0.1.2 did **not** publish the supervisor, signed plan,
  or host bootstrap as an installable release. Those capabilities are included in
  the later 0.1.4 release candidate and become installable only if that candidate
  completes Stable publication; 0.1.3 also remained an unpublished snapshot.
- Settings can separately observe public Stable and Testing source revisions. That
  read-only GitHub metadata is a review aid and can never deploy, activate, restart,
  migrate, or roll back the application.
- The installed Help Center remained part of the Web artifact at `/docs/0.1/`.
  Because no `v0.1.2` tag was published, it never became an immutable public release
  or updater source.
- Repository contribution hygiene now includes a Code of Conduct, structured issue
  forms, support routing, a pull-request checklist, and generated release-note
  categories. Repository description and license remain explicit owner/legal
  decisions rather than guessed source changes.

### Console and analyst workflow

- Case Manager, Workspace Chat, setup, Settings, loading states, and the shared shell
  use the standardized Agentic SOC design system and retain Light, Dark, System,
  narrow-width, keyboard, and reduced-motion behavior.
- The Console presents exact source/model execution provenance and recorded Standard,
  Flex, Batch, or Unconfirmed cost tiers without inferring a provider discount that
  the ledger did not record.
- Noise reduction, case lifecycle, effectiveness, and tuning outcomes keep unavailable
  cohorts explicit rather than manufacturing saved time, causal improvement, or
  provider-invoice precision.

The historical change inventory is in the

## Historical boundary

The 0.1.2 snapshot is not a supported upgrade source and has no release evidence or
immutable identity to verify. Do not bootstrap from it, publish it, or create a
replacement tag. Operators upgrading from the published `v0.1.1` release must use
the current [upgrade procedure](../operations/upgrades.md) and the first later exact
annotated release that passes its complete gate.

For the active publication checklist, build identity, supported updater topology,
rollback limits, and exact command sequence, use the
[0.1.4 release record](0.1.4.md), [Known limitations](known-limitations.md), and
[Release channels and versioning](channels.md).

# Agentic SOC 0.1.2

Agentic SOC **0.1.2** is a backward-compatible beta patch in the **0.1**
documentation line. It consolidates the current Testing work into one release
identity and release record; it does not create a new documentation selector entry.

!!! warning "Candidate until promotion and tag"

    The source tree on `Testing` is a release candidate. Agentic SOC 0.1.2 becomes
    Stable only after that accepted tree is promoted to `main`, the complete release
    gate passes on the resulting commit, and the exact commit receives the immutable
    annotated tag `v0.1.2`. Until then, `v0.1.1` remains the published Stable tag.

## Release highlights

### Governed Intelligence and continuous improvement

- Threshold tuning observes independently analyst-confirmed outcomes and proposes
  bounded changes for human approval by default. Missing evidence remains explicit;
  suppression always requires approval, and confirmed-evidence auto-apply remains a
  separate operator opt-in that requires shadow evaluation. Rule identifiers are
  normalized before evidence, proposal, ledger, and rollback operations, so harmless
  source whitespace cannot create a second tuning history for the same rule.
- Tuning preference changes and their durable ledger records are one governed
  operation: a ledger failure restores the exact prior preference, while rollback is
  idempotent and retry-safe. Historical duplicate rows imported from an older release
  remain historical evidence; new v0.1.2 observations converge on the normalized rule.
- Approvals, scheduler health, and tuning evidence make the reason, recommended
  action, attempts, and latest success or error visible without turning a model
  suggestion into decision authority.
- Runbooks and Playbooks are durable operator catalogs layered over immutable bundled
  content. Runbooks remain retrieval guidance; Playbooks remain selected procedures;
  neither can override deterministic case policy.
- Case Manager records the latest investigation's actual knowledge, approved memory,
  runbook, playbook, and tuning inputs. It does not infer use from enabled settings or
  leak earlier investigation inputs into a later run.
- Telemetry-source recommendations require versioned query or tool evidence for a
  specific investigation gap. Connector absence by itself never creates a
  recommendation.

### Operations, export, and release handling

- Authorized administrators can export supported application-state scopes through
  resumable, response-bounded segments rather than treating 5,000 records as a
  lifetime ceiling. Cursors stay actor, scope, and snapshot bound; secrets and raw
  source telemetry remain excluded.
- The Console can announce a different release already deployed on the same origin.
  It offers activation only after `/release.json`, backend build-info, and health
  describe one fully stamped target, then repeats those checks and validates the new
  entry document before preserving the current hash route across reload.
- Settings can separately observe public Stable and Testing source revisions. That
  read-only GitHub metadata is a review aid and can never deploy, activate, restart,
  migrate, or roll back the application.
- The installed Help Center remains part of the Web artifact at `/docs/0.1/`; public
  GitHub Pages publication continues to update the existing `0.1`, `stable`, and
  `latest` aliases only from the exact annotated `v0.1.2` tag on verified `main`.
- Repository contribution hygiene now includes a Code of Conduct, structured issue
  forms, support routing, a pull-request checklist, and generated release-note
  categories. Repository description and license remain explicit owner/legal
  decisions rather than guessed source changes.

### Console and analyst workflow

- Case Manager, Workspace Chat, setup, Settings, loading states, and the shared shell
  use the standardized Agentic SOC design system and retain Light, Dark, System,
  narrow-width, keyboard, and reduced-motion behavior.
- The Console presents exact source/model execution provenance and recorded Standard,
  Flex, Batch, or Unconfirmed cost tiers without inferring a provider discount that
  the ledger did not record.
- Noise reduction, case lifecycle, effectiveness, and tuning outcomes keep unavailable
  cohorts explicit rather than manufacturing saved time, causal improvement, or
  provider-invoice precision.

The complete change inventory is in the [`0.1.2` changelog](https://github.com/ARYDESTROYER/Agentic-Kibana/blob/main/CHANGELOG.md).

## Upgrade boundary

Version 0.1 still does not provide a universal database migration and rollback
framework. Before replacing an installation:

1. Read [Known limitations](known-limitations.md) and [Upgrades](../operations/upgrades.md).
2. Back up the selected application state store and retain the matching deployment
   configuration and secret references.
3. Build or obtain the backend and Web artifacts from the same accepted commit.
4. Stamp both artifacts with `TLSOC_VERSION=0.1.2`, one release channel, the same
   non-`unknown` commit SHA, and the same build time.
5. Rehearse readiness and restore behavior in the Testing environment.
6. Deploy the coherent pair while retaining the previous Web build's hashed assets,
   or use an equivalent blue-green static origin, through the observation window.
7. Verify `/api/health`, `/api/health/build-info`, `/release.json`, authentication,
   Case Manager, Approvals, Intelligence catalogs, export, and installed Help Center
   before moving traffic.

Do not treat starting an older image against newer state as rollback. Restore the
matching pre-upgrade state unless compatibility has been explicitly proven.

### Exact Stable build identity

After the annotated tag exists on the already verified `main` commit, resolve the
identity from that tag and pass the same four values to both Compose image builds:

```bash
git switch main
git pull --ff-only origin main
git fetch --tags origin

release_version="$(tr -d '[:space:]' < VERSION)"
test "$release_version" = "0.1.2"
release_sha="$(git rev-parse "v${release_version}^{commit}")"
test "$release_sha" = "$(git rev-parse HEAD)"
release_date="$(git show -s --format=%cI "$release_sha")"

export TLSOC_VERSION="$release_version"
export TLSOC_RELEASE_CHANNEL=stable
export TLSOC_BUILD_SHA="$release_sha"
export TLSOC_BUILD_DATE="$release_date"

docker compose -f deploy/docker-compose.agnostic.yml build --pull \
  tlsoc-backend tlsoc-webui
```

Do not omit any variable or substitute `unknown`. The backend image reads the
channel, SHA, and build date at runtime, while the Web image compiles the same values
into `/release.json` and the immutable browser bundle. Only that exact match can
become an activatable target for an older open Console.

## What the in-app Update button does

The update control is intentionally an **activation** control, not an installer:

1. an operator or deployment system first deploys the 0.1.2 backend and static Web
   artifacts;
2. an older open Console notices the same-origin, no-store release manifest on its
   next periodic, focus, or visibility check;
3. the button appears only when that manifest exactly matches a healthy backend and
   differs from the currently running immutable Console identity;
4. confirmation is blocked while a known draft is unsaved;
5. a final no-store manifest, backend, health, and entry-document preflight succeeds;
6. the browser reloads the same route into the already-deployed build.

Pushing `Testing`, merging `main`, or creating `v0.1.2` alone does **not** make the
button appear. The browser has no Git, image-pull, process-control, migration,
credential, promotion, or rollback authority. A partial deployment, an unhealthy
backend, mismatched identities, or `unknown` provenance fails closed and leaves the
current Console running.

## Release evidence required

The candidate is ready to tag only when the exact promoted `main` commit has:

- canonical version, OpenAPI, npm/Python package, Compose image, and Help Center
  metadata aligned at `0.1.2`;
- one active empty `[Unreleased]` section and a dated `[0.1.2]` changelog section;
- backend, Web, design-system, contract, deployment, and strict documentation gates
  passing;
- a recorded Light/Dark/System desktop and narrow browser acceptance receipt against
  the exact release artifacts;
- upgrade, restore, installed-docs, release-manifest, and backend-readiness checks
  completed; and
- the annotated `v0.1.2` tag created only after the resulting `main` commit passes.

### Immutable annotated-tag checklist

On the verified `main` commit, create a descriptive annotation, prove that the tag
object and commit are exact, then push it without force:

```bash
test "$(tr -d '[:space:]' < VERSION)" = "0.1.2"
test -z "$(git status --porcelain)"
git tag -a v0.1.2 \
  -m "Agentic SOC 0.1.2" \
  -m "Beta patch: governed Intelligence, continuous-improvement evidence, portable export, safer release activation, standardized Console workflows, and version-matched Help Center. Detailed notes: docs/releases/0.1.2.md; CHANGELOG.md."
test "$(git cat-file -t v0.1.2)" = "tag"
test "$(git rev-parse 'v0.1.2^{commit}')" = "$(git rev-parse HEAD)"
git show --no-patch --show-signature v0.1.2
git push origin v0.1.2
```

`git status --short` must be empty before tagging. Publish the GitHub Release from
that existing tag, retain the detailed release page and changelog as the canonical
human-reviewed notes, and use GitHub's `.github/release.yml` categories only to add
the reviewed pull-request inventory. Never force-move a published release tag.

See [Release channels and versioning](channels.md) for the canonical promotion and
publication procedure.

# Agentic SOC 0.1.4

Agentic SOC **0.1.4** is the governed successor to `v0.1.1`. Once its immutable
publication gate completes, it is the first Stable patch published after that
release. It carries forward the accepted work from the unpublished 0.1.2 and 0.1.3
Testing snapshots and adds the immutable artifacts required by the supervised update
path. It remains in the **0.1** documentation line.

!!! warning "Candidate until the immutable release exists"

    A source checkout, branch head, or version string is not a Stable release.
    Version 0.1.4 becomes installable only after its accepted `main` commit passes
    the complete gate, receives the immutable annotated tag `v0.1.4`, and the exact
    tag workflow publishes the signed plan, public digest-pinned images, and GitHub
    Release described below. Until then, `v0.1.1` remains the last published Stable.

## Release highlights

### Signed supervised updates

- The tagged release publishes separate multi-architecture `backend`, `webui`, and
  `updater` images for `linux/amd64` and `linux/arm64`. The signed plan references
  immutable image digests; mutable version tags are operator convenience only.
- Every image and the canonical upgrade plan are signed keylessly with Sigstore by
  the exact release workflow identity for `v0.1.4`. The updater independently checks
  that identity, issuer, repository, tag, source commit, image digest, compatibility,
  and local deployment shape before permitting an installation.
- The GitHub Release is staged as a private draft, receives exactly the plan and
  Sigstore bundle, downloads and byte-compares both assets, verifies the bundle, and
  becomes public only after the entire inventory is valid.
- Anonymous GHCR reads are a publication gate. A missing or private image stops the
  workflow before an apparently installable release can be published.
- On first publication GitHub may create the three packages as private. A repository
  or organization administrator must set `backend`, `webui`, and `updater` under
  `agentic-kibana` to **Public**, then rerun the unchanged tag workflow. Never move or
  reuse the tag. Treat public package visibility as effectively irreversible.
- The supported updater remains a narrow host-authorized boundary. It verifies and
  pulls before mutation, quiesces writers, creates and catalog-verifies a PostgreSQL
  backup, switches the coherent backend/Console pair, observes health and immutable
  identity, and records durable success or rollback state.

### Accumulated beta patch

The release also includes the accepted operator-facing work recorded in the 0.1.2
and 0.1.3 Testing snapshots:

- the Security Command Center and canonical split-pane Case Manager;
- durable Workspace Chat history and governed runbook/playbook catalogs;
- explainable Intelligence inputs, analyst-confirmed tuning evidence, approvals,
  portable export, and version-matched installed Help Center;
- clearer rules, tuning, setup, Settings, sign-in, collaboration, loading, compact
  viewport, and accessibility states;
- OpenAI live Flex preference with truthful fallback and one cost ledger; and
- stricter fail-closed CI, workflow, packaging, documentation, and image-build gates.

## Compatibility and migration

The one-click path supports only the reference, single-replica standalone Compose
deployment with:

- PostgreSQL-owned application state and the canonical PostgreSQL volume;
- existing operator-managed PostgreSQL and Redis infrastructure;
- canonical project, network, service, and container names;
- durable `.env` secrets and `TLSOC_AUTH_ENABLED=true`;
- the version-invariant updater protocol v1 base Compose file; and
- updater protocol 1 with migration strategy `none`.

The frozen `deploy/docker-compose.agnostic.yml` SHA-256 is:

```text
e3f7ecbb0f749cc9d88f4392c58c9a63ddbd064e80ecde9f21fe9de199086fd4
```

Release-specific versions and digests exist only in the signed generated override.
Changing the base file requires a new protocol and manual bootstrap; it must never be
hidden in a patch plan.

SQLite, Elasticsearch-owned state, external PostgreSQL, Kubernetes, the legacy ELK
merge, horizontal replicas, modified Compose topology, missing durable secrets,
infrastructure changes, or an unsupported migration remain **Manual upgrade
required**. The updater never modifies PostgreSQL or Redis versions.

There is no application-state schema migration in 0.1.4. A verified PostgreSQL dump
is still mandatory before the application switch. Automatic rollback restores the
prior application images; it does not automatically restore PostgreSQL because that
could discard valid writes made after the snapshot. Database restore remains an
explicit break-glass operator action.

## Bootstrap and upgrade boundary

A clean exact `v0.1.4` checkout is the host-authorized bootstrap transport only when
the currently running deployment is the supported older canonical Stable release,
`v0.1.1`. The script installs or reconciles the private supervisor and asks it to
verify and apply the strictly newer signed 0.1.4 plan. After that successful
transition, later compatible Stable patches become eligible for the top-bar
supervised update action.

An existing source-built or Testing-stamped 0.1.3 deployment is not immutable Stable
and is deliberately not accepted as a bootstrap source. Reconcile it manually to the
canonical signed 0.1.4 deployment; do not relabel a mutable build as Stable. Because
the updater also requires a strictly newer target, an already-running 0.1.4
deployment cannot bootstrap itself from the same 0.1.4 plan. The next newer
compatible Stable release can establish or use the supervised path according to the
documented procedure. The historical 0.1.2 and 0.1.3 snapshots must never be tagged
retroactively.

For the supported `v0.1.1` → `v0.1.4` transition, use a clean exact-tag checkout and
durable environment on the deployment host:

```bash
git fetch --tags origin
git switch --detach v0.1.4
test "$(git cat-file -t v0.1.4)" = tag
test "$(git rev-parse 'v0.1.4^{commit}')" = "$(git rev-parse HEAD)"
test -z "$(git status --porcelain --untracked-files=all)"

# .env must include durable TLSOC_PG_PASSWORD, TLSOC_AUTH_ENABLED=true,
# TLSOC_AUTH_JWT_SECRET with at least 32 characters, and:
# AGENTIC_SOC_UPDATE_REPOSITORY=ARYDESTROYER/Agentic-Kibana
./scripts/bootstrap-updater.sh
```

After the supervisor selects a signed release, use
`./scripts/agentic-soc-compose.sh` for every manual lifecycle command. Raw Compose
commands omit the active digest override and lifecycle lock and are unsupported.

Read [Upgrades and promotion](../operations/upgrades.md) and
[Known limitations](known-limitations.md) before rehearsing the transition.

## Independent artifact verification

Install a reviewed cosign version and verify the downloaded plan:

```bash
tag=v0.1.4
repo=ARYDESTROYER/Agentic-Kibana
identity="https://github.com/${repo}/.github/workflows/release.yml@refs/tags/${tag}"
base="https://github.com/${repo}/releases/download/${tag}"

curl --fail --location --output upgrade-plan.json \
  "${base}/upgrade-plan.json"
curl --fail --location --output upgrade-plan.sigstore.json \
  "${base}/upgrade-plan.sigstore.json"

cosign verify-blob \
  --bundle upgrade-plan.sigstore.json \
  --certificate-identity "${identity}" \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com \
  upgrade-plan.json
```

Extract and verify each exact digest reference from the authenticated plan. A fresh
Docker configuration directory prevents existing registry credentials from turning
the public-access check into an authenticated one:

```bash
anonymous_docker_config="$(mktemp -d)"
for component in backend webui updater; do
  image="$(jq -er --arg component "${component}" \
    '.components[$component].image' upgrade-plan.json)"
  cosign verify \
    --certificate-identity "${identity}" \
    --certificate-oidc-issuer https://token.actions.githubusercontent.com \
    "${image}"
  DOCKER_CONFIG="${anonymous_docker_config}" docker manifest inspect "${image}" >/dev/null
  DOCKER_CONFIG="${anonymous_docker_config}" docker pull "${image}"
done
```

Both Docker commands must succeed with the fresh configuration to prove that every
exact digest is anonymously pullable. A logged-in pull does not satisfy the
public-package gate.

## Release acceptance

Publication requires the fail-closed `CI passed` aggregate to succeed independently
on:

1. the frozen 0.1.4 candidate on `Testing`;
2. the resulting content-equivalent `main` commit; and
3. the immutable `v0.1.4` tag.

The exact candidate must also pass the documented Console browser matrix and the
canonical PostgreSQL Compose upgrade rehearsal. The release workflow then verifies
the annotated tag, exact `main` SHA, tag CI, multi-architecture images, OCI labels,
anonymous registry access, image signatures, plan schema, plan signature, Release
asset bytes, and final published inventory. A tag or published Release is never
moved, overwritten, or repaired; any post-publication defect becomes 0.1.5.

## Exact Stable build identity

Resolve every Stable stamp from the exact annotated tag on the already verified
`main` commit. Do not substitute a branch head, local clock, or unknown value:

```bash
git switch main
git pull --ff-only origin main
git fetch --tags origin

release_version="$(tr -d '[:space:]' < VERSION)"
test "${release_version}" = "0.1.4"
release_sha="$(git rev-parse "v${release_version}^{commit}")"
test "${release_sha}" = "$(git rev-parse HEAD)"
release_date="$(git show -s --format=%cI "${release_sha}")"

export TLSOC_VERSION="${release_version}"
export TLSOC_RELEASE_CHANNEL=stable
export TLSOC_BUILD_SHA="${release_sha}"
export TLSOC_BUILD_DATE="${release_date}"
```

Backend, Console, updater, `/release.json`, OCI labels, signed plan, tag, and GitHub
Release must all resolve to that same version and SHA. A mismatch fails safe to
Testing and cannot authorize installation.

## Immutable annotated-tag checklist

Create the tag only on the clean, fully verified `main` commit and never force it:

```bash
test "$(tr -d '[:space:]' < VERSION)" = "0.1.4"
test -z "$(git status --porcelain)"
git tag -a v0.1.4 \
  -m "Agentic SOC 0.1.4" \
  -m "Stable beta patch: signed supervised updates, governed Intelligence, truthful operator states, responsive Console hardening, and fail-closed release acceptance. Detailed notes: docs/releases/0.1.4.md; CHANGELOG.md."
test "$(git cat-file -t v0.1.4)" = tag
test "$(git rev-parse 'v0.1.4^{commit}')" = "$(git rev-parse HEAD)"
git show --no-patch --show-signature v0.1.4
git push origin v0.1.4
```

Do not create `v0.1.4` before Testing and main acceptance, and never delete, move,
or reassign it after it is pushed. If the workflow stops before publication, repair
the external gate and rerun the exact immutable tag; the workflow may resume only
that tag's exact draft and artifacts. See [Release channels and
versioning](channels.md) for the canonical promotion sequence.

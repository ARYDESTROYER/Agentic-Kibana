# Agentic SOC 0.1.3

Agentic SOC **0.1.3** is a backward-compatible beta patch in the **0.1**
documentation line. It is built on the unpublished 0.1.2 Testing snapshot and
packages the completed release-gap hardening into one reviewable release. It does
not create a second Help Center line.

!!! warning "Release identity is tag-bound"

    This source is a Testing candidate unless and until the accepted tree is
    promoted to `main`, the complete gate passes again on the resulting commit,
    and that exact commit receives the immutable annotated tag `v0.1.3` with its
    signed artifacts. A push to `Testing`, a merge to `main`, or an observed branch
    revision is not a release by itself. Check the installed release badge and the
    immutable tag rather than inferring the channel from this page.

## What changed from the 0.1.2 Testing snapshot

### Governed Intelligence coverage

- The protected catalog adds cloud-IAM compromise and data-exfiltration runbooks,
  plus exact-match cloud-identity, exfiltration, and ransomware response playbooks.
  Dedicated cloud-identity and data-protection personas improve routing without
  creating a second agent engine.
- Runbooks remain retrieval guidance and playbooks remain recommendation-only.
  Neither can modify deterministic case policy or become executable authority.

### Supervised Stable updates

- The reference single-replica PostgreSQL Compose deployment gains a separately
  isolated update supervisor, signed and digest-pinned release plans, verified
  PostgreSQL backup, durable progress and receipts, coherent backend/Web switching,
  readiness observation, and automatic in-flight application-image rollback.
- The browser and ordinary backend never receive the Docker socket, host commands,
  arbitrary artifact coordinates, registry credentials, or migration authority.
  Unsupported state backends or deployment topologies fail closed to a documented
  manual upgrade.

### Clearer and more truthful Console states

- Shared empty states now distinguish first use, no data, no results, success,
  unavailable data, and errors. Initial request failures can no longer look like
  successful empty accounts or queues.
- Case collaboration loads discussion, tasks, and activity independently. A
  refresh failure preserves the last known good content, identifies only the
  affected region, and offers a scoped retry.
- Standup marks a degraded report as **Limited data** and never reports an empty
  attention queue as a complete success when the report itself is incomplete.
- Runbooks, Models, and other migrated surfaces use the same semantic feedback
  contract rather than page-local loading or empty-state inventions.

### Honest Detection & Rules authoring

- The rule editor exposes the one executable predicate supported by the current
  backend instead of offering additional rows that cannot be enforced.
- Cadence is presented as source-feed-owned, read-only context. Existing supported
  MITRE, schedule, and suppression metadata remains losslessly preserved when a
  rule is edited, without pretending those inactive controls are authored here.
- Preview continues to use the authoritative predicate and remains a non-billing
  what-if; deterministic close/escalate authority is unchanged.

### Responsive operational workspaces

- Detection & Rules and Case Manager now contain their tables, detail panes, and
  editor controls at narrow widths instead of widening the document or clipping
  controls.
- The shell and primary content area prevent accidental document-level horizontal
  overflow while intentional table regions retain local scrolling where needed.

### Stricter acceptance evidence

- `npm run test:strict` now fails on a non-zero Vitest result, any stderr byte, or
  captured unexpected Console output. A green test count can no longer hide noisy
  runtime diagnostics.
- CI now exposes seventeen independent quality lanes plus a fail-closed aggregate.
  Workflow/ShellCheck and deploy/updater contracts no longer hide behind one job;
  the supported PostgreSQL+pgvector/Redis path is exercised with a real readiness
  write/read; and backend, Console/Help Center, and updater images must all build and
  carry the exact candidate identity before promotion.
- A repository-owned policy checker allow-lists the complete workflow surface across
  both YAML extensions and rejects missing workflows, mutable action references,
  duplicate keys, bypasses, unsafe triggers, missing timeouts, and aggregate drift. Fatal Python
  defects are independently blocked, while weekly dependency proposals keep reviewed
  immutable action pins maintainable. Workflow shell analysis uses a checksum-verified
  ShellCheck binary rather than the runner's mutable preinstalled copy.
- Stable application artifacts and versioned Help Center publication both wait for
  the exact immutable tag's successful **CI passed** aggregate, closing the race where
  documentation could otherwise publish ahead of release acceptance.
- First-party checkout and runtime-setup actions use reviewed Node 24-compatible commit
  SHAs, removing the runner's Node 20 deprecation path from candidate checks.
- All six shipping Dockerfile base stages use reviewed multi-platform manifest digests;
  weekly Docker update proposals keep those deterministic inputs maintainable.
- The recorded candidate snapshot passed 2,306 backend tests and 1,935 frontend
  tests across 286 files, generated 217 OpenAPI paths, and built 3,189 Web modules.
  Lint, TypeScript, design-system gates, documentation checks, version contracts,
  dependency integrity, and narrow browser checks also passed. These results are
  evidence for the Testing snapshot, not a substitute for the final `main` gate.

## Compatibility and update boundary

Version 0.1.2 established source discovery and coherent-pair activation but did not
publish the host supervisor or a signed upgrade plan. Version 0.1.3 introduces that
supervised-update foundation with a version-1 protocol and canonical base-Compose
contract. It does not add a database migration, replace the base Compose file,
support another state backend, or make the updater universal.

Consequently:

- an existing `v0.1.1` reference PostgreSQL Compose deployment requires the one-time
  host-authorized bootstrap from the clean, exact annotated `v0.1.3` tag after that
  tag and its signed release assets are published;
- 0.1.2 is an unpublished historical Testing snapshot, not an operational bootstrap
  source and not an installable Stable hop;
- later compatible Stable patches may use the Console only after that supervisor is
  installed and every signed preflight condition succeeds; and
- SQLite, Elasticsearch-owned state, legacy merged ELK, Kubernetes, customized
  Compose, horizontal replicas, non-durable secrets, base/protocol mismatches, and
  migration-bearing plans continue to fail closed as manual upgrades.

The updater still has a private host-authorized boundary, requires a verified backup,
uses digest-pinned signed artifacts, retains durable receipts, and rolls application
images back on an in-flight failure. It never transports the base Compose file, never
accepts browser-supplied commands or artifact coordinates, and never restores
PostgreSQL automatically. Read [Known limitations](known-limitations.md) and
[Upgrades](../operations/upgrades.md) before an upgrade rehearsal.

## Version and patch-note discipline

Starting with version 0.1.3, every published change that affects user-visible
behavior, dependencies, configuration, API contracts, documentation, packaging, or
operational procedure receives a new SemVer and release notes. Related changes may be
bundled into one candidate; internal commits do not each need a unique version.

For the 0.1 line, backward-compatible corrections advance the integer patch component
in order: `0.1.2` → `0.1.3` → `0.1.4`. A value such as `0.1.21` means patch number 21,
not a fourth “minor-minor” component, and should not be used to encode change size.

Release notes must state what changed, operator impact, migration or rollback steps,
verification evidence, and remaining limitations. Documentation-only Stable fixes
also receive a patch version so the installed Help Center, source tag, artifacts, and
public guidance stay attributable to one release identity.

## Promotion checklist

1. Keep `0.1.3` on `Testing` while integration and upgrade rehearsal run.
2. Align root `VERSION`, package/image metadata, generated contracts, installed Help
   Center, changelog, and release notes in the same candidate.
3. Pass the complete backend, strict frontend, lint, type, design, documentation,
   packaging, deployment-configuration, and browser acceptance gate.
4. Promote the accepted tree to `main` without content changes and run the complete
   gate again on the resulting `main` commit.
5. Only then create the immutable annotated `v0.1.3` tag from that exact commit and
   publish its signed artifacts and the existing **0.1** documentation line.

If any release artifact or note requires correction after publication, prepare
`0.1.4`; never move or reuse `v0.1.3`.

### Exact Stable build identity

Resolve every Stable stamp from the exact annotated tag on the already verified
`main` commit. Do not substitute a branch head, local clock, or `unknown` value:

```bash
git switch main
git pull --ff-only origin main
git fetch --tags origin

release_version="$(tr -d '[:space:]' < VERSION)"
test "$release_version" = "0.1.3"
release_sha="$(git rev-parse "v${release_version}^{commit}")"
test "$release_sha" = "$(git rev-parse HEAD)"
release_date="$(git show -s --format=%cI "$release_sha")"

export TLSOC_VERSION="$release_version"
export TLSOC_RELEASE_CHANNEL=stable
export TLSOC_BUILD_SHA="$release_sha"
export TLSOC_BUILD_DATE="$release_date"
```

Backend, Web, updater, `/release.json`, and release-plan identities must resolve to
that same version and SHA. A mismatch fails safe to Testing and cannot become an
installable update.

### Immutable annotated-tag checklist

On the clean, fully verified `main` tree, create and inspect the tag without force:

```bash
test "$(tr -d '[:space:]' < VERSION)" = "0.1.3"
test -z "$(git status --porcelain)"
git tag -a v0.1.3 \
  -m "Agentic SOC 0.1.3" \
  -m "Beta patch: release-gap hardening, truthful Console states, honest rule authoring, responsive operations, and stricter acceptance evidence. Detailed notes: docs/releases/0.1.3.md; CHANGELOG.md."
test "$(git cat-file -t v0.1.3)" = "tag"
test "$(git rev-parse 'v0.1.3^{commit}')" = "$(git rev-parse HEAD)"
git show --no-patch --show-signature v0.1.3
git push origin v0.1.3
```

The GitHub Release workflow must publish only after its exact signed plan, signature
bundle, image digests, and tag/SHA identity verify. A published release is immutable;
repair any post-publication defect as `0.1.4`.

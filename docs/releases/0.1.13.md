# Agentic SOC 0.1.13

Agentic SOC **0.1.13** corrects the canonical-runtime blocker found after
the otherwise complete v0.1.12 signed publication. The immutable v0.1.12 images,
plan, bundle, signatures, attestations, anonymous pulls, GitHub Release, and Stable
documentation all verified. Its canonical v0.1.1 bootstrap then stopped safely
before application mutation because both legacy application images omit the
state-schema OCI label and the updater compared one normalized missing value with
one raw missing value.

The correction normalizes an absent state-schema label on both installed components
to the same explicit `unknown` value for coherence comparison. The existing
one-time v0.1.1 bootstrap exception may then evaluate that coherent legacy identity.
Mixed labels still fail. Every later release still requires matching version,
channel, immutable revision, image IDs, and state-schema-1 labels.

This patch does not change application state schema, updater protocol, signed-plan
schema, keyless publisher identity, privileges, migration behavior, or the frozen
base Compose file. It remains in documentation line **0.1**.

!!! warning "A candidate is not an installable Stable release"

    Branch content, a version string, an image tag, or a signature alone is not
    update authority. Version 0.1.13 is installable only after the exact accepted
    `main` commit has the immutable annotated tag `v0.1.13`, the tag and release
    workflows pass, all three public pinned images and signatures verify, the
    canonical plan and bundle publish, and canonical v0.1.1 supervised-update plus
    browser acceptance succeeds. Never move or reuse the tag.

## Operator-visible change

- Canonical v0.1.1 deployments whose backend and Web images both omit
  `io.agentic-soc.state.schema` can pass the intended one-time host-authorized
  bootstrap identity check.
- A deployment where just one component has the label remains blocked as a mixed
  identity.
- Version 0.1.2 or later without exact managed Stable identity and schema-1 labels
  remains blocked. The fix does not create a general source-build escape hatch.
- The Console update flow, deterministic decision boundary, authorization, backup,
  rollback, and signed-artifact checks are unchanged.

## Signed plan and compatibility

Plan schema remains **1**. The release record must bind:

- product `agentic-soc`, version `0.1.13`, tag `v0.1.13`, channel `stable`, and the
  exact 40-character lowercase tag commit;
- supported source versions `>=0.1.1,<0.2.0`;
- PostgreSQL-owned state only, state schema 1, updater protocol 1;
- a verified backup and migration strategy `none`;
- the exact frozen Compose SHA-256
  `e3f7ecbb0f749cc9d88f4392c58c9a63ddbd064e80ecde9f21fe9de199086fd4`;
- the three immutable component references and matching OCI labels; and
- bounded backend, Web, and observation timeouts.

Release-specific image pins exist only in the updater-generated signed override.
`deploy/docker-compose.agnostic.yml` must remain byte-identical. A base-file change
requires a new protocol and explicit manual bootstrap; it cannot be hidden in this
patch.

Supported automatic update topology remains the canonical single-replica
PostgreSQL Compose profile with standard project/service/container/network names,
the canonical owned-state volume, durable environment secrets,
`TLSOC_AUTH_ENABLED=true`, and a 32-or-more-character JWT secret. SQLite,
Elasticsearch-owned state, external PostgreSQL, Kubernetes, horizontal replicas,
modified Compose topology, missing durable secrets, and unsupported migrations use
the manual path.

The backend build-info endpoint, Web `/release.json`, plan, image labels, and tag
must agree on that version, channel, and commit. The required release workflow uses
the same values and publishes only after exact-tag CI passes.

## Immutable annotated-tag checklist

1. Merge the exact candidate through protected `Testing` after its fail-closed
   `CI passed` aggregate succeeds.
2. Verify the resulting Testing push aggregate, then promote the content to
   protected `main` through a pull request without release-content drift.
3. Verify the exact `main` push aggregate.
4. Create the annotated tag once from that accepted main commit:

   ```bash
   git tag -a v0.1.13 -m "Agentic SOC v0.1.13"
   git show --no-patch --format=fuller v0.1.13
   git push origin refs/tags/v0.1.13
   ```

5. Require exact-tag CI and the signed-release workflow to pass completely. Do not
   use `continue-on-error`, move the tag, or republish altered artifacts.
6. Verify public assets, anonymous digest reads, keyless signatures, canonical
   bootstrap, supervisor receipt, application health, and browser controls before
   declaring the release installable.

## Operator bootstrap

Use a clean checkout of the accepted tag on the host that owns the canonical
deployment:

```bash
git clone --branch v0.1.13 --depth 1 \
  https://github.com/ARYDESTROYER/Agentic-Kibana.git agentic-soc-0.1.13
cd agentic-soc-0.1.13
test "$(shasum -a 256 deploy/docker-compose.agnostic.yml | awk '{print $1}')" = \
  "$(tr -d '[:space:]' < deploy/update-base-v1.sha256)"
test "$(git cat-file -t v0.1.13)" = "tag"
test "$(git describe --tags --exact-match)" = "v0.1.13"
test "$(git rev-parse HEAD)" = "$(git rev-parse 'v0.1.13^{}')"
test -z "$(git status --porcelain --untracked-files=all)"
./scripts/bootstrap-updater.sh
```

The script installs the narrow private-socket supervisor, downloads the canonical
plan and Sigstore bundle from the public Release, verifies them, runs preflight,
pulls and verifies the pinned images, backs up PostgreSQL, writes the generated
override, performs the rollout, observes health, and records a durable receipt.
It must be run from the exact tag; do not copy the script into another checkout or
hand-edit the frozen base/override.

After bootstrap, use the wrapper and public health endpoints:

```bash
./scripts/update-runtime.sh ps
curl --fail --silent http://127.0.0.1:8080/api/health/ready
curl --fail --silent http://127.0.0.1:8080/api/health/build-info
curl --fail --silent http://127.0.0.1:8080/release.json
curl --fail --silent http://127.0.0.1:8080/index.html >/dev/null
```

The Console must report `v0.1.13 · Stable`; its release manifest and the healthy
backend must agree on the exact commit. The update sheet must expose the completed
receipt. An already-running 0.1.13 deployment cannot apply the same-version plan;
the next strictly newer compatible Stable patch will make the update action
available.

## Rollback and known limits

The updater captures prior immutable application pins, creates and verifies a
PostgreSQL backup, and rolls application images back automatically on failed
rollout/observation. Database restore remains an explicit break-glass operation so
automation cannot discard valid writes. The runtime keeps durable receipts and
does not auto-prune updater records in 0.1.13.

This patch intentionally fixes only legacy identity normalization. It does not
broaden supported topology, change the trust root, add online state migrations,
upgrade PostgreSQL/Redis, or make source-built post-v0.1.1 deployments eligible.
See [Known limitations](known-limitations.md), [Upgrade operations](../operations/upgrades.md),
and [Release channels](channels.md) before authorizing an update.

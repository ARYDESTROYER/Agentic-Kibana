# Agentic SOC 0.1.11

Agentic SOC **0.1.11** is the governed native-builder portability correction after
the immutable, non-installable `v0.1.10` attempt. Version 0.1.10 passed protected
`Testing`, promoted-`main`, and exact-tag CI, then its signed-release job reached the
fail-closed 120-minute timeout while the arm64 Web Console target was running
architecture-independent `npm ci` under target emulation. Publication stopped before
the complete three-image set, image signatures, canonical signed plan, attestations,
GitHub Release, Stable tags, or Stable Help Center existed.

Version 0.1.11 pins only the Console's Python documentation and Node application
builder stages to BuildKit's native build platform. The final nginx runtime stage
remains target-platform-specific, so the published image remains a real linux/amd64
and linux/arm64 manifest. A fail-closed CI policy test prevents either builder from
returning to target emulation and prevents the final runtime from becoming a
single-platform native artifact.

This patch changes no application behavior, application-state schema, updater
protocol, signed-plan schema, keyless publisher identity, process UID/GID,
capability set, trust predicate, or frozen base Compose file. It remains in
documentation line **0.1**.

!!! warning "Verify the immutable release before installation"

    A checkout, branch head, version string, candidate image, generated plan, or
    signature alone is not a Stable release. Version 0.1.11 becomes installable only
    when the annotated tag `v0.1.11` resolves to the accepted `main` commit, every
    fail-closed tag and release gate passes, the public GitHub Release contains
    exactly the canonical plan and bundle, all three pinned digests are anonymously
    readable and signature-verified, and canonical bootstrap/update acceptance
    succeeds. If any evidence is missing, keep the existing supported deployment
    unchanged.

    The immutable `v0.1.10` tag and partial backend candidate are historical
    evidence only. Its GitHub Release and canonical asset pair do not exist. Never
    move, reuse, repair, install, or bootstrap from that tag.

## What changed after 0.1.10

The Web Console Dockerfile separates build-host work from target-runtime work:

```dockerfile
FROM --platform=$BUILDPLATFORM python:3.11-alpine@sha256:<pinned> AS docs
FROM --platform=$BUILDPLATFORM node:22-alpine@sha256:<pinned> AS build
# No platform override: Docker builds the final nginx stage for TARGETPLATFORM.
FROM nginx:1.27-alpine@sha256:<pinned>
```

The documentation bundle and Vite application assets are architecture-neutral.
They now build once per invocation using native Python and Node tooling instead of
running package installation under QEMU for a non-native target. The final nginx
stage still resolves independently for each requested target and copies the same
verified static artifacts into each runtime image.

CI parses the shipping Dockerfile and requires:

1. the named `docs` and `build` stages use exactly `$BUILDPLATFORM`;
2. the unnamed final runtime is the last stage, has no platform override, and
   therefore retains Docker's requested `$TARGETPLATFORM`; and
3. all shipping base images remain digest-pinned.

The 0.1.10 least-privilege verification-fixture correction also remains: the plan
and Sigstore bundle are mode `0444` beneath a mode-`0555` read-only verification
directory before the real constrained updater starts. Sigstore trust state remains
on the existing updater-state volume:

```text
TUF_ROOT=/var/lib/agentic-soc-updater/sigstore-root
```

The updater remains the only host-authorized component. The backend and Console
never receive the Docker socket, registry credentials, host commands, arbitrary
artifact coordinates, Compose text, or migration authority.

## Carried application scope

This patch carries the complete accepted 0.1 application scope described by the
[0.1 release line](0.1.md), including:

- vendor-neutral OCSF ingest, deterministic correlation/risk/decision boundaries,
  and one cost-ledgered LLM gateway;
- the Security Command Center, canonical split-pane Case Manager, durable Workspace
  Chat, collaboration, and version-matched installed Help Center;
- governed runbook/playbook, memory, tuning, rules, approval, enrichment, and export
  workflows; and
- signed supervised updates for the supported canonical PostgreSQL Compose profile.

The model, memory, runbook, and playbook layers remain advisory. Deterministic code
continues to own the final close/escalate route.

## Compatibility and migration

The supervised path supports only the canonical single-replica standalone Compose
deployment with PostgreSQL-owned state, canonical project/service/container/network
names, the canonical PostgreSQL volume, durable secrets,
`TLSOC_AUTH_ENABLED=true`, and updater protocol 1.

The frozen `deploy/docker-compose.agnostic.yml` SHA-256 remains:

```text
e3f7ecbb0f749cc9d88f4392c58c9a63ddbd064e80ecde9f21fe9de199086fd4
```

Release-specific version and digest pins exist only in the signed generated
override. A base-file change requires a new protocol and manual bootstrap; it cannot
be hidden in a patch plan.

SQLite, Elasticsearch-owned state, external PostgreSQL, Kubernetes, the legacy ELK
merge, horizontal replicas, modified Compose topology, missing durable secrets, or
unsupported migrations remain **Manual upgrade required**. PostgreSQL and Redis
infrastructure remain operator-managed.

There is no application-state schema migration in 0.1.11. A verified PostgreSQL
dump is mandatory before switching. Automatic rollback restores prior application
image pins; database restore remains an explicit break-glass operation because an
automatic restore could discard valid writes.

## Bootstrap and upgrade boundary

For a canonical deployment running supported Stable `v0.1.1`, use a clean checkout
of the strictly newer, fully published `v0.1.11` tag as the one-time host-authorized
bootstrap transport:

```bash
git fetch --tags origin
git switch --detach v0.1.11
test "$(git cat-file -t v0.1.11)" = tag
test "$(git rev-parse 'v0.1.11^{commit}')" = "$(git rev-parse HEAD)"
test -z "$(git status --porcelain --untracked-files=all)"

# .env must contain durable TLSOC_PG_PASSWORD, TLSOC_AUTH_ENABLED=true,
# TLSOC_AUTH_JWT_SECRET with at least 32 characters, and:
# AGENTIC_SOC_UPDATE_REPOSITORY=ARYDESTROYER/Agentic-Kibana
./scripts/bootstrap-updater.sh
```

Bootstrap verifies the exact public Release before installing or reconciling the
private supervisor and applying its strictly newer plan. If an earlier failed
attempt left an inspectable idle supervisor whose version differs from 0.1.11,
bootstrap preserves durable state and replaces it with the exact 0.1.11 updater.
Active, unreadable, malformed, or otherwise unsafe supervisor state fails closed.

After a successful transition, use `./scripts/agentic-soc-compose.sh` for every
manual lifecycle operation so the active digest override and lifecycle lock remain
in effect. A deployment already running 0.1.11 cannot bootstrap from the same plan;
future compatible releases are installed through the Console after recent built-in
super-admin reauthentication and server-bound preflight confirmation.

Source-built/Testing 0.1.3 and immutable 0.1.4 through 0.1.10 failed or
bootstrap-blocked records cannot be relabelled Stable. Reconcile them according to
their actual installed state.

Read [Upgrades](../operations/upgrades.md) and [Known
limitations](known-limitations.md) before rehearsing the transition.

## Independent artifact verification

Verify that the remote exposes both the annotated tag object and its dereferenced
commit:

```bash
git ls-remote --tags https://github.com/ARYDESTROYER/Agentic-Kibana.git \
  refs/tags/v0.1.11 'refs/tags/v0.1.11^{}'
```

The command must return two different 40-character IDs: the tag object and the
accepted `main` commit.

Verify the canonical plan with a reviewed cosign installation:

```bash
tag=v0.1.11
repo=ARYDESTROYER/Agentic-Kibana
identity="https://github.com/${repo}/.github/workflows/release.yml@refs/tags/${tag}"
base="https://github.com/${repo}/releases/download/${tag}"

curl --fail --location --output upgrade-plan.json "${base}/upgrade-plan.json"
curl --fail --location --output upgrade-plan.sigstore.json \
  "${base}/upgrade-plan.sigstore.json"

cosign verify-blob \
  --bundle upgrade-plan.sigstore.json \
  --certificate-identity "${identity}" \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com \
  upgrade-plan.json
```

Verify every immutable image signature and anonymous registry read with a fresh
Docker configuration so cached credentials cannot satisfy the public-access test:

```bash
anonymous_docker_config="$(mktemp -d)"
for component in backend webui updater; do
  image="$(jq -er --arg component "${component}" \
    '.components[$component].image' upgrade-plan.json)"
  cosign verify \
    --certificate-identity "${identity}" \
    --certificate-oidc-issuer https://token.actions.githubusercontent.com \
    "${image}"
  DOCKER_CONFIG="${anonymous_docker_config}" docker buildx imagetools inspect \
    "${image}" >/dev/null
done
```

The workflow also performs credential-free HTTP verification of every exact index,
child manifest, and config. All three GHCR packages must be **Public**; image push
alone does not change package visibility.

## Release acceptance

Publication requires the fail-closed `CI passed` aggregate on the frozen 0.1.11
candidate on `Testing`, the resulting accepted `main` commit, and the immutable
`v0.1.11` tag. The tag workflow then requires:

1. annotated tag and dereferenced commit equal the accepted `main` SHA;
2. all three dual-platform images build with exact Stable labels and signatures;
3. every image digest is anonymously readable and content-verified;
4. the plan passes schema, compatibility, digest, and Sigstore checks;
5. the real updater verifies the plan inside the production-constrained runtime,
   including readable immutable verification inputs and writable TUF state;
6. attestations complete;
7. the private draft contains exactly the canonical notes, plan, and bundle;
8. downloaded assets byte-match and signature-verify before one atomic public
   transition; and
9. Stable convenience tags are created only after Release publication.

Canonical PostgreSQL Compose acceptance must then bootstrap from the supported
baseline, retain the verified backup and durable receipt, switch to the exact plan
digests, and pass the post-update Console browser matrix. Never move, reuse, repair,
or republish a tag. Any later defect receives a newer SemVer.

## Exact Stable build identity

Resolve every Stable stamp from the exact annotated tag on the accepted `main`
commit. Never substitute a branch head, local clock, or unknown value:

```bash
git switch main
git pull --ff-only origin main
git fetch --tags origin

release_version="$(tr -d '[:space:]' < VERSION)"
test "${release_version}" = "0.1.11"
release_sha="$(git rev-parse "v${release_version}^{commit}")"
test "${release_sha}" = "$(git rev-parse HEAD)"
release_date="$(git show -s --format=%cI "${release_sha}")"

export TLSOC_VERSION="${release_version}"
export TLSOC_RELEASE_CHANNEL=stable
export TLSOC_BUILD_SHA="${release_sha}"
export TLSOC_BUILD_DATE="${release_date}"
```

Backend, Console, updater, `/release.json`, OCI labels, signed plan, annotated tag
`v0.1.11`, and GitHub Release must resolve to one version and commit. Any mismatch
fails safe to Testing and cannot authorize installation.

## Immutable annotated-tag checklist

Create the tag only after the clean candidate passes on `Testing`, promotion passes
on the resulting `main` commit, and the final tree is frozen:

```bash
test "$(tr -d '[:space:]' < VERSION)" = "0.1.11"
test -z "$(git status --porcelain)"
git tag -a v0.1.11 \
  -m "Agentic SOC 0.1.11" \
  -m "Native-builder portability correction: native architecture-neutral Console builders with a dual-platform target runtime. Detailed notes: docs/releases/0.1.11.md; CHANGELOG.md."
test "$(git cat-file -t v0.1.11)" = tag
test "$(git rev-parse 'v0.1.11^{commit}')" = "$(git rev-parse HEAD)"
git show --no-patch --show-signature v0.1.11
git push origin v0.1.11
```

Do not create the tag before every candidate/main gate passes, and never force,
delete, move, recreate, or reassign it after push. See [Release channels and
versioning](channels.md) for the canonical promotion sequence.
